Technical Monograph · 精读报告 发布 2026 年 11 月 18 日 生成 2026 年 11 月 19 日

Matt Pocock 用一期近七十分钟的实况，把自己的课程视频管理器里一个用了七年的缩略图流程彻底重做了一遍：以后做封面，不必再截图、粘贴、来回摆弄，直接在自己的照片旁边画图。整件事只用了两条主线技能——开头的 grill-with-docs 与结尾的 retro。前面四十分钟几乎没写一行代码，全花在拷问上：术语表里给每个概念定名，架构决策记录里写下每个“为什么”，再拿场景测试检验哪种说法最贴合直觉，顺手做出三个原型挑出一个；随后把规格与工单写成目的地，压缩上下文，让 Agent 离线并行实现，交出一个两万一千行的 PR；最后把这个大 PR 拆成七个能逐个回滚的叠层 diff，逐行审读，审出的十二条意见全部指向同一个根因——代码库的成文标准与现状背道而驰。他的结论是：人最有价值的时刻在两头，开头的对齐与结尾的审读，中间交给机器。

Key Takeaways

  1. 先定语言，再写代码。术语表定下来，数据模型、表名与模块就都有了落点；语言没对齐之前写代码，等于在流沙上施工。
  2. 提问要给“为什么”，不要给“怎么做”。把问题讲清，Agent 才有空间拿出比你更好的方案；把做法讲死，它只会照抄你的平庸。
  3. 实现之前先把决策空间收干净。规格、工单、原型三件套齐全，Agent 离线跑才不会在细枝末节上自作主张；每多一个未决定的点，就多一次踩错的机会。
  4. 大 PR 要拆成能逐个回滚的小门。双向门随便进出，单向门只留最后一扇；能用功能开关兜底的，先并行跑着再开闸。
  5. 审代码不是审代码，是审生产代码的系统。审出的每一类问题都该变成一条可递增收紧的 lint 规则或一段改掉的文档；注释是绕开设计的遮羞布，删掉它，改掉绕路本身。

1. 开场：一个用了七年的缩略图流程

开场没有铺垫，直接交代任务：给 CVM（Course Video Manager，他自己的课程视频管理应用）做一个缩略图编辑器。缩略图这件事，他对着镜头说，自己手工做了七年：拍一张脸、画几个框、拼一张图，次次如此。这次要把它做进 CVM，让缩略图成为视频发布流程里的一步，而不是发布前的一次手工活。动手之前，他先把决策树摆出来：小改动直接 oneshot，一次提示词写完；大的先走 grill-with-docs，拷问一轮再动手；巨大的走 Wayfinder，先画一张决策地图。这期属于中间那档：先拷问，再动手。

场地与工具也一次交代清楚：他的 home repo、Claude Code、模型 Opus 5.5、Claude Ultra 订阅，口述用 Whisper Flow。1 分 33 秒处，他点开 CVM 的视频列表——“Building CVM Thumbnail View”赫然在列，48 秒，那是他之前录的一段演示；这次要做的，就是把演示里那个东西真正造出来。开场他随口说了 25,000 行，那是估算；最终落点是 21,000 行，这个数字以正文为准，差异见脚注。

还有一句开场白值得记住：这期不是表演写代码，而是把他那套技能（mattpocock/skills）从头用到尾——grill-with-docs、to-spec、to-tickets、implement-spec、retro，一个不少。21,000 行代码是结果，对齐才是过程；这期视频要拍的，其实是后者。

2. 拷问的艺术

4 分 42 秒，拷问开始。终端里敲下 /grill-with-docs，第一条规矩就来了：给 agent 讲“为什么”，别讲“怎么做”。提示词里写满实现细节，是他点名最常见的错——细节越多，agent 自由发挥的余地越小，选错的可能越大；把“为什么”讲清楚，agent 才有空间自己拿出方案。

“If you give it the why, then the agent feels a lot more empowered to go away and actually produce a solution itself.”给它“为什么”，它就更有底气自己走开、拿出一个方案。

拷问的问法也有讲究：一次只问一个问题；语言要松，不要一上来就钉死术语；后台 agent 先去搜集信息，人来主导对话——用他的话说，“you drive the conversation”。第一轮从 Q1 问到 Q7：缩略图是什么、谁来画、画在哪、存在哪……每个问题都把决策空间收窄一点。拷问不是走过场，他说，这活儿其实远比大多数人以为的更像一门手艺。

“Grilling is really much more of an art form than most people assume.”拷问其实远比大多数人以为的更像一门手艺。

■ 拷问 Grilling：在写代码之前，由 agent 一次一个问题地追问，把想法与现有仓库的语言、规则对齐；问完才有规约，没有规约不动手。

拷问发生的地方不是 CVM 仓库本身，而是他的 home repo——拷问先对齐语言，再落到具体仓库。这也是 grill-with-docs 与 grill-me 的区别：前者有仓库可写，拷问的成果会留进术语表与 ADR，成为纸面记录；后者只是聊一聊。

3. 语言就是数据模型

10 分 23 秒，术语表登场。GLOSSARY.md，约 560 行，是他“最引以为傲”的文件。打开看：每个词条不只有定义，还有禁用词（Avoid）——比如 Job 的定义是“作者发起、然后走开的工作”，禁用词是 Task、Upload、Background request；Sidecar 是“应用旁边跑 Job 的进程”，禁用 Worker、Daemon、Queue。定义告诉你这个词是什么，禁用词告诉你它不是什么，两面夹住，词义才钉得死。

为什么要较真到这个地步？因为五个长得几乎一样的词——diagram、diagram snapshot、active diagram、restore to head、preserved snapshot——在代码里是五种不同的东西；缩略图那边也一样：thumbnail、thumbnail diagram、thumbnail drawing、thumbnail scene，四者各指各的。语言没对齐，代码一定对不齐。他的判断只有一句，放在这里当纲。

“Once I’ve figured out the language, then I’ve actually figured out the app.”一旦我把语言想明白了，应用本身也就想明白了。

15 分 19 秒，ADR 与数据模型。决定一处，写一处 ADR（架构决策记录），连同“为什么不选另一条路”一起留下。他在这里引用了切斯特顿的篱笆：在弄清一堵篱笆当初为何立起之前，不要拆掉它。旧代码里的怪设计，很可能就是这样一堵篱笆。

“Do not remove a fence until you know why it was put up in the first place.”在弄清一堵篱笆当初为何立起之前，不要拆掉它。（切斯特顿，Pocock 引用）

22 分 37 秒，场景测试：拿具体场景去试决策，而不是空谈。拷问进行中，agent 会急着写新的 ADR——可以写，但要经过人点头才算数。还有两条纪律：一次只问一个问题；别把两条思路混在一起。连“从哪个快照出发”这类引用关系，也要写进术语表钉住。

■ 术语表 Glossary（GLOSSARY.md）：仓库的通用语言手册；每条词给出定义与禁用词，语言对齐了，数据模型才对得齐。

■ 架构决策记录 ADR：把一项架构决定连同“为什么不选另一条路”写下来；本期新立 ADR 0060，标题本身就是结论。

■ 场景测试 Scenario Testing：用具体场景去验证一个设计决定是否成立，而不是空谈原则。

4. 原型三选一

25 分 36 秒，拷问加宽：Q14 一路问到 Q40。加宽的拷问定下了软删除等边界，也撞上一个命名冲突：图组件（Diagram Component）与 React 组件同名，必须分清——名字撞了，讨论就没法进行，这正是术语表存在的理由。

33 分 13 秒，三个原型。A 是“Live editor in the frame”：直接在画面里画框，把人脸框进画面；胜出的是它，B 与 C 留在原地当参照。A 里有个“Ghost face”开关：指针悬停时人脸半透明，不挡画布。原型只回答一个设计问题，答完就扔——这是 prototype 技能的规矩，也是它与正式实现的分界。

37 分 21 秒，白条 bug。先搭复现工具（reproduction harness），把 bug 关进笼子再谈修：根因是 Windows 125% 缩放下，Chrome 把一张 120 像素宽的图片缩放后，最后一列像素只画了一部分，留下一条白边。不是逻辑错，是渲染错——复现工具的价值就在这里：没有它，这种 bug 只能靠运气复现。

“The more decisions you give it, the more decision space it has, the more likely it is to choose a bad one.”你给它的决策越多，它的决策空间就越大，选错的可能也就越大。

40 分 15 秒，聪明区与笨区。这个说法他归于 Human Layer 的 Dex Horthy：聪明区是“想明白”，笨区是“动手干”。聪明区只能有一小块，因为关系按平方增长——约 15 万 Token 的上下文里，agent 还能 hold 住；放一个子 agent 进去，26 万 Token 也不是不能谈，但聪明区必须小。命名、结构、边界属于聪明区；重复劳动属于笨区。分不清这两块，agent 就会在不该动脑子的地方动脑子。

42 分 28 秒，to-spec 与 to-tickets：拷问的成果收成一份规约，再切成约 47 个用户故事、9 张票。每张票都是纵切：从界面到底层，一票走通一条线，而不是“先写后端、再写前端”的横切。

■ 软删除 Soft Delete：被删的条目不是真删，而是先标记删除、留一条可恢复的痕迹；边界在加宽的拷问里定下。

■ 聪明区与笨区 Smart Zone / Dumb Zone：聪明区做需要判断的事（命名、结构、边界），笨区做重复劳动；聪明区必须小，因为其中的关系按平方增长。

5. 离线实现

46 分 28 秒，压缩与离线。手动压缩是安全的，自动压缩不可靠——上下文一旦被自动压掉，对齐就丢了。所以实现这一步，他选了 implement-spec v1.3：规约与票据一次读进，多个子 agent 并行开工，人离开座位约 45 到 60 分钟。这一步的名字就叫 AFK：人不在场，机器干活。

回来时，21,000 行代码已经长在集成（integration）分支上。code review 跑了一遍：1 处硬违反，外加一点范围蔓延。数字本身不重要，重要的是顺序：先对齐、再离线、最后审——审的不是代码写得好不好，而是它有没有偏离之前定下的语言。

这里有个容易误读的点：21,000 行不是一个人一晚上敲出来的，是多 agent 并行、按票推进的结果；人做的事在两头——开头对齐，结尾审阅。中间那段“离线”，恰恰是这套方法要买的东西：把人的注意力从实现里抽出来，留给判断。

6. 拆 PR

48 分 43 秒，叠层 diff（stacked diffs）。21,000 行不能一次合进主分支，要拆成 7 个 PR；最后一个 PR 太大，又拆成 4 个。每个 PR 是一道“小门”：能逐个合、逐个回滚。两扇门之间还有区别：双向门可以反悔，单向门不能；叠层 diff 的意义，就是把尽量多的决定变成双向门，再加一个 feature flag 兜底。

51 分 30 秒，人工审阅。PR 1 是术语表加 ADR 0060——先合语言，再合代码。#2736 号 PR 的标题就是“Thumbnails glossary terms, Diagram Component and ADR 0060”，分支 stack/1-terms-adr，只改两个文件。审阅的规矩是：每一行都要有人看过；机器审过的，人才放心合。

审阅时，ADR 0060 的标题本身就是结论：《A Thumbnail Diagram is not a Diagram》——缩略图有自己的绘图，在作者脸边就地编辑，要一个属于自己的 TLDraw 场景，而不是复用 diagram 的快照机制。决定是“把两条流分开”：缩略图没有 Clips，快照那套机器只会多添规则；两边在 TLDraw 层面共享一切，往上各走各的。模型还必须不丢信息：缩略图从空开始，形状从哪复制进来，就记下它的来源。

■ 叠层 diff Stacked Diffs：把一个大改动拆成一串上下相依的小 PR，逐个合、逐个回滚；最后一个 PR 太大时再拆。

■ 双向门与单向门 Two-Way Doors / One-Way Doors：双向门做了可以反悔，单向门做了无法回头；能变成双向门的决定，都不要做成单向门。

7. 复盘

57 分 50 秒，合并与复盘。7 个 PR 按顺序合进主分支，交给后台子 agent 去跑。合完之后跑 /retro：回顾约 30 个会话与 12 条审阅意见，问的不是代码哪里错了，而是环境哪里没管住——标准没覆盖的地方，旧代码反着写的地方。复盘的产出不是代码，是环境：导航提示、自动检查、编码标准。

棘轮（ratchet）就是这么来的：as 类型断言全仓库约 2,000 处，逐个收；交叉类型改写成 interface extends；约 230 个 useEffect 散在 140 个文件里，逐个审；useSearchParams 里的魔法字符串、裸 fetch 调用，都要有类型化的替代品。有些错没有 lint 规则兜底——那就写进标准，让下一轮的 code review 去执行。棘轮只往一个方向走：每次复盘，标准收紧一格。

■ 棘轮规则 Ratchet：复盘发现的机械错误变成确定性检查，判断问题变成编码标准；标准每次只收紧、不放松。

1 小时 4 分 16 秒，注释审计。约 2,000 行注释：约 940 行可删，约 1,000 行是解释性的，7 行已经过期；按处理方式分，是 22 处删除、18 处变通、3 条 ADR。Matt 在这里借用了 Lauren Tan 的说法：注释有时是遮羞布，有时是安全阀——遮羞布是拿注释盖住烂代码，安全阀是拿注释给后来人留一条“别动这里”的活路。审计要分的正是这两者。两组数字口径不同，见脚注。

1 小时 5 分 58 秒，试用做好的功能：打开 CVM，点开“Building CVM Thumbnail View”，缩略图编辑器里，人脸已框进画面，左侧存着两张已保存的缩略图，右上角是 Capture Face。测试文字写的是“Foobar tesawdawd”——糙，但够用。1 小时 8 分 2 秒，下一步：QA 走一遍，小问题走 oneshot，不必再拷问。

整期视频真正的顺序是反直觉的：最长的不是写代码，是写代码之前的事——拷问、术语表、ADR、场景测试、原型。21,000 行代码只花了一个离线小时；让 21,000 行代码不跑偏的对齐，花了前面一个小时。人的价值也在两头：开头把“为什么”讲清楚，结尾把每一行看一遍。中间交给 agent 的，是一个已经对齐过的世界。

代码看不见的上下文

What Your Coding Agent Can’t See in the Code

Speaker: Tom Moor, Linear

Event: AIE Code Summit, New York

Length: 21 分 13 秒

Source: youtu.be/Xw9utONfhIY

Technical Monograph · 精读报告 发布 2026 年 11 月 9 日 生成 2026 年 11 月 17 日

Linear 的 Tom Moor 说，编码 Agent 今天能读代码，却看不见代码背后的东西：意图、此前的决定与权衡、产品该有的样子、正在进行的相关工作、谁是决策者，以及潜藏的风险。三年前价值 100 美元的智能如今只要 5 美分，任务时限呈指数级拉长，Agent 一跑就是几小时、几天，上下文随之从内环移向外环——人不再逐个手动派活，系统必须替人管理这团混乱。真正的瓶颈不是写代码，而是维持产品的一致性：成千上万个局部正确的改动会拼出一件不连贯的产品。本报告按演讲顺序还原 Linear 的做法：入口处，分流 Agent 从 Zendesk、Slack、Teams、Gong 等渠道收齐想法与故障，标注、分组、去重、指派并调查，在工单上留下一份填满的上下文；实施时，小故障自动修复，验证技能与 CI 失败回流是成败关键；评审时，另一支评审 Agent 从原始工单与产品历史出发，查既往决定、回滚、事故、重叠改动与完整会话，把问题从“代码对不对”改成“改动对不对”；最后，每日蒸馏循环把评审意见提炼成教训，写回 AGENTS.md，让人的判断在下一轮复用。评审实例里，评审 Agent 抓住了一处 Codex 没发现的事故风险——长时间持有数据库事务，也翻出了一年前因“太拥挤”而砍掉的界面元素。收束时演讲者说，代码越便宜，人的判断越值钱。

Key Takeaways

  1. 代码不是瓶颈，一致性才是。写代码与实现都不再是瓶颈；真正的失败模式是成千上万个局部正确的改动拼出一件不连贯的产品，伟大来自一致、克制、权衡与相互加强的小决定。
  2. 上下文正在从内环移向外环。Agent 一跑几小时、几天，智能便宜到几美分，人不可能逐个手动派活；系统必须替人管理混乱与上下文。
  3. 入口决定成败，分流 Agent 先把上下文填满。想法与故障从各渠道进来，分流 Agent 标注、分组、去重、指派并调查，在工单上留下意图、客户、日志与相关决定。
  4. 评审要问“改动对不对”，不只问“代码对不对”。评审 Agent 从原始工单与产品历史出发，查既往决定、回滚、事故与重叠改动，连 Codex 没发现的事故风险也能抓住。
  5. 判断会越来越值钱，蒸馏让它复利。每日循环把评审意见提炼成教训写回 AGENTS.md，人的纠正变成下一轮的上下文；代码越便宜，判断越值钱。

1. 开场：从问题跟踪器到 Agent 时代

演讲者先介绍自己与 Linear：公司 2019 年创立，源于对当时问题跟踪器的不满——慢、难用、漏洞多。创始人自私地想用好工具：最好的工匠总是投资自己能负担的最高质量的工具，而当时的工程师恰恰缺这样的工具。

时间线说明变化有多快：2021 年 GitHub Copilot 的 Tab 补全；2022 年 ChatGPT 的对话式调试；2024 年第一批编码 Agent，早期、粗糙，只有走在最前面的人在用；2025 年 Claude Code 成熟；2026 年软件工厂，编排成为前沿。公司成立才五年多，软件工程已经被彻底重造了一遍。

联合创始人几周前刚讲过不该叫它“工厂”，演讲者不纠缠这个词；重要的是变化本身：从本地手把手指挥一个 Agent，走向编排更多 Agent、让它们在云端自动运行——这改变了上下文的用法与需求。

2. 速度曲线：智能越来越便宜，任务越跑越久

先看速度。Twitter 上有唱反调的人说免费午餐结束了，补贴一停就涨价；演讲者完全不信：成本还会继续降。幻灯片上的曲线是例证：三年前 100 美元才能买到的智能，如今 5 美分；中间两年分别是 7.7 美元与 0.6 美元。

“The cost is going to keep dropping.”成本还会继续降。

往未来外推，结果很有意思：几年后，超高速会成为常态，打个响指，一整个功能量的代码就会出现。

任务时限同样呈指数级增长。METR 的实测曲线叠加 4–7 个月翻倍的预测，从 2019 年的几分钟量级一路爬升，到 2028 年逼近 4000 分钟。

演讲者自嘲：Pitch 是好软件，可惜画不出指数轴——但这样看起来更震撼。

Agent 越跑越久：2024 年还在紧循环里盯着，如今能跑几小时、几天，有人让它周末接着跑还成功了；有多少代码真正上线不得而知，但趋势只会继续。

■ 任务时限（Task Horizon）：Agent 能独立完成的任务时长；METR 以人类专家完成同一任务所需的时间（分钟）度量，实测曲线呈指数增长。

■ 内环 / 外环（Inner Loop / Outer Loop）：内环是人与 Agent 一对一的紧循环；外环是任务派发、运行与治理的系统层，上下文正从前者移向后者。

3. 真正的瓶颈：产品一致性

速度引出真正的问题：代码会越来越多、越来越便宜，软件工厂会像流水线一样出功能；但演讲者说，写代码与实现如今都不是瓶颈。失败模式不是造不出来，而是维持不住一致性——产品作为一个整体是否讲得通。

“Code is not the bottleneck now. Implementation is not the bottleneck now.”代码不是瓶颈了，实现也不是瓶颈了。

伟大的产品是什么？一致、克制、权衡，以及大量相互加强的小决定。演讲者放了一张 Codex 生成的设置页——开关密密麻麻，失控的样子一目了然：再加一个设置，能出什么事？

“What makes a product great is consistency, restraint, trade-offs, and lots of tiny decisions that reinforce one another.”伟大的产品来自一致、克制、权衡，以及大量相互加强的小决定。

今天的编码 Agent 会读代码，这很有价值；但它仍然看不见代码背后的东西：意图——要解决什么问题、为什么重要、对最终用户意味着什么；此前做过哪些决定、付出了什么权衡；东西该长什么样、用起来该什么感觉。

还有组织里的其他工作、谁是决策者、谁最终负责，以及风险——比如两周前同一块代码刚发生过回滚，代码本身不会主动告诉你。

办法是把这份上下文从最初的想法一路带下去，经过规划、实施与评审。演讲者接下来讲的就是 Linear 的这套系统：大部分已经上线、别人也能用；这不是 Linear 的广告，原则放进任何系统都成立。

4. 四段流水线：让上下文贯穿始终

流水线分四段：接收（Intake）→ 实施（Implement）→ 评审（Review）→ 蒸馏（Distill），每一段都给下一段留下上下文。

演讲者强调，整件事是 Agent 套 Agent——每深入一个问题，答案都是更多的 AI，他对此相当看好。

“It’s agents all the way down.”Agent 套着 Agent，一路到底。

“The principles apply broadly, and you can build this into any system that you’re using.”原则放进任何系统都成立。

5. 入口：分流 Agent

第一段是自动接收。想法从 Zendesk、Slack、Teams、Gong、Twitter、内部产品团队、CEO 那里涌进来，还有 Datadog 的告警；演讲者说，幻灯片上只列了五分之一。分流 Agent 接手：打标签、指派、按主题归组、关闭重复项、路由给正确的人与团队，信息不足时还会追问以澄清问题。

■ 分流（Triage）：把涌入的想法与故障分类、去重、指派的过程；Linear 用一支分流 Agent 自动完成。

分流 Agent 还会调查，调查结果留在工单上，成为下一位人类或 Agent 的基础上下文：一份简单报障进来时只有一句话，出去时已经填满——谁提的、客户价值几何（高价值客户、一个月内第三次提同一需求）、Slack 里的堆栈、Datadog 日志、通过内部 MCP 关联的账号，以及此前碰过同一区域的相关工单与决定。

■ 分流 Agent（Triage Agent）：自动接收并调查的 Agent，负责标注、分组、去重、指派与调查，在工单上沉淀上下文。

5.1 两个例子：调查做到什么程度

第一个例子是视频字幕总被自动打开。分流 Agent 不只找到了设置，还复现了故障：字幕轨道被标为 default，浏览器便自动启用；播放器又把这次启用当作偏好变更，存回了用户设置。正是这份细节，让后续自动修复成为可能。

第二个例子里，分流 Agent 先查了代码库：找到已上线过的类似工作，确认不是回归；又找出关联的全部客户，判断出高价值；还定位了代码库里最可能的下手点。演讲者说，这样的起点能大幅提高编码 Agent 的成功率。

6. 实施：已经解决的一环

有了基础上下文，下一步是实施：分流 Agent 判断问题够小就自动修复；也可以手动触发，本地经 MCP 或远程在云端跑。演讲者坦言，如果以为演讲重点在这里，恐怕要失望了——在他看来，实施今天基本已经是解决的问题。

■ MCP（Model Context Protocol）：模型调用外部工具与内部系统的开放协议；分流与实施 Agent 经它访问账号与组织上下文。

真正关键的是两样：验证的能力，以及 CI 失败能回流进 Agent。有了基础上下文、能验证、能看到失败，团队的成功率大幅提升。

验证技能可以现成取用：xAI 的 Lauren 在 Twitter 上分享了一套技能，可以为编码 Agent 生成验证技能，演讲者说差别巨大。

■ 验证技能（Verification Skill）：让 Agent 在动手前定义如何验证结果的技能；演讲者推荐 xAI 的 Lauren 分享的一套生成方法。

7. 评审：从“代码对不对”到“改动对不对”

上下文最被忽视、也最有意思的地方是评审。今天的评审 Agent——PR 上跑的 Codex、CodeRabbit 之类——上下文基本只来自代码库，关注点是逻辑正确性；它们确实能抓到很多 bug，这很好。

Linear 内部给了评审 Agent 更多上下文：先派另一支评审 Agent，从原始工单与基础上下文出发，再去查产品历史——既往决定、回滚、回归与同一区域的事故；有了代码与 PR 意图，还能进一步丰富上下文。

还要收拢相关工单（这可能是几周后的事，也可能是几分钟后）、发现重叠与冲突的改动、调出完整的 Agent 会话（一次成型，还是来回多轮、中间做了关键决定），最后是归属：谁该拍产品层面的板、哪些评审覆盖可能缺失——产品负责人、CEO、产品主管都可能需要发声。

“We’re now thinking less about is this code correct and more about is this the right change for the product?”我们想的越来越不是“这段代码对不对”，而是“这个改动对产品对不对？”

■ 评审 Agent（Review Agent）：从原始工单与产品历史出发评审改动的 Agent，关注点是改动是否合乎产品，而不只是代码是否正确。

7.1 三个评审实例

第一个例子里，评审 Agent 翻出了六七个月前的几处相关改动，标出事故风险：附件下载缓慢时会让数据库事务长时间挂起，可能重现邮件接收里的同类故障，堵住工单创建。标准的评审 Agent 也许能发现，但多出来的上下文确实帮了忙——Codex 没发现它。

第二个例子更直观：一年前团队因为界面太拥挤砍掉了一组图标；一份 PR 想把它加回来，而这组图标此前已被多次否决。评审 Agent 把一年前的决定翻了出来，评审意见随即直接回流给编码 Agent，变成新的上下文。

第三个例子关于团队与工作区标签的层级：截图里工作区标签显示在团队标签下方，一般的代码评审工具未必会注意；但此前有过一次回滚与相关工单，评审 Agent 把它们翻了出来。演讲者说，代码里没有任何地方定义这条顺序——标签列得到处都是，唯独这条规则不在代码里。

“There’s no place in the code that defines that.”代码里没有任何地方定义这一点。

7.2 给人的评审界面

Linear 还为此建了一个界面，引导人类评审者走完整个改动集，把需要判断的地方与相关决定摆在面前；任何评审产品都能做这件事，但他们偏爱亲手打磨工具，于是自己建了这个界面。

8. 蒸馏与收束：判断越来越值钱

最后一环是蒸馏。评审意见一路存在工单与 PR 里，改动合入代码库，上下文不断积累——这在组织层面是指数级放大的。

一套每日运行一次的自动化（量大可以更勤）会扫过当天合入的全部代码，找出可执行的教训：PR 里出现过这类意见、改动已做或已回滚的地方，提炼出学习点，注回代码库——AGENTS.md 或相关文档，让教训持续复利。

8.1 每日蒸馏循环

提示词得靠实验调；教训也不能无限堆积，否则 AGENTS.md 会变成上百万行的上下文。现场有人问这是否总由提示词处理——演讲者答，这是 Linear 的自动化，但任何带触发器的自动化产品都能做。

■ 蒸馏（Distill）：把评审与合入过程中产生的意见提炼成可复用的教训，注回代码库的环节。

■ AGENTS.md：仓库根目录的 Agent 指导文档；蒸馏循环把提炼的教训写回其中，供下一轮 Agent 使用。

收束时，演讲者算了这笔账：入口处理解意图，少做解决错问题的改动；实施时产品历史帮人站在既往决定上；评审时相关工作帮人发现与产品、与进行中工作的冲突，判断改动是否合乎产品整体；结果是更少可避免的错误、更少返工、更快迭代。

而蒸馏循环让整件事闭环：过程中产生的人类判断，成为下一轮的上下文。演讲者的最后一句是：代码越便宜，判断越值钱。

“Our judgment matters more as code gets cheaper.”代码越便宜，我们的判断越值钱。

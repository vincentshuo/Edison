教 Agent 建人人能用的产品

Teach Your AI Agent to Build Products Everyone Can Use

Speaker: Jemima Abu, CAIS

Event: AIE Code Summit, New York

Length: 14 分 38 秒

Source: youtu.be/YV1x6gCdgQA

闭上眼睛，解锁手机，打开备忘录，写下 hello world——这是 Jemima Abu 开场时给全场的唯一一道题。多数人做不到：没有视觉反馈，不知道自己在屏幕上按了什么。靠肌肉记忆蒙对的人，换一部第一次用的手机也一样会失败。而对一部分人来说，闭眼不是一个练习，是永久的状态。这就是无障碍：无论有无残障，人人都能用的产品。她给出的数据是，头部一百万网站里约 96% 存在无障碍问题。她又做了一个实验：让 Agent 按同一份 Figma 设计实现同一页面，一次不给任何无障碍指导，一次给她写好的无障碍技能——后者耗时从 15.6 分钟降到 5.2 分钟，成本从约 14.20 美元降到约 5.97 美元，降幅 58%，token 用量少了 69%。她随即提醒，这只是一次非受控实验，不能当作实证结论；但道理成立：把做法写成具体的技能，Agent 跑得更快，也更省钱。演讲随后讲清代价：人类对无障碍的漠视会被 AI 学去，循环放大，最终把全球约 16% 的残障人口挡在门外；流行的做法未必是最好的做法；无障碍事后贴不上去；顾客会流向能用的产品；美国还有《残疾人法案》与成堆的诉讼。做法有四步：先定标准、审计存量代码、用设计系统、把规则写进 Agent 的每次运行。她最后给出了一份五条规则的轻量版技能，并提醒：做到这些也不等于 100% 无障碍，但能帮上忙。

Key Takeaways

  1. 无障碍不是加分项，是产品能不能用的问题。闭眼解锁手机都做不到的人，面对的是永久的闭眼状态；头部网站约 96% 有无障碍问题，等于把一部分人挡在门外。
  2. 给 Agent 一份具体的技能，比让它自由发挥更快更便宜。同一份设计、同一模型，有无障碍技能的一次耗时从 15.6 分钟降到 5.2 分钟，成本降 58%。
  3. 人类的偏见会变成 AI 的偏见，再变回人类的偏见。开发者发布不可访问的代码，AI 拿它训练并当成正常，再帮开发者生成更多不可访问的代码。
  4. 无障碍要从第一行代码烤进去，事后贴标签没用。成品网站上补一堆 aria 标签，就像在白面松饼上撒一把蓝莓，算不上蓝莓松饼。
  5. 把规则写进 Agent 的每次运行。先定标准、审计存量代码、用设计系统复用修复、强制执行——缺了最后一步，截止日期一到就会被忘掉。

1. 开场：闭眼解锁手机

演讲开场没有标题页，只有一道题：拿出手机，闭上眼睛，解锁，打开备忘录，写下 hello world。她甚至退了一步——只输锁屏密码也行，给了 30 秒。

多数人做不到。没有视觉反馈，你不知道自己按了什么。有人靠肌肉记忆蒙对：记得上滑的位置、记得键盘的布局。但她追问：如果这是你第一次用这部手机，不知道任何一个键在哪里，还能做到吗？答案同样是否定的。

“Accessibility is the practice of building products that people can use regardless of disability.”无障碍，就是建人人都能用的产品，无论有无残障。

■ 无障碍（Accessibility）：产品与服务可供残障人士使用的程度；演讲者的定义是“无论有无残障，人人都能用”。

对一部分人来说，闭眼不是练习，是永久的状态。视力、运动、认知、听力——任何一种残障，都可能让人用不了一件产品。而一件一部分人用不了的产品，用她的话说，就是一件没用的产品。接下来的整场演讲，都在回答一个问题：怎么建出有用的产品。

2. 无障碍是什么：96% 的网站不及格

她先给出定义，再给出数字：头部一百万网站里，约 96% 存在无障碍问题。对残障用户来说，这意味着这些网站无法完整使用。

她常年在外讲无障碍，问开发者为什么不多花时间，听到的回答总是同一套：太花时间、经理不会批、客户不在乎、公司不把它当优先级。

她的假设正好相反：建不可访问的产品，反而要花更多时间、更多钱。她决定做个小实验来验证这个假设——按她自己的话说，身为 STEM 领域的女性，她得拿出实验来说话。

实验的思路很简单：让 Agent 实现同一份设计，做两次，一次不给任何无障碍指导，一次给她专门写好的无障碍技能，然后比较耗时、轮次、token 用量与成本。

3. 一次实验：有技能的 Agent 更快更便宜

实验设计控制得很干净：同一份 Figma 设计、同一提示词、同一模型。第一次不给任何无障碍指导，让 Agent 自由发挥；第二次给她专门写好的无障碍技能。

幻灯片上的数据是：耗时从 15.6 分钟降到 5.2 分钟，降幅 67%；对话轮次从 84 轮降到 32 轮，降幅 62%；token 总用量从约 460 万降到约 143 万，降幅 69%；粗略成本从约 14.20 美元降到约 5.97 美元，降幅 58%。

她随即给自己的结论踩了一脚刹车：这只是一次实验，不在受控环境里，不能当作实证数据，更不能据此断言“有技能就一定更快更便宜”。但道理成立：把做法写成具体的技能，告诉 Agent“这件事就按这个办法做”，Agent 跑得更快，长期也更省钱。

“When you provide skills to agents that tell them, ‘Do this thing this specific way,’ it’s going to be faster and it’s going to save you a lot more money in the long run.”把做法写成具体的技能，告诉 Agent“这件事就按这个办法做”，它会跑得更快，长期也更省钱。

这时她才正式自我介绍：Jemima Abu，CAIS 的产品工程师，Google 开发者专家、微软最有价值专家、无障碍核心能力认证专业人士。她自称是“中年孩子与资优儿童的危险组合”，总在寻求认可、渴望关注——所以站在这里讲这个话题。

4. Agent 是个三岁小孩：给它一张地图

今天最流行的模型不过三岁：ChatGPT、Claude、Copilot 都很聪明，但也只是个孩子。

她喜欢的日本节目《Old Enough》讲的是小孩第一次独自出门办事：一个两岁女孩被派去超市，父母总会给非常具体的指引——和妈妈一起走过很多次的路、一张手绘小地图、“别进树林，别迷路”，还有一张购物清单。

提示 Agent 是同一回事：别让它走到你不希望它去的地方。建产品时，别让它迷失在生成一堆 div 里；要让它跟着你给的提示走，成品正好是你想要的样子。

幻灯片把这张地图画了出来：从代码库出发，沿着“按无障碍提示走”的路抵达网页，路边的树全是 div 陷阱；下面的无障碍清单只有五行：语义化 HTML、键盘可用、可见焦点、标注输入、不用纯颜色提示。

■ 语义化 HTML（Semantic HTML）：按含义选用 HTML 元素（如用 button 表示按钮、用 details 表示折叠区），浏览器与辅助技术原生理解其行为。

接下来她算了一笔账：让 Agent 生成人用不了的代码，我们到底失去了什么。

5. 不可访问代码的代价

第一笔账：人类的偏见变成 AI 的偏见。96% 的网站有无障碍问题，说明开发者整体上不太在乎无障碍。

“能用就行”的心态是这样的：自己笔记本上跑通了就发货，不会想到屏幕阅读器用户、不用鼠标只用键盘的人。这些事没人教过我们要想到。而 AI 正在学我们：它看人类写的代码，认定“好代码就长这样”，再生成更多不可访问的代码；人类又产出更多这样的代码。循环一旦闭合，等 AI 写大多数代码的那天，全球约 16% 的残障人口就被挡在门外。

■ 屏幕阅读器（Screen Reader）：把屏幕内容读给盲人或低视力用户听的辅助技术；代码结构不清，它就读不出页面的含义。

5.1 流行的做法不一定是最好的做法

第二笔账：AI 喜欢写很多代码。五行能写完的东西，它宁愿写五百行——用的 token 越多，赚的钱越多。

以手风琴组件为例：用 JavaScript 定制实现是一种写法；用 HTML 的 details 元素是同一种东西，代码少得多，默认可访问，还经过浏览器厂商的测试。

但 details 不如定制实现流行，所以 AI 会写定制实现。开发者的工作就是告诉它：别追流行，追最好的。

“Don’t go for what’s popular, go for what is best.”别追流行，追最好的。

这也是技能里要盯住的一点：流行度不是质量标准。Agent 默认会选最常见的写法，开发者得在技能里把“最好的写法”写死。

5.2 无障碍烤不进去，只能从头烤

第三笔账其实是时机：等网站建完了再补无障碍，要难得多。

她举了蓝莓松饼的例子：左边是真正的蓝莓松饼，右边是有人递给你一个白面松饼、上面撒了一把蓝莓，还说“给，蓝莓松饼”。你只会说：拿走这垃圾，这算什么？

建好的网站上补一堆 aria 标签、就宣称自己无障碍，就是同一回事。无障碍和蓝莓一样，得从一开始烤进去。

“You cannot shove a bunch of aria labels into a product and call it an accessible website.”不能往成品里塞一堆 aria 标签，就宣称它是个无障碍网站。

■ ARIA：无障碍富互联网应用属性，给 HTML 元素补充角色、状态与标签信息；是补丁，不是替代语义化 HTML 的办法。

5.3 顾客会用脚投票

第四笔账是顾客：她在会上听到的故事——一位残障用户用的银行 A 应用不可访问，于是换到了银行 B。不是银行 A 的功能更差，而是用户根本用不了它的产品。

于是就有了那句她总听到的反驳：“可我们的用户都不用辅助技术。”她的回答是：你的用户不用辅助技术，是因为他们用不了你的产品——到站就走，所以你根本看不到他们。

“Oh, nobody comes into our store. Yeah, why do you think that is? They can’t get in the building.”“哦，没人进我们的店。”是啊，你想过为什么吗？他们根本进不了这栋楼。

建得可访问，人才进得来、用得上；建得不可访问，等于一家没有门的店。

5.4 还有法律账单

最后一笔账是法律：美国《残疾人法案》要求任何面向公众的网站都必须可访问；而美国人爱打官司，与不可访问网站有关的诉讼成堆。

■ ADA（Americans with Disabilities Act）：美国《残疾人法案》，要求面向公众的网站可访问；违反者面临诉讼风险。

她开玩笑说，摆在面前的选择是：把网站建得可访问，或者用微软 Teams 里那张好玩的贴纸——自己掂量。

6. 让 Agent 写出可访问代码的四步

现状是，我们已经不太自己写代码了，大部分是 Agent 在写。那么怎么保证它写出的代码是可访问的？她给出四步。

6.1 先定标准

第一步，定义无障碍需求。每个公司、每个领域的要求不同：Web 应用和移动应用的标准不一样。无论你是开发者、产品经理，还是在 vibe coding，都得先知道这款应用的无障碍标准是什么，再带着它去提示 Agent。

6.2 先审计存量代码

第二步，审计现有代码库。她打了个比方：新室友搬进来，看见水槽里堆满盘子，这辈子都不会主动洗碗——“你搬进来时盘子就在那儿，我凭什么现在开始洗？”

把 Agent 引进一个代码写得差的代码库也一样：它会把现有的写法当成标准，反问“你都没这么写，我凭什么这么写？”所以先审计、修掉存量里的无障碍问题；好在现在可以让 Agent 自己来做这份审计，再动手修。

6.3 用设计系统

第三步，落地设计系统或某种可复用的组件库：一处修好，处处都好。她举的例子是，修一个组件，就能同时修好 150 个页面。

■ 设计系统（Design System）：可复用的组件与规范库；一处修复，随处生效。

6.4 写进每次运行的强制规则

第四步，让 Agent 每次运行都强制遵守这些规则。离截止日期只剩三小时、你上周就跟经理说做完了、打开文档才发现权限还没加——这种时候最容易忘掉无障碍；写进 Agent 的默认流程里，它才更可能真的落地。

7. 两份现成的技能

她最后给出了一份轻量版无障碍技能，是她自己在用的版本的简化版。写在 AGENTS.md 里，开头就写明“强制执行”：生成任何 UI 组件前，先执行这五条规则——尽可能用语义化 HTML；只有语义化 HTML 表达不了行为时才用 ARIA；每个交互元素必须只用键盘就能操作，且有可见焦点；元素必须正确标注、能被屏幕阅读器读出；返回代码前，对照以上全部检查一遍。

■ 技能（Skill）：写给 Agent 的操作手册，通常是一份 Markdown 文件，规定它做某件事的具体做法；放在 AGENTS.md 里即成为每次运行的默认指令。

其中第二条值得单独说：ARIA 是补丁，不是默认值。语义化 HTML 能表达的，就别用 ARIA 绕路；只用键盘操作加可见焦点，则是所有交互元素的底线。

■ 键盘可操作性（Keyboard Accessibility）：只用键盘就能完成全部交互，且焦点始终可见；不能用鼠标的用户就靠它使用产品。

7.1 现代 Web 指导技能

另一份她喜欢的技能是现代 Web 指导技能，出自 Chrome——或者说 Google，她自己也分不清这两家为什么名字不一样。它告诉 Agent 用最新的功能：要做手风琴就用 details，要做弹窗就用 popover。

她提醒，这些提示大多面向 Web，因为那是她的主场；换个领域，照着自己的需求改写就行。

“It does not mean that your website is going to be 100% accessible, but it does mean that it can help.”这不等于你的网站能做到 100% 无障碍，但它确实能帮上忙。

8. 收束：Web 属于所有人

演讲收在同一句话上：Web 属于所有人，所以人人都应该能用它。做到前面这些，不等于终点，但能让产品离这句话更近。

“Make sure you’re building accessibly so everybody can use it.”把产品建得人人能用，别等用户走了才发现门都没装。

8.1 问答：最讨厌的两件事

问答环节有人问她，在无障碍这件事上最受不了什么。她的回答是两个极端。

一端是完全不在乎：拿 div 当按钮、不给键盘处理函数，借口还是那句“我们的用户不用辅助技术”。

另一端是矫枉过正。她最讨厌的是无障碍覆盖层：网站角落里一个小人图标，点开就宣称万事大吉。

“They’re like the blueberry muffin analogy. You’re just adding blueberries to a plain muffin.”覆盖层就像蓝莓松饼的比喻：你只是在白面松饼上撒蓝莓。

■ 无障碍覆盖层（Accessibility Overlay）：叠加在网站上、宣称一键修复无障碍问题的第三方工具；演讲者认为它只是事后贴标签。

两件事其实是一件事：要么不把无障碍当回事，要么假装贴个东西就当回事。她的收尾仍是开场那句话的反面：把产品建得人人能用，别等用户走了才发现门都没装。

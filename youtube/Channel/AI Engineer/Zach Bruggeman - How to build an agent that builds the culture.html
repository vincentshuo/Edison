Ramp 的工程师 Zach Bruggeman 上台讲的不是 Inspect 的技术——沙箱五秒启动、内部上下文全接通、多人协作，这些都已经不是新鲜事。他要讲的是另一面：当一个智能体写出并交付了公司大约 75% 的代码，真正难的是让整个组织都学会信任它、用好它。Ramp 的答案藏在三条经验里：全公司只用一个 Inspect，消灭信息孤岛；会话默认公开，让学习发生在日常工作里；每一次改动都展示它是怎么来的，让信任有据可查。而最动人的证据，是一个二月下午的 Slack 帖子：一次公开的排障，让一个怀疑者变成了一起造东西的同事。

Key Takeaways

  1. 技术不再是门槛，文化才是。沙箱五秒启动、上下文全接通、多人协作都已实现，Inspect 也已成为市面上的产品；难的是组织怎么用好它。
  2. 消灭信息孤岛：全公司只用一个 Inspect。好的配置与工具一推送到全员；从不强制使用，因为一个足够好的默认就够了。
  3. 公开工作是最好的培训。会话默认全公司可见，学用法靠看同事怎么做，不靠集中授课；连 Inspect 团队自己也从用户的用法里学。
  4. 信任来自看得见的验证。每次改动都附带会话、工具记录、前后截图与验证录像，评审看到的不是四百行 diff，而是一份活的证据。
  5. 一起想得更大。独狼操作员不是终点；Review Buddy 证明，工具的边界由使用者决定，而不是由造工具的人决定。

1. 开场：Inspect，Ramp 的协作式编程智能体（约 0:00–2:06）

Zach Bruggeman 上台先报身份：Ramp 的工程师，Inspect 的创始工程师之一。这场演讲的题目本身就是一次演示——他请 Inspect 展示"Inspect 是如何重塑 Ramp 工程文化的"，Inspect 的回答是：光说不如做，最清楚的办法，是当场修一个真实的线上 Bug，一次会话完成。屏幕上就是那次会话：#help-expenses 频道本周上报最多的问题，审批人看不出为什么有些卡交易的"批准"按钮是灰的；Inspect 读了 useGetTransactionReviewActions.ts，九秒就开始干活。

Inspect 是 Ramp 的协作式编程智能体。大约一年前，Ramp 下注自研：每个会话都在远端运行、完全多人协作。可以在 Inspect 自己、Slack、Linear 或任何集成里与它一起工作。它早已不止写代码：内置设计原语、评审智能体与验证流程，从提示到交付，全在 Inspect 里完成。它还接通了全公司的集成——遥测、数据库与各种工具，数据与工具自动就位。

■ Inspect：Ramp 自研的协作式编程智能体，在远端沙箱里运行，会话默认全公司公开，可经 Inspect 界面、Slack、Linear 等入口使用，覆盖从提示到交付的完整流程。

数字是这场演讲的起点：如今 Ramp 大约 75% 的代码由 Inspect 写出并交付。这个数字是 Bruggeman 自己的说法；Modal 的博客说，短短几个月内，Inspect 发起的合并请求已占 Ramp 前后端仓库的一半以上；他在 Modal Runtime 大会上的另一次演讲里给出的增长曲线，也与约 75% 的说法一致。

■ 沙箱（Sandbox）：每次 Inspect 会话运行的隔离环境，内含完整的 Ramp 开发环境；据 Modal 的介绍，会话从文件系统快照启动，因此能在五秒内就绪。

年初公开分享 Inspect 时，新鲜的是技术：五秒内拉起沙箱、接通内部上下文、让智能体多人协作。现在这些概念已被广泛采用，Inspect 本人也成了市面上的产品，技术不再是门槛。难的是另一面：围绕 Inspect 建立一种文化。这场演讲不谈技术细节——想看技术深挖，可以去读 Ramp 的博客与 Pragmatic Engineer 几个月前做的深挖报道，也可以去关注 Dylan Garcia，他在社交媒体上持续分享 Inspect 的实战心得。

2. 第一课：造消灭信息孤岛的工具（约 2:06–4:20）

在 Ramp 工作，会让人凡事都用省时省钱的眼光看。理解系统与工具固然重要，但一家几百上千人的公司，如果每人都要花十五分钟做配置，乘下来就是几天时间，浪费在非常机械的工作上。更何况前沿的最佳实践变得飞快，配置成本不是一次性的。

而且进步不会均匀扩散：有人花了不确定的时间与精力维护自己的配置，有人没有，组织内部的结果就拉开了差距。个人层面这也许是优势，但要赢，就得让每个人都处在最佳状态。这是第一课：造消灭信息孤岛的工具。

■ 信息孤岛（Information Silos）：知识与配置只留在个人手里、不在组织内流动的状态；Bruggeman 认为，它是智能体时代组织效能的第一道裂缝。

幻灯片上的算术很直观：一千名工程师，每人十五分钟，合计 238 小时，约等于 31 个工作日。发现好用的模式或工具，就能立刻推给整个组织。想自己折腾配置也行，但 Inspect 永远是一个非常扎实的默认。Ramp 从不需要强制使用 Inspect——因为有一个好的默认，人们就没那么需要到处找自己的配置了。

更深一层的原因是：这个行业里，没有人能永远知道用智能体的绝对最佳方式，哪怕这就是你的全职工作，每个人都会错过东西、有偏见、有盲点。所以 Inspect 的设计是：全公司只有一个 Inspect。有人找到更好的用法、有了改进的想法，就能把它带给全公司；大多数改动对其他人是不可见的——你照常用 Inspect，改进自然就来了。

3. 公开工作：不用上培训课的学习（约 4:20–5:22）

Ramp 几乎不用开正式的"怎么有效使用 AI"培训课。因为每个 Inspect 会话默认在公司内公开，公开工作比私下工作更容易。你默认在公开场合工作，在已经在的频道里看同事怎么用，你就学会了；同事也能从你身上学。甚至可以直接请 Inspect 复盘某位同事最近的会话，告诉你他怎么组织提示、怎么拆解难题。

“It’s easier to work in public than in private.”公开工作比私下工作更容易。

这不只帮了 Ramp 的建造者，也帮了 Inspect 团队自己。他们经常看到人们用 Inspect 做出当初没想到的事，这反过来决定了该往哪儿建：是给常见模式加原生原语，还是补上缺失的工具与数据。于是形成一个自我维持的循环：看着人们已经用 Inspect 做成的事，去建让 Inspect 更成功的东西。

■ 原生原语（Native Primitives）：Inspect 内置的、针对常见模式的现成能力；用户反复做的事，会被沉淀成原语，而不是每次都从提示词重新发明。

4. 第二课：用看得见的验证建立信任（约 5:22–7:05）

第二课是信任。采用智能体编程，对每个工程师来说都是一场大规模的信任建设：模型写高质量代码的能力越来越强，但很大一部分是学会信任智能体造出来的东西。而信任工具，很大程度上是向别人学来的——这也是大多数人来听演讲的原因：听值得尊敬的人讲他们学到的东西。但如果知识的来源只限于那些乐于公开演讲的少数人，画面仍然不完整。

这正是公开会话的另一层意义：知识共享的民主化。不必围着少数领袖转，而是建一个系统，让每个人的知识自然流动。幻灯片先是一句"我们向台上的人学习"，接着反问："如果向所有人学习呢？"——台下密密麻麻的圆点，每一个都代表一位同事的经验。

Inspect 的做法是让每一次改动都展示它是怎么来的。有人用 Inspect 交付了东西，大家直接在那份工作上就能看到：完整的对话、用过哪些工具、前后截图，甚至一段验证智能体在浏览器里点开应用、证明改动成立的录像。评审一份拉取请求时，看到的不再是凭空丢过来的四百行 diff 与一句"祝好运"，而是这份改动是怎么来的、为什么可以信任它。

■ 验证智能体（Verification Agent）：Inspect 内置的评审环节之一，在真实浏览器里点开应用、操作界面，用前后截图或录像证明改动成立，而不是只看代码。

这也让把不常一起工作的人拉进来变得容易：证据摆在那里，不需要先建立私人信任再谈合作。信任不再靠口头保证，而是靠一份活的、可复核的记录。

“Every time someone ships something with Inspect, people can see it right there on the work you’ve done.”每次有人用 Inspect 交付东西，大家都能直接在那份工作上看到它是怎么来的。

5. 一次公开排障：连机器人都不信机器人（约 7:05–10:09）

信任的考验发生在一个二月下午：工程师 Andrew 报告 Inspect 出了一个 Bug。Bruggeman 顺手就请 Inspect 自己去查。巧的是，Inspect 接 DataDog 已经有一阵子，但给 Inspect 自身加埋点才刚刚做完——Inspect 主要由前端产品工程师建造，追踪对他们来说是个陌生的概念。正好拿这次来检验。

Inspect 的结论是：埋点本身就是故障的源头——正是用来调试这个错误的埋点，正在造成这个错误。Bruggeman 和 Dylan 都不信这台机器人的解释；Andrew 干脆说"算了，我用 Claude Code"。没有人信任任何人：Dylan 和 Bruggeman 不信机器人的解释，Andrew 不信他们能造出好用的东西。

■ 可观测性（Observability）：通过埋点、追踪与日志了解系统内部状态的能力；Inspect 团队此前主要做前端产品，追踪对他们来说是个新课题。

但因为这件事发生在公开场合，大家继续追问。Dylan 请 Inspect 去读遥测库的代码，看看是不是以前就有这个问题，只是以前看不见。这一次 Inspect 的回答具体多了：OTEL 库调用了 fetch，却从不读取、也不取消响应体。这是当时 Cloudflare 平台的一个限制——偏偏出在一个专门为 Cloudflare Workers 写的库里。Bruggeman 的评价是：这个库毕竟写于 AGI 之前，这种事难免。

■ OpenTelemetry（OTEL）：开源的可观测性框架与协议，提供追踪、指标与日志的埋点标准；本案中出问题的正是它的一个 Cloudflare Workers 遥测库。

于是请 Inspect 打补丁：让导出器显式取消响应体。部署时大家还在帖子里抱怨了几句，但部署之后，错误再也没有出现。Dylan 在帖子里写道：自从发了这个补丁，就再也没收到过停滞的 HTTP 响应；Bruggeman 回了一句："God bless observability"——感谢可观测性。

修好一个 Bug 本身没什么特别；特别的是帖子里同时发生的另一件事。没有 Inspect 之前，这样的报告会被确认、建一张票，然后有人默默去排障；Andrew 之后可能收到一条"修好了"的消息，但有趣的工作全在私下完成。现在一切都在公开场合进行，Andrew 自然而然地参与进来，贡献自己的想法与经验；同一个帖子里，还冒出了 Inspect 可以赋能其他工作的新点子——没有人催、没有人施压，只是"这些人在做一件很酷的事，我们可以一起做"。

一个小时之内：一个带着坏体验的怀疑用户，变成了一个想一起造东西的同事；Inspect 也更稳定了。幻灯片把前后对照画得很清楚：以前是"报告 Bug—建一张票—私下排障—'修好了'"；现在是"报告 Bug—答案错了—顶回去—找到根因—发版修复"。

“God bless observability.”感谢可观测性。

6. 第三课：一起想得更大（约 10:09–11:39）

有了第一天就能用的最好配置、没有信息孤岛，又有了把创新聚在一起的信任系统，接下来是什么？最后一课：一起想得更大。这一年让 Bruggeman 难受的一件事，是人们对"独狼操作员"的崇拜：有了 AI，每个人确实能独自做得更多，但这不能是终点。

如果不向外建设、不与人协作、不持续分享进展与学到的东西，这一切会向内塌缩：我们只把自己当目标受众，不再从别人的视角与经验中成长。他并不悲观——大家聚在这里，本身就是连接有价值的证明；更重要的是，我们可以把工具塑造成让连接更强壮的样子。

“If we don’t build outwards, collaborate with other people, and continue to share the progress and learnings we make, I think this is all going to collapse in on itself.”如果我们不向外建设、不与人协作、不持续分享进展与学到的东西，我觉得这一切都会向内塌缩。

Andrew 的故事在 Ramp 内部一次次上演，这是 Inspect 最让 Bruggeman 着迷的地方。Inspect 当然是个编程智能体，但它已经成了文化的一部分：Ramp 的每个人都认识它的脸，节假日给它换装，慢慢往里面加彩蛋，随着 Ramp 自身的演变而演变。不是每次迭代都完美——任何一位 Ramp 工程师都能告诉你——但每一次迭代都是一起完成的。

7. Review Buddy：没有许可的创新（约 11:39–12:52）

回到今年早些时候，Inspect 远没有今天这么多功能。一个好例子是它的代码评审智能体。此前 Ramp 用过各种现成的代码评审产品，换来换去找合适的。后来，两位工程师 Daniel 与 Pranjal 意识到：既然 Inspect 已有自动化触发器——拉取请求一打开就能触发，干嘛不自己造一个？

■ 自动化触发器（Automation Triggers）：Inspect 的事件驱动机制，可由 Slack 消息、Linear 工单、拉取请求打开等多种来源触发会话；Review Buddy 正是挂在"拉取请求打开"这个触发器上的。

他们没问任何人要不要造，就动手了；用 Inspect 加快速度，很快造出了一个全 Ramp 都喜欢的智能体：Review Buddy。就像 Inspect 自己当初也是一个副业项目一样，他们只是挑战自己造一个更好的东西。

■ Review Buddy：Ramp 工程师 Daniel 与 Pranjal 用 Inspect 造的代码评审智能体，拉取请求一打开即自动评审；它是 Inspect 从"编程智能体"长成平台的标志性例子。

这件事逼着 Inspect 团队重新思考 Inspect：那时他们还满足于 Inspect"只是一个编程智能体"。一旦看到别人把它推到新的地方，他们才开始想，Inspect 怎样才能形成完整的闭环：提示、设计、编码、评审、验证、交付。Bruggeman 说，如果不是这种自然发生的推动，Inspect 团队要花长得多的时间才能走到这一步。这就是"一起想得更大"的意思。

8. 收尾：你们的团队下一步造什么（约 12:52–14:28）

模型还在不断变强，现在正是逼自己、也逼身边的人想得更大的时候。Bruggeman 请听众在接下来的一周里，问问一起工作的每个人："我们一直在等着做、却还没做的事，到底是什么？"找到了，就一起去造。

“What have we been waiting to do that we haven’t done yet?”我们一直在等着做、却还没做的事，到底是什么？

现在真的没有借口不去试一试了：人人都能用上同样的模型；但总得从某个地方开始。他相信，解锁胜利的潜力，不只是为自己，也是为身边的人。Inspect 本人就是这样诞生的：不只是他和 Jason 想造的东西，更是为一支他们真正热爱、真正尊敬的团队造的——让他们的工作稍微愉快一点。

“There’s really not an excuse to not just try anymore.”现在真的没有借口不去试一试了。

如果想用一个体现了这些教训的编程智能体，Inspect 现在已经对 Ramp 之外开放：去 inspect.com/aie，团队会优先安排你和你的团队上等待名单；名单消化得很快，不久就会有消息。

讨论问题

1. 全公司只用一个智能体，与每人自选配置相比，各自的代价是什么？你的团队现在更接近哪一端？

2. "公开工作比私下工作更容易"——在你的团队里，哪些工作现在还只能私下做？公开它们需要什么条件？

3. 一次改动附带会话、工具记录与验证录像，会改变你评审代码的方式吗？评审时你最想看到哪一种证据？

4. Bruggeman 说，信任工具很大程度上是向别人学来的。你的团队里，关于 AI 的知识现在掌握在谁手里？怎样让它流动起来？

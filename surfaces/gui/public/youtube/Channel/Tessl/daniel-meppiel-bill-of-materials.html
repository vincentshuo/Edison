开发者快要不写代码了，改写散文与技能——微软 Global Black Belt 团队的 Daniel Meppiel 在 AI DevCon 纽约站的访谈与演讲里，把这句判断一路推到底：如果技能就是新的软件模块，那么写技能的“软件工厂”也得像软件一样被版本化、被清点、被签名。他先在访谈里拆开技能的版本难题与 APM 的物料清单，再在演讲里现场跑通一整条证据链：一份 Markdown 意图文件进厂，五份 Agent 合约依次执行，出来一份带签名的收据，门禁只认证据、不认风险分级——受监管的企业凭这条链，才敢让工厂自动合并。

Key Takeaways

  1. 开发者不再写代码，改写散文与技能。技能是新的软件模块，MCP 服务器、钩子等 Agent 原语与技能一起组成软件工厂的基础设施。
  2. 技能的版本号卡在行为上。代码看方法签名就能定大版本，技能得看改动是否改变了行为方向——而行业至今没有系统地评测技能改动。
  3. APM 把 npm 的做法搬进 Agent 世界。清单、锁文件与策略三件套，锁文件直接生成 Agent 物料清单，出事能一路追溯到出问题的技能。
  4. 技能永远只是指引。写进技能里的禁令，大写加粗重复十遍，模型照样可能不照做；真正的安全控制必须是确定性的运行时治理。
  5. 工厂要像程序一样被版本化，产出要带签名的收据。收据里有 SLSA 来源证明、in-toto 证据与物料清单，门禁凭证据放行或拦截，自动合并才有可审计的依据。

1. 开场：不再写代码，改写散文与技能（约 0:00–2:53）

视频以 Meppiel 的一句话冷开场：开发者不再写代码了——要写的是散文，是技能。接着是节目片头：AI Native Dev，一档面向开发者与工程负责人的播客，主持人是 Guy Podjarny 与 Simon Maple；这一期是在 AI DevCon 纽约站现场录的，Simon 穿着一件黄色 aiDevCon 文化衫，隔着玻璃门就是正在进行的另一场演讲，他得压低一点音量，怕声音漏过去。

坐在他对面的是 Daniel Meppiel，微软 Global Black Belt 团队的开发与 Agent 平台负责人。Global Black Belt 是微软商业业务里的参考方案架构团队，Meppiel 的工作是帮全球最大的客户用 AI 改造软件工程实践——此前他在 GitHub 做过同样方向的工作。他的演讲题目叫《Version Your Factory, Not Just Your Code》，讲的是提示词、技能与工作流背后的东西：把它们当作软件来对待，可以测试、可以升级。

“We are not going to be writing code anymore. We are going to write prose. We are going to write skills.”我们不再写代码了。我们要写散文，写技能。

核心判断就一句：代码不写了，写的是散文——而散文一旦被装进技能这样的模块，就拼成了一座“工厂”：一套自动化的流程。这是一种新的编程范式，而经典软件工程里的大量做法，可以直接搬到这种用自然语言写代码的新方式上。

2. 技能取代代码之后，开发者还剩两件事（约 2:53–7:52）

开发者角色随之分叉。Simon 替听众把问题拆成两件：第一，决定到底要建什么；第二，盯着工厂本身——让底下的 Agent 最高效地出活。Meppiel 的补充是，工厂不只是技能：MCP 服务器、钩子这些 Agent 原语都挂在 harness 上，共同让 Agent 的输出值得信任。

■ 技能（Skill）：用自然语言写成的可复用模块，告诉 Agent 该怎么做、按什么风格做，是 Agent 世界里的软件模块。

■ Agent 软件工厂（Agentic Software Factory）：把意图自动变成代码改动的自动化流程，由技能、提示词、工作流与各类 Agent 原语串联而成。

技能分两种。一种是补模型短板的：模型今天还不会、但人人都想要的做法，写成技能大家都能用；另一种是风格与偏好：这家组织喜欢这样做，那家喜欢那样做。各家工程团队都会建自己的技能、分享自己的技能。

眼下最大的问题是各建各的。几千名开发者的组织里，欧洲的团队、美国的团队、亚洲的团队各自把独特知识与流程沉淀进技能，确实换来了生产力与回报——但同一份技能被不同的团队在不同的笔记本上反复重造。第一道坎就是怎么把它们收拢到一处，不再重复造轮子，好让规模经济显出来。

■ Agent 原语（Agentic Primitives）：挂在 Agent harness 上的基础构件——技能、MCP 服务器、钩子等，作用是让 Agent 的输出更可靠。

3. 版本号的难题：行为变了，算大版本吗（约 7:52–14:09）

演讲标题里的“版本化”不只指技能。Meppiel 说，工厂盖子里还有一样东西今天没人版本化，但很快就会：循环——拿到技能，还得有触发器（什么启动这轮自动化），还得有验证（什么标准算达标）。这些部件今天散落在各处：检查在一边，技能在另一边，意图又在另一边。他在演讲里把循环叫作 Agent 合约，认为它可能成为 harness 的下一个标准单元。

测试也随之分叉。代码世界有两种编程方式（确定性的编程语言与不确定的散文），就有两种测试：经典的单元测试与集成测试，仍然是出货信任的根基，不能拿掉；另一类是 LLM 评审——它能发现确定性引擎发现不了的漏洞，比如代码里违反监管框架的地方，而那类框架根本没有确定性检查可用。两类测试都要有，包括评测技能与工厂的时候。

“How on earth do we go about a good versioning system where we can recognize that this is a major change to the skill, and what constitutes a major change?”我们到底怎样才能建立一套好的版本系统，认得出这是一次对技能的重大改动、什么才算重大改动？

语义化版本在代码世界里很清楚：方法签名变了、会弄坏别的东西，就是大版本；虽然常被滥用，但什么时候升主版本、什么时候升次版本，判断标准是清楚的。技能呢？Meppiel 说行业至今没想明白：核心是区分“沿着同一方向的增量改动”与“把方向切换到另一边、改动输出、要求使用者另做点什么”的改动——后者才是大版本，也就是行为上的重大变化。

要稳定地判断，就得靠评测：评测要能测出一次改动是否让技能偏离了原有的标准行为或行为方向。可现实是，Meppiel 接触的客户里，至今没人严谨、系统地评测自己的技能与技能改动。等评测成了家常便饭——每次改技能都有评测证明改动把我们带向想要的方向——才能有把握地说“这是 2.0，不是 1.1”。

■ 语义化版本（Semantic Versioning）：用主版本号、次版本号标识软件变更的规则；破坏性变更升主版本，兼容的新功能升次版本。

4. APM：把 npm 的做法搬进 Agent 世界（约 14:09–17:44）

Simon 一眼看出 APM 像什么：Agent Package Manager。Meppiel 说，它就是把 npm 这类包管理器的想法搬进 AI 原生开发，不重复造轮子，而是把经典软件工程里已经解决的问题再解决一遍：第一是可复现——你有一套好用的技能，为什么还要让别人发邮件传给你？从一份清单里安装就行；第二是可信——npm 安装时会给一份锁文件，里面是每个依赖的密码学签名与哈希，能认出装回来的就是你要的那一份。APM 同样给锁文件。

第三是可审计：用了什么、什么版本、在什么上下文里建的，都能查；第四是供应链——依赖世界里供应链是大问题，Agent 世界只会更严重。锁文件把这两件事连在一起：有了清单与锁文件，就有了可追溯性——从工厂的产出，一路追回到参与构建的技能。这就是一份“材料清单”的上下文。

■ APM（Agent Package Manager）：Meppiel 创建的 Agent 包管理器，把 npm 的做法搬进 Agent 世界：清单声明依赖，安装时写锁文件，还能加策略控制允许或拒绝哪些依赖。

■ Agent 物料清单（Agent Bill of Materials，ABOM）：一份 Agent 用到的全部技能及其传递依赖的清单，由 APM 的锁文件直接生成，类比软件物料清单（SBOM）。

Meppiel 对这点很看好：APM 今天就能生成他所说的 Agent 物料清单——拿锁文件，看全部依赖与传递依赖；一个技能可以依赖另一个技能，形成传递依赖树。“这就是进到我的 Agent 里的东西，它在 Agent 运行时起到了关键作用，无论结果是好是坏。”出了坏事，就能往回追溯，说问题出在这里，出在这个技能里。

“When bad things happen, you need to have a way to backtrack and say, the problem was here. The problem was in this skill.”出了坏事，你得有办法往回追溯，说问题出在这里，出在这个技能里。

5. 技能永远只是指引，控制必须是确定性的（约 17:44–21:02）

技能是指引，这意味着 Agent 大多数时候会照做，但统计上总有时候不照做——不是公然违抗，而是做得跟技能要求的有细微出入。安全恰恰卡在这里：有些事必须按某种方式做，这就得区分“指引”与“真正的控制”。

Meppiel 的类比是招人：招一个人进来，你面试他是因为他已经自带技能，不用你再给他装技能；但同时你会给他一张门禁卡——卡能进楼，这就是安全控制；再给他一台装了安全措施的笔记本。Agent 也一样：一边是技能，另一边是安全控制——运行时的治理、检查、运行时拦截、沙箱与权限，全都僵硬而确定。

“Skills are always guidance. Even if you write it in capitals or you repeat it ten times that you cannot do this…”技能永远只是指引。就算你用大写写下来、重复十遍说不许这么做……

主持人追问：那就对了，完全确定。Meppiel 的回答是：完全确定。技能定的是 Agent 的行进方向——流程、工具与品味；控制定的是不许越过的线。两者不能混为一谈，混了，安全就只剩一张写在提示词里的纸。

6. 先集中成目录，再谈治理与度量（约 21:02–28:08）

听众大多已有自己的 Agent 配置、一堆提示词与技能，下周先改什么？Meppiel 的第一步：把共享的技能集中进一个目录，人人能去读、能改进、能从那里取用——这就启动了内源化（inner sourcing）的循环。第二步是治理，尤其对大型受监管行业：定政策，哪些技能按任务、项目、团队必须在场，哪些不许进、哪些允许进，往标准化走；归属按技能的作用范围定：组织级、团队级、部门级、项目级乃至个人级。

平台团队是牵头的人选：把技能目录与企业级治理当作一种服务，提供给 Agent 开发者。APM 的策略引擎支持级联继承——仓库级、团队级、组织级层层继承，这与平台工程至今的做法如出一辙。

标准化之后，下一个解锁的是可观测性：接入编码 Agent 的日志，看哪些技能在何处被使用、用的时候发生了什么，再把这些与 DORA 那套结果指标连起来——比如每周每名开发者合并的 PR 吞吐量。指标向好，才能说这是一次正向影响，而不是“上次管用一次”的轶事。

工厂跑起来之后，开发者做什么？Meppiel 看到两件事。第一，会出现一个运维团队，专职照看工厂——像 DevOps 团队照看 DevOps 实践与基础设施一样，而且是跨组织、跨项目的；一个组织里可能同时跑着几十座工厂，就像今天每个项目各有一条 DevOps 流水线。第二，开发者的重心移到意图与决策上：该开发什么、为什么开发——更多是人与人之间交流想法，讨论建什么、对用户有什么帮助。Simon 笑问：这不就是 DevOps 平台角色加产品经理角色吗？Meppiel 的回答是，别急着贴旧标签，等着看未来的新标签；守住核心想法，反而更自由。

7. 银行那一杆，你敢自动合并吗（约 28:08–31:30）

访谈结束，Meppiel 走上讲台。先报身份：他不在工程也不在产品，而在技术方案架构一线，帮大型企业——常常是受监管的企业——落地 AI 与编码 Agent，演讲的经验来自一线。

设想一家银行：它跑着自己的核心银行系统，任务是改支付逻辑——向新收款人汇出 1 万美元以上的电汇，要先内部审批。工厂生成了这份 PR，问题是：你敢自动合并吗？Meppiel 说，今天每家银行都会说不。

风险分类器、验证器，这些东西都有，但答案在一段时间内很可能还是“不”。Meppiel 要讲的，就是怎样才能有一天自信地自动合并。工厂产得越多，新的瓶颈越明显：一个是 CI——每个请求都让 CI 从头跑一遍；另一个是人。昨天主题演讲里说要把人全部拿掉，否则 Agent 软件工厂在大组织里也扩不出去。

行业正在收敛到风险分类器：识别改动改了什么，只在风险值得时才交给人。但对大型受监管企业，这还不够：自动合并之后，谁来回答“这是哪座工厂做的、我们信它吗？”只凭风险分类器，还没有信任。

8. 企业要的四样东西，与经典软件的信任织物（约 31:30–35:00）

每次跟大企业聊，四个问题总会出现。第一是验证：工厂产出的代码，真的符合我们的意图吗？第二是标准：这次改动是按我们的平台工程标准、合规框架与编码风格写的吗？第三是可追溯性：合并的代码来自用了多少技能的工厂，生产出问题时，怎么追回到该改进的技能、追回到被攻破的工厂？第四是安全：Agent 软件工厂成了新的攻击面，而且是极有利可图的攻击面——它们将生成全部代码，把人从编码里拿掉。

再看经典软件在 AI 时代之前是怎样建立信任的。Meppiel 的比喻是“信任织物”：一切从版本化开始——版本是给软件制品一个身份、一枚指纹；有了身份，才能建清单、来源证明、证据这些其余部件；行业还为此立了标准、说同一种语言：CycloneDX、in-toto；又发明了签名；最后是准入检查——每家企业自己的策略：查这份软件的物料清单、查是哪个组织创建并签名的，再决定它能不能在我的银行里跑。

■ 信任织物（Fabric of Trust）：经典软件靠版本、清单、来源证明、证据、签名与准入检查织成的一张信任网；Meppiel 主张为 Agent 工厂织一张同样的网。

问题是：Agent 软件工厂生成软件时，这张织物在哪里？Meppiel 说，今天几乎没有。所以得建一张。

9. 工厂就是程序，合约就是它的函数（约 35:00–41:00）

第一步是把工厂看作一个 Agent 程序、一款软件。Tessl 讲 loops，GitHub 讲 automations——说到底都是一堆技能、一堆提示词，跑着一段用自然语言写成的流程；工厂就是把这些串起来的集合，像程序串起函数。既然是程序，就该版本化——版本化是信任织物的第一根线。

第二个问题是今天的“准工厂”把太多散件胶在一起：技能、提示词、脚本、代理、网络层、沙箱层、环境层、基础设施层。另一条路是直接用厂商的工厂——GitHub 的 automations、Tessl 的 loops、Cursor 的 automations：界面体验很好，但工厂一旦建在那里，就很难搬走、拿到别的 harness 上跑。中间缺的是一套标准。

“Trust comes from the factory, not the model.”信任来自工厂，不是来自模型。

缺的是定义 Agent 工作最小单元的唯一标准方式。Meppiel 的提议叫 Agent 合约（agent contract）：不叫 automation，也不叫 loop——就像入职要签工作合同一样。合约是一份简单的 Markdown 文件（YAML front matter 是一种可能的格式），里面写：任务（外部输入，今天改这段代码、明天改那段，任务会变）；角色（Agent 在这份合约里扮演的角色，不变）；依赖（为完成这份工作提供给 Agent 的东西）；预算（我们愿意为这份工作付多少钱）。产出则是检查结果、验证与交付物——代码改动、diff、PR。

■ Agent 合约（Agent Contract）：定义一份 Agent 工作的 Markdown 文件：输入的任务、Agent 扮演的角色、可用的依赖与预算，以及产出的检查与交付物。

合约把技能与完成工作所需的一切连起来，本身就成了一段程序、一段 Agent 程序：可以版本化，可以组合（合约之间互相组合），如果更多 harness 与厂商接受它，就可以移植；它有身份，可以开始织信任织物。工厂就是一张合约组成的图：规划一张、规格一张、构建与实现一张、文档一张、评审一张，串起来就是工厂。给它一个版本，就有了指纹、有了身份。

10. 现场演示：同一份工厂，两台 Harness 上跑（约 41:00–44:30）

有了定义，怎么跑起来？Meppiel 回到开头的银行例子：意图写在一份 Markdown 文件里——contoso-payments 仓库的 request.md：“向新收款人汇出 1 万美元及以上的大额电汇，需二次审批”，规则、约束与完成标准都写在里面。工厂本身来自公开仓库，合约文件夹里放着一堆合约；比如构建合约：输入是意图与上一份合约产出的规格，产出是一份 diff，导入某个指定的技能，还有预算。

旁边还有一份 APM 的 YAML 文件——相当于 npm 世界的 package.json，声明工厂运行所需的依赖（技能）。依赖装好后，合约像普通编程语言里导入模块一样引用它们。运行用的是 apmx——类比 npm/npx、uv/uvx。Meppiel 同时开了两个终端：左边在 Copilot 上跑工厂，右边在 OpenCode 上跑。APM 先读清单、安装依赖、写锁文件，然后工厂作为一段程序跑起来，合约一环接一环：先跑规划。

这就是他说的可移植开放格式：同一份工厂，换一个 harness 照样跑。演示用的意图文件来自 GitHub 上的公开仓库 danielmeppiel/contoso-payments，仓库说明写明这是“为 APMX 演示准备的虚构银行电汇服务”；意图文件只有 27 行：1 万美元按 1000000 美分计，9999.99 美元按 999999 美分计；已知收款人照旧放行，低于 1 万美元照旧放行；“已知”按账户算——别的账户付过的收款人，对这个账户来说还是新的；无效金额（负数、零、布尔值、非整数）在任何扣留与记录之前就按今天的做法驳回；已有行为与测试保持不变，只用标准库。

11. 收据：签名的证据链，门禁只认证据（约 44:30–49:00）

APM 是 Meppiel 独立发起的开源项目，入职微软后转到了微软开源组织，目标是移到一个中立基金会。它很简单：清单声明依赖，安装时写锁文件，企业再加一条策略——允许哪些依赖、拒绝哪些依赖。合约作为程序运行，依赖技能、MCP、钩子等等，可以在任何编码 Agent 上跑。产出除了 PR 与 diff，还有一样东西：收据。

收据为什么重要？意图进来，工厂（合约链、循环或自动化，随你怎么叫）产出 diff，也产出一份收据。收据由运行工厂的那台机器签名——由我们选择信任的运行方来签。规则与策略随之而来：我们信任哪些工厂、允许哪些技能、拒绝哪些——比如听说某个技能被攻破了，就在规则里拒掉它。门禁通常落在 CI/CD 里、落在指向 main 的 PR 上；Meppiel 的演示命令是 apmx audit：读收据、读策略，看两者是否对得上，再决定拦截 PR 还是自动合并。

■ 收据（Receipt）：工厂每次运行产出的签名记录，内含来源证明、检查结果与物料清单，是门禁判断能否自动合并的证据。

收据本身建立在软件供应链的公开标准上。第一块是 SLSA 来源证明：产出的 diff 与工厂通过指纹与摘要链在一起，带来可追溯性；第二块是检查与检查结果：每份合约里定义的检查，Agent 改不了——“记住，Agent 是不能信任的，它们会改游戏规则”——所以检查本身与检查结果都要用密码学链进收据与证据里，这一块基于 in-toto；第三块是 Agent 物料清单：工厂的组成，类比软件物料清单；最后是签名：签名方必须是可信的签名者，不能是跑工厂的那台机器——因为 Agent 不可信。身份（工厂版本指纹）、清单（锁文件生成的 ABOM）、来源证明（SLSA）、证据（in-toto 的检查与结果）与带证明的签名合起来，就是信任织物；门禁凭实际证据自动放行，而不是凭风险分级。

12. 这套做法能回答的四个问题（约 49:00–54:00）

有了收据、门禁与规则，Meppiel 说可以跳过人工评审、跳过造成瓶颈的 CI 流程，直接自动合并——不是凭风险分类、个人信心，或是“我们招了很聪明的工程师、他们说信得过这座工厂”，而是凭可以追溯的实际证据。监管机构的审计员上门时，可以精确指向遵循某套监管框架的控制、指向当初决定信任的技能或工厂、指向出了什么问题、该采取什么行动、责任落在谁头上。

他举了四个这套做法能回答的问题。生产坏了，全部由工厂建成——哪座工厂、哪一步负责？从源代码追到收据、再追到工厂，版本化从一开始就给了身份。开源世界里用的某个技能被攻破了——谁暴露了？查 ABOM 或存过的每一份收据，找出用它的工厂，打补丁、在规则里吊销，门禁随即禁止这些工厂的产出进生产，直到修好。

检查通过了，可 Agent 有没有动手脚？Meppiel 说，Agent 一贯会钻检查的空子。但检查写在合约里，不是干活的那个 Agent 创建的，所以改不了；检查与检查结果用密码学绑进收据，篡改会被发现，门禁执行时也会核对。想加新检查？新检查改了工厂，那就发一个新工厂版本；再去策略文件里写：从今往后只接受 2.1 版以上工厂的 diff——门禁会拦下所有旧版本的产出。策略里还能写清允许工厂用哪些技能，依赖本来就锁在清单与锁文件里，审计命令一查便知。

回到演示现场：Copilot 那一路，五份合约（规划、规格、构建、文档、评审）全部跑完，11 项检查全部通过，耗时 5 分 05 秒；状态靠文件在合约之间流动——Markdown、diff、产出物；收据以 receipt.in-toto.jsonl 落盘。Meppiel 当场跑了一遍审计命令：本地这份收据没签名，所以检查没通过；随后他展示了一份工厂生成的 PR，里面 apmx audit 作为唯一的检查——收据已由运行工厂的环境签名，可以是 CI/CD，也可以是 Kubernetes 集群，随你把工厂跑在哪里；检查全部通过，这才是一份可以说“现在能自动合并吗”的有效陈述。

13. 收尾与问答：检查必须是确定性的（约 54:00–61:08）

收尾时 Meppiel 把线索收拢：大家正在趋同于“工厂最小单元”的某种定义——Tessl 讲 loops，各家厂商讲 automations，他讲 contracts。真正需要的是一个共享的格式、共享的标准，不要重复造轮子：经典软件的信任织物已经造过一次了，把学到的教训搬过来，为 Agent 软件工厂织一张同样的网，而且要在开放中做。工厂即代码，用开放格式定义；版本化（身份是一切的起点）；然后是证据；随之而来的是可信、来源证明、可移植；跳过 CI、跳过 PR 评审——这就是 Agent 软件工厂扩展到大型受监管企业的方式。他把这份开放格式的草案（0.1 版）公开出来，请在场的人参与讨论。

“We need a shared format. If we do want portability of software factories, we need a shared format, a shared standard, and we need not to reinvent the wheel.”我们需要一个共享的格式。如果我们想要软件工厂可移植，就需要一个共享的格式、一个共享的标准，而且不要重复造轮子。

问答只留了一分钟。第一个问题：合约里定义的检查，是不是要取代单元测试与集成测试？Meppiel 的回答是：检查必须是确定性的——检查就是模型周围那层值得信任的 harness。写规格的合约，检查可以是规格的格式；做 PR 评审的合约，检查可以是评审的格式；做构建的合约，检查可以是“不许碰这段代码”“必须遵守这种风格”，也就是 lint 之类。第二个问题没听清，只听到“staging”与 CI：他的回答是，既然有了可信的签名证据证明检查已经跑过而且通过了，CI 里就不必再跑一遍——把测试尽量左移，而且是以可信的方式左移。第三个问题来自一位听众：“瀑布对人来说是坏主意，为什么对 AI 就是好主意？”Meppiel 说，瀑布在某些场合其实做得很好；问题大概来自图上那条看起来像瀑布的链；他同意瀑布不是万能答案，这只是一个例子，完全可以用合约去建模别的流程。

别再跟电子表格聊天：造一个能托付金钱的 Agent 脚手架

Stop Chatting With Spreadsheets

Speaker: Francesco Galletta & Felippe Felisola Caso, Monzo

Event: AIE Code Summit, New York

Length: 1 小时 50 分 34 秒

Source: youtu.be/ATMcd9tkhhc

Technical Monograph · 精读报告 发布 2026 年 11 月 9 日 生成 2026 年 11 月 17 日

Monzo 数据团队的 Francesco Galletta 与 Felippe Felisola Caso 用一场婚礼预算现场造了一个金融分析师脚手架，回答一个问题：答案唾手可得，能托付金钱的答案却很难。他们的论点是，瓶颈不是速度，而是信任—— traces、循环、评估、单元测试这些组件都不新，真正缺的是把信任焊进系统的五条设计原则：共享领域、一致性、证据、问责与验证。五条原则层层相叠：先对齐计划，再让算术只发生在代码里，再让每个数字都能倒查回来源，再由人守住高信号关卡，最后用外部参照点做验证。演讲全程是一场现场工作坊：观众跟着同一套脚手架规划同一场婚礼，从三笔付款、每席约 150 美元的晚宴、500 美元的花艺一路算到每月该存多少钱；结尾的问答则把问题推回原点——什么时候值得造一个脚手架，什么时候用技能与指令就够了。

Key Takeaways

  1. 瓶颈不是速度，是信任。钱是最讲信任的题材；赢得信任，才能把无聊的工作委派给一群 Agent。
  2. 先对齐，再计算。共享领域是地基：计划是决策树，数字只在计划被接受之后才出现。
  3. 算术只许发生在代码里。写一次、测一次、每次跑同一份；改了一个乘号，测试就该拦住你。
  4. 每个数字都要有收据。事实、假设与解读分开标注，改了任何一处都能倒查回去。
  5. 问责与验证是两道不同的门。人守住高信号关卡，第二双眼睛只提供信息，从不接管责任。

1. 瓶颈不是速度，是信任

演讲开场先自我介绍。Francesco Galletta 来自委内瑞拉，在英国住了约七年，最近搬到马德里，在 Monzo 做数据工作；Felippe Felisola Caso 来自巴西，到英国约一年半，此前在 Nubank 工作，如今也在 Monzo，负责用内部 AI 方案提升数据团队的生产力。两人声明，这场演讲不代表 Monzo 发言——他们带来的是在 Monzo 积累的经验，现场要造的例子是另外的东西：如果好奇 Monzo 内部在造什么，第二天另有一场分享，讲 Monzo 自研的远程 Agent 能力 agent chip。

他们在 Monzo 的 AI 采用方式很克制：不追求 token 用量最大化，只看是否带来具体的业务价值；采用是深思熟虑的，效果也很好。与此同时，Francesco 把同一套思路用在自己的生活里——不是给一个通用 Agent 接上所有东西，而是挑自己真正在乎的事，让 AI 把它变简单。婚礼预算就是这样一件事。

“The bottleneck now is how it connects with us.”瓶颈在于它如何与我们连接。

今天的目标是一个词：信任。这听起来有点虚，尤其这是一场两小时的工作坊，本该埋头写代码。但演讲者的判断是，产出答案的速度早已不是瓶颈——后台跑着 Claude 或 ChatGPT 的人大有人在。瓶颈在于它如何与我们连接：你怎么信任它给你的结果？钱尤其如此，这是风险最高的题材之一，必须把信任建进系统里。如果你觉得钱还不够高风险，能一键解决预算与融资的一切问题，演讲者开玩笑说，会后可以找他聊聊投资点子。

信任买不来，但可以一层层建。演讲者先点名了一串大家耳熟能详的东西：traces、循环、评估、单元测试、跟 Agent 一起规划、可观测性、循环与图。这些都不新，也都有用，但它们只是组件。今天要讨论的是设计原则——造一个能托付金钱的脚手架，靠的是原则，而不是把组件堆上去。也不讨论具体技术，不念某个产品的说明书，并假定听众已经知道这些概念。

五条原则按顺序叠起来。第一是共享领域：确保你和模型用同一套语言说话，这比听起来难得多。第二是一致性：数字必须来自正确的地方，模型不直接做算术，而是调工具、写脚本，让结果每次都一样。第三是证据：拿出收据，能一路倒查每个决定是怎么来的。第四是问责：即便跑着一百个 Agent，你仍然要为它们的结果负责。第五是验证：需要一个独立的视角、另一个参照点，否则你只会按自己的偏见跑。

■ 脚手架（Harness）：把设计原则焊进确定性代码、流程与检查点的运行层，而不只是给模型一堆指令。

五条原则不是并列的清单，而是递进的链条：没有共享的领域，就没有可信的计划；没有一致性，证据无从谈起；没有证据，问责没有抓手；没有问责，验证只会把责任推给评审者。演讲的后半程会逐条拆开，每条都配现场演示与一个可以动手试的环节。原则本身也留了余地：这不是唯一的模型，只是在他们手头的多个用例里行得通的一套做法，没有银弹。

2. 一场婚礼：把信任问题具体化

在讲原则之前，演讲者先坦白了一个“别有用心”的安排：全场观众今天要帮 Francesco 规划他的婚礼——具体来说，是为婚礼筹钱的财务问题。听起来简单，结过婚的人都知道不是这么回事：数字怎么会贵得这么快，本身就不是一目了然的。

Francesco 讲了一个家里的插曲：未婚妻说晚宴每席是这个价，他说不对，上面还有另外两项可变成本，所以那不是最终数字。婚礼预算就是这样一点点失控的。现场的任务就是这件事：帮他算清楚，或者规划你自己的方案。仓库里备好了三样东西：今天的指南、婚礼示例、脚手架本身，还有一个文件夹，装你偏离主线后自己造的东西——都可以带回家。

婚礼的具体数字在演示中一点点出现：三笔付款，第一笔 6,000 美元，第二笔金额未知，第三笔是余款；固定成本有 DJ 与装饰；未知的是到场人数与每席晚宴的价格（约 150 美元），花艺 500 美元，还要买西装；他没有存款，钱从自己口袋出，妈妈可能给 5,000 美元。这些数字本身不重要，重要的是它们的状态各不相同：有些是事实，有些是未知，有些是别人的承诺——而脚手架必须分得清这三者。

这个例子是故意选的：它足够小，每个人都能跟上；又足够真，钱一动就见分晓。演讲者提醒，脚手架本身是过度工程化的，界面也不好看——重点不是它有多 slick，而是用起来“感觉”如何：一个按信任原则造出来的 Agent，用起来应该是什么感觉。

3. 原则一 · 共享领域：先对齐计划，再算数字

第一条原则是共享领域，演讲者也叫它计划模式。做法是从目标出发、倒着往回走，和 Agent 一起把问题拆开。关键在于一个多数人没意识到的事实：模型知道的，不一定是你以为它知道的。除非你有专为自己训练的模型，否则你对某个词的定义，很可能与大多数人的定义不一样。模型或许够聪明，知道这个词落在哪个空间里，但那未必是你想说的那件事。来回沟通才有意义，脚手架的作用就是逼你深挖、挑战自己的假设，问出那些你没想到需要问自己的问题。

“What is obvious to you is not what the model learned.”对你显而易见的，未必是模型学到的。

现场演示从一个空白聊天窗口开始。Francesco 像用户一样描述问题：我有一场婚礼，要付三笔钱，一笔 6,000 美元，一笔金额未知，一笔是余款；有些成本是固定的，DJ 与装饰的价钱我知道；但我不知道会有多少人来，也不知道每席晚宴多少钱，更不知道怎样才能保证按时付上钱。他刻意说得含糊、没有条理——因为重点正是 Agent 不能放过含糊之处：它必须追问，直到每个数据点都被钉住。

大多数脚手架都有某种计划环节：它会尝试理解你要规划的问题，提出一套合理的问题来澄清。但这里的区别在于，脚手架规定了追问的严格程度，以及计划在动手之前必须达到的严谨度。它不会立刻进入“好好先生”模式，把你那个含糊的想法直接实现，而是逼你把问题挖到底。这就是共享上下文的原则：先有计划，再有执行。

来回大约十分钟后，计划被接受了。屏幕上出现一张图：计划被拆成一个个步骤，每个步骤都是决策树上的一个决策点。图里的每个节点都标明信息从哪里来——是你说的事实，是 Agent 根据你的措辞推断的，还是尚未决定的开放问题。点开第三步，能看到每条信息的来源与 Agent 的推理，包括它根据你的用词做了什么假设。你也可以点开某个节点告诉 Agent：你这里的假设不对，再来回修正。计划不是一团文字，而是一张可以逐项检查、逐项争论的图。

■ 共享领域（Shared Domain）：你与模型对同一问题的定义、口径与假设达成一致的状态，是其余四条原则的地基。

■ 决策树（Decision Tree）：计划拆解成的决策节点图，每个节点标明信息来自你、来自 Agent 的推断，还是尚未决定。

演讲者提醒，这张图背后的东西值得看一眼：脚手架里写着访谈 Agent 的指令——它必须问什么、必须以什么收尾。这就是原则在脚手架里的物化：原则不只是一句口号，而是写进指令里的行为。仓库里还有一份额外的“自己造”指南，把全部原则按顺序焊进去，引导你造一个类似的脚手架——重点不在代码本身，而在你打算用什么方法解决问题。

3.1 长线性对话为什么撑不住

现场做了一个举手调查：谁有过十轮以上的对话，最后说“让我从头开始吧，这已经讲不通了，有些事我们明明讨论过，现在全没了”？全场都有同感。演讲者说，这是今天脚手架设计的直接后果：它们为线性讨论而设计，把一切都塞进一个大上下文里。而这里的设计是把问题拆开，让你可以逐项讨论，而不必让整件事变得更复杂。

共享领域的代价是时间：大部分时间都花在对齐上。演讲者的结论很直接——设计得好的脚手架会牵着你的手走，帮你想出一个好计划、把事情实现好、知道哪些组件重要、哪些不重要。如果脚手架只是对你说的每句话都说好、尽力去实现，你得到的就是不稳定的结果。计划环节的价值，正在于它把“你以为你说了什么”和“模型以为你说了什么”之间的缝隙先找出来。

4. 原则二 · 一致性：算术只许发生在代码里

第二条原则建立在第一条之上：计划已经有了，Agent 很容易判断出，计划里的哪些部分只是一段代码、一次电子表格计算——也就是确定性的部分。确定性的东西每次都给出同样的结果，所以必须用代码实现，而不是让模型现算。

“You write the calculation once and then you run it every time you need it.”计算写一次，每次都跑同一份。

现场又做了一次举手调查：在聊天里做过预算或财务计算的人，结果如何？答案是参差不齐。Francesco 讲了自己的经历：他给了 Agent 全部必要信息，Agent 还回一个公式，排版得漂漂亮亮的斜体公式，看起来很懂行——结果他一眼就看出是错的，从头再来。另一位听众补充：结果有时看起来合理，但同样的东西再跑一次，答案变了，那一刻你就知道出问题了。

这正是造脚手架而不是只给现有脚手架加一堆指令的原因。只加指令的做法，本质上是把一堆“请按正确的方式做、请不要出错”的要求交给 Agent，然后指望后台不出错——每次得到一个非确定性的结果。脚手架的价值在于把非确定性与确定性混在一起：在需要的地方，由你控制确定性的部分。这是他们在 Monzo 应用的同一条原则，与实现细节无关。

有人追问：现在 Agent 的工具调用越来越强，会自己造工具做确定性计算，问题不是迟早会自己解决吗？演讲者的反驳是，Agent 会在飞行中现造代码——这次造对了，下一次跑到第一百次，它可能又发明了一段本不需要重造的代码。Francesco 自己的例子是每月的预算：他把分类、汇总、退款与开支交给 Agent 决定，结果每次都略有不同；有三次算对了，第四次错了，他花在与 Agent 纠缠上的时间与金钱比省下的还多。最后他把它写成了脚本：计算写一次，每次都跑同一份。

判断标准很简单：如果是计算，大概率就该用代码实现，附带测试、单元测试与黄金示例。代码还要有版本：如果代码变了，Agent 应该能发现并告诉你——函数名虽然一样，算出来的东西已经不一样了，你不该再信任它的输出。演示里，接受计划后屏幕上方会出现提示：要不要我来建代码？点进去，第一步有代码、有测试，点“运行测试”，测试直接通过，没有 Agent 惯常的“思考中”之类的动词——因为这只是需要在你的环境里跑的测试，不要过度工程化。

■ 确定性计算（Deterministic Computation）：同一输入永远给出同一输出的计算；脚手架规定它只许发生在代码里，不许由模型现算。

现场还可以试一个破坏性动作：把某行代码里的乘号改成加号，保存，然后跑测试。你会发现结论出不来了——脚手架按自己的定义把你拦住了。演讲者的点评很直白：你刚亲手破坏了分析。重点不是不许你改代码，而是改完之后，系统必须让你知道后果，而不是悄悄给你一个错的数字。同样，Agent 也必须被严格约束：它不许用解析 token 的方式做算术。否则，算术只存在于模型的那次会话里，新开一个会话就没了；同一个问题，换一个问法，答案又变了——你等于在要求一台随机的机器给出一致的输出。

5. 原则三 · 证据：每个数字都能倒查回去

第三条原则是证据，演讲者的说法是“拿出收据”。它建立在第二条之上：既然代码是经过测试的，一切都有迹可循，你就能倒着跟回去，为每个决定找到依据。原则本身需要解释，不能只留一句“要讲证据”——证据要管的事，是信息并不都一样。

在数据工作中，这一点每周都会咬人一口。聊天里的零散想法要标为解读；Agent 从记忆里调取信息、进行推理，要当作假设；而银行对账单提交上来的数字，就是事实——花了多少钱，没什么可讨论的。婚礼的例子很小却很致命：受邀人数是一个事实，直到未婚妻多请了三个人却没告诉他，整个模型就错了。一个藏在某处的错误假设，如果不知道它从哪里来，对任何财务分析都可能是致命的。

■ 收据（Receipt）：每个数字、每个结论都能一路倒查回来源的证据链；事实、假设与解读必须分开标注。

演讲者讲了一个“总表文件”的恐怖故事：每家公司都有一个总表文件，收藏在共享盘里，有人往里面填数字，一切看起来都正常。但文件里藏着对“合理取值范围”的假设；文件改了，当事人不知道——他什么都没做错，只是不知情——结果全错了。确定性代码也一样：如果代码的改动没有可追溯性，流程一变，你就会留下盲点，输入变了都不知道。

证据也进代码：不只是这个数字从哪里来，还有它是怎么得来的。演示里可以点开任何一个带下划线的数字——比如 31,000——一路倒查回它来自哪一步、经过哪些输入、通过了哪些测试；也可以在聊天里加一个“曲线球”，改一个事实，再看证据链如何变化、变化的源头是不是你刚才的纠正。行业里的金融分析师实现也一样：可追溯到数据集，知道是哪个连接器、哪个数据供应商在当天的那个时点给了苹果股票那个价格。

证据缺失的代价，现场有一位听众用做幻灯片的经历接上了话：他造了一个脚手架，帮他挖问题、找相关文档、提炼要点；但他没发现，每次他要求改动并给一个例子，模型会死死抓住那个例子，把它铺满整份演示。直到给高层汇报时被问“这个数字和假设从哪里来”，他才发现自己完全不知道。这条后果链会直接伤害你对脚手架及其产出结果的信任。

6. 原则四 · 问责：Agent 不承担后果，你承担

第四条原则是问责，建立在证据之上：你只有在有事实、有参照点的时候才能做决定。演讲者的核心判断很直白：我们最终要为 AI Agent 所做的一切负责。有一句话他很喜欢，却总引不出处：Agent 不承担现实世界的后果，你承担。

“Agents face no real-world consequences. You do.”Agent 不承担现实后果，你承担。

现场立刻有人接话：谁见过、或者自己说过“不知道，Claude 给我的就是这个”？全场都笑了。演讲者的点评是：这话一出，仿佛一切都被原谅了——但事实并非如此。问责机制的存在，就是为了减少你脑子里那种“它是不是在这里做了个错误假设”的压力。目标是减少歧义，而不是消灭歧义。

这里有一个光谱：极端的一头是自动模式出现之前，每改一处都要按回车批准——一百个标签页里，大部分是一行的小改动，偶尔有一处让你庆幸“还好我在看”。另一头是让 Agent 全权做主，每行 PR 都由你逐行审——没人真的这么干过。演讲者的答案是：只设少数几个高信号的关卡。就像代码评审只看功能测试是否通过，在此之前可以大致放过；但没有通过全部测试的东西，绝不推上生产。

■ 问责关卡（Accountability Gate）：人必须亲自拍板的高信号检查点；设得太多会变成低信号的噪音，设得太少等于把责任交给了随机性。

Claude Code 里可以调节“你想参与多深”的功能被当作类比：造金融脚手架时，同样可以引导用户参与到同样的程度。关卡必须与用例匹配：有些值可以让 Agent 自己定，比如有几个可能的值，就让它做三个场景，但决定之前你要并排审过；但你不会把王国的钥匙整个交给一个你未必信任它会为你着想的东西——坏决定会带进下一个决定。所以关卡设在哪里，取决于你对用例有多了解；否则就是“每个决定之前都问我”，信号又低回去了。代码则不需要问：测试自己会说话，有了收据，你只需确认全部通过，就能有很大的信心。

婚礼计划的问责设计其实很克制：唯一的关卡是最后一步——“我会检查算过的一切、全部场景，然后决定每月需要存多少钱”。钱没有离开银行账户，但这道关卡足以挡住其他一切。另一道机制藏在计划图的结构里：图不是直线，而是有分支、再汇合的树。每个决定都可追溯是谁做的——是 Agent 假设的、你放行了，还是你给过修正输入。聊天中途改主意、补上下文是正当权利，好的脚手架要允许你安全地纠正路线，而不是一句话就让整个分析消失——这种事演讲者说自己经历过很多次，比如对着手机口述时中间插了一句，整个分析就没了，因为没法只撤回那一句话、其余保持原样。

分支对话是同一思路的延伸：点开第五步，可以开一个分支——一个真正独立的旁支，而不是混进主上下文的闲聊。演讲者拿 Claude 里的旁支功能作对比：有时管用，有时不管用，而且你没得选，它总会变成上下文的一部分。而在这里，分支可以汇合回主干并改变计划，也可以被驳回——有些对话本来就不影响流程，你最清楚这一点。设计反馈机制时，要按你真正想用的方式来裁剪它。

7. 原则五 · 验证：第二双眼睛，但不接管责任

最后一条原则是验证：你需要第二双眼睛。它建立在问责之上，因为评审的责任仍然在你身上。演讲者先讲了一个正在发生的现象：随着 Agent 写的东西越来越多， correctness 的负担落到了评审者手里——你拿到一堆看起来大致正确的东西，最终却要由你保证它正确。这很打击士气。验证的意义就是多建反馈环、不留盲点，但不把任何问责推给别人：它只是来自另一个来源的额外信息，帮你避开偏见、避开困在自己的思路里。

“Experts do not check every cell.”专家不会逐格检查。

金融与数据团队的专家通常不会逐格检查。他们打开电子表格，看几个能给出大致总数的格子，感觉不对就会说出来——“我们怎么会在营销上花了这么多钱？这不对吧。”这是一种直觉，不需要重做整个计划、不需要挑战每个决定，但你确实需要一个独立的参照点。演讲者举了一个流传很广的例子：有人发帖说马斯克有几万亿美元，可以给世界上每个人一百万美元还剩很多钱；读起来似乎合理，再想想就不对了——你得去查他算的账。这就是“感觉不对”的价值：有个东西帮你审一遍、给一个粗略答案，或者在不对劲时提出挑战，极有帮助。

验证的原材料之一是黄金示例：已知正确答案的对照样本，告诉你流程是否走在正确的空间里。但黄金示例也有自己的偏见——它们是你按你的领域挑的。演讲者讲了自己做 BI 分析师时的经历：查询写得很好，数字看起来合理，检查了一切都没问题；给业务方一展示，对方立刻说“这不对”——对方来自另一个团队，凭直觉知道那年销售额大概是多少，所以这个数字不可能是对的。只凭自己的黄金示例，你永远发现不了这一点；换一个相邻的领域看一眼，不用重算，就知道错了。

■ 黄金示例（Golden Example）：已知正确答案的对照样本，用来校验流程是否走偏；但它自带选择偏见，不能替代外部参照点。

■ 薄切片（Thin Slicing）：专家凭领域经验对少数关键数字的直觉校验——感觉不对，就是一个信号。

这个概念在演讲里叫薄切片：你凭零散的经验知道什么感觉对、什么感觉不对；模型只有所有人经验的平均值。所以脚手架需要一个反馈机制，让你能从你的经验出发，告诉它这看起来完全离谱还是大致合理——有时候“看起来大致正确”还不够，因为你的团队可能在乎那 5% 的差别，而这 5% 会决定整个方案的成败。没有这个参照点，你的脚手架也不会有。

演示里的验证节点就长在决策树上：一个独立的评审 Agent 被指派去审计划、审假设，做一番健康的挑战——“这读起来合理吗？”它可以汇合回主干并改变计划，也可以被驳回。演讲者特意区分了这一点与“LLM 当裁判”的做法：如果评审之后没有反馈环，金融决策或任何决策都不会因此变好。评审只是设计的一部分，品味在于把它做成适合用例的样子。

8. 收束：何时造脚手架，何时不用

五条原则讲完，演讲者把框架留在屏幕上总结了一遍：共享领域、一致性、拿出收据、守住问责、再加上有意的验证循环——这是造一个能托付金钱、值得信任的脚手架的框架。然后问答把话题推向了更实际的问题：什么时候该造一个新的脚手架？

答案是没有标准答案。光谱的一头是把一切都交给 Claude Code 或 Codex，用技能与指令包办一切；另一头是每遇到一件小事就从头造一个脚手架——那样你花在造工具上的时间比用工具还多。判断标准有三条：用例是否值得、可复现性是否重要、以及你是否反复发现现成的脚手架总在出错。对非关键任务，让人在回路里审输出、多走几轮也无妨；但如果是五十个信贷分析师用它支撑公司关键决策，你绝不希望结果有那么大的方差。金融用例之所以适合这套配方，是因为利害攸关、反馈环多；换成用 AI 批量生产短视频发 Instagram，证据收集、验证与问责就没那么重要了——配方是为信任系统准备的，不是对所有用例都适用。

另一个问答关于多 Agent 分工：要不要为婚礼配一个餐饮 Agent、一个场地 Agent？Francesco 承认，他自己用的就是最贵的 Claude 订阅，而且用到了上限——他让 Agent 调研了马德里的摄影师前五名、比价甚至联系对方，这类事“好得惊人”。但遇到更细微、需要控制与可预测的财务规划，他发现自己需要更结实的东西。最疼的一次是开车时用语音模式：来回一小时的车程，同一段对话他重复了三遍——每次做到财务相关的规划，总有地方出问题。研究清单可以交给一群 Agent；算钱的事，他要一个不会反复算错的东西。

技能与脚手架的边界也被追问到了极致。演讲者的区分很直白：技能与提示词方法，本质上是把一堆组织得很好的指令交给机器，再希望它照做——“请按这些做、请不要出错、拜托拜托”。Agent 如今够好了，99% 的时间会照做；但那 1% 的边缘情况呢？分发给内部用户时，某个用户的个人指令文件里有一条与你的指令冲突的内容，又怎么办？Monzo 内部有一个 Agent 扩展的共享机制，各团队可以分享好用的插件与技能；评审指令时，他们经常发现要补上一句“如果用户想这么做，请告诉他这个技能不支持”——而确定性代码把这些情况天然地覆盖掉了。他的经验法则是：先加几个技能、几条命令试试；还不行，发现自己在不同聊天之间复制粘贴、反复开新会话，那就值得造一个脚手架——把重复了三五次的事，设计一次，造进去。

最后一个追问关于如何向领导交代：领导一听说用了 AI，就会要求 200% 正确，仿佛 AI 出现就意味着零错误。演讲者的回答是把讨论拉回结果：我们要什么结果？用什么衡量成功？是减少与 BI 团队的来回，还是减少“数字看起来不对”的内部工单？如果能追踪这些结果，手段本身就不那么重要——AI 只是更快、护栏更好的工具。信任的对象不是 AI 的实现，而是我们要驱动的结果。金融归根结底是一门混合手艺：一部分必须 100% 可靠地运行，中间又夹着大量的解读与创造自由——会计的创造性正在于此，现金流的归属差一个月，账就全变了。

“Better models still have to earn trust.”再好的模型也要赢得信任。

演讲的收束回到标题：别再跟电子表格聊天。脚手架的设计必须是有意的，为的是增加信任——不要以为跑在 AI 上就会 200% 准确，除非你把所有机制都设计进去，让你能在一定程度上信任结果。模型在过去六到九个月里进步快得让人眩晕，但它们仍然要赢得信任；谈到钱的时候，1% 的错误也是很多钱。信任也不是一件单一的东西：对有些人来说验证最重要，有些人更怀疑、想亲眼看到实际的计算与数字——流程的意义在于，它引导并覆盖了多种可能性，而不是只给一种答案。

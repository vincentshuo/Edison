一年 40 倍：Cognition 的软件工厂

40x More Merged PRs With 2.7x the Engineers — Walden Yan, Cognition

Speaker: Walden Yan, Co-founder & CPO, Cognition

Event: AI Engineer Code Summit 2026

Length: 14 分 07 秒

Source: youtu.be/U92J5mCDLMc

Technical Monograph · 精读报告 发布 2026 年 11 月 18 日 生成 2026 年 11 月 19 日

十四分钟的演讲，只讲一件事：Cognition 怎样在一年里把合并 PR 做到 40 倍，而工程师只多了 2.7 倍。联合创始人兼首席产品官 Walden Yan 的答案不在模型本身，而在一套叫"软件工厂"的打法——默认让 Devin 从 Bug 报告一路跑到合并、监控与维护，人只在需要判断时出场；团队拆成两三人的小 Pod，纵向包揽从客服 Bug 到 QA 的一切；全部服务搬到本地、虚拟机每小时重建；Agent 每天反过来优化工厂本身；最后把"任务"换成"工作"，直接给 Agent 一个目标，让它自己定 KPI、拆任务、每天汇报。从 Vera Rubin 新卡上的推理调优，到 44 天里几乎无人过问的 Android 应用，Yan 的收尾只有一句：限制团队的不是工具，是野心。

Key Takeaways

  1. 默认自动驾驶，人工只做判断。从 Bug 报告到合并、监控与维护，整条开发流程默认由 Devin 跑完；人只在需要判断的地方升级出场，流程本身不再等人。
  2. 团队按纵向重组，两三人一个 Pod。不再按职能分工，而是按业务纵向——计费、移动应用、集成——每个 Pod 对产品、QA 与客服全权负责，配一群 Agent 干活。
  3. 先改基建，再谈 Agent。全部服务本地可跑、第三方服务全部 mock、虚拟机每小时重建、Agent 自己写测试技能；不改建造方式，买 Agent 也快不起来。
  4. 给 Agent 工作，而不是任务。把"P99 延迟降到 500 毫秒"这样的目标交给它，让它自己定 KPI、拆任务、每天汇报；人类只收更新，不再写提示词。
  5. 野心是唯一的上限。从 Vera Rubin 推理调优到 44 天养出一个 Android 应用，循环一旦搭起来，限制团队的就只剩下敢不敢想。

1. 开场：一年 40 倍的合并 PR（约 0:00–1:42）

Walden Yan 是 Cognition 的联合创始人兼首席产品官。Cognition 是 Devin 背后的公司——Devin 是 2024 年 3 月亮相的自主软件工程 Agent，能从规划、写代码、测试一路做到提交 PR。Yan 开场先报成绩单：过去大约一年，Cognition 的合并 PR 数量涨了 40 倍；同一时期，工程团队人数只涨了 2.7 倍。按他的算法，每个工程师的生产力提高了 10 倍以上，而且 PR 的质量"不降反升"，至少不比一年前差。

幻灯片上的柱状图把这句话画了出来：2025 年 11 月为 1 倍，之后逐月爬升，2026 年 10 月达到 40.4 倍；底部一条不起眼的虚线是工程人数（研发口径），同期只爬到 2.7 倍。Yan 说，这场演讲的主题就是：到底做了什么，才解锁了 40 倍的工程吞吐。而且他强调，接下来的每一步都很具体，别的团队照着做也能复现。

他先问台下：有多少人听说过"软件工厂"。这是一个老词——把软件开发当作一条流水线来经营。Yan 说，他要从最基础的讲起，再一路讲到最前沿的东西。

■ Devin：Cognition 的自主软件工程 Agent，能独立完成从规划、写代码、测试到提交 PR 的全过程，人类只做评审；本次演讲里它是全部流程的执行者。

■ 合并 PR（Merged Pull Request）：经评审后并入主分支的代码变更请求；Yan 用它衡量团队的交付量。

2. 默认自动驾驶：软件工厂（约 1:42–2:31）

软件工厂的基本想法只有一句话：默认情况下，一切都应该自动驾驶。Yan 的原话是，Cognition 的 PR 从最初的 Bug 报告到最终合并，再到监控与维护，全程可以没有任何人类参与——当然，很多时候确实需要人的判断，那时就会升级；但默认状态是，整个开发流程由 Devin 从头跑到尾。

“By default, our entire development process is just run by Devin from end to end.”默认情况下，我们整个开发流程就是由 Devin 从头跑到尾。

幻灯片把这条流水线画成六站：分流（Triage）、构建（Build）、测试（Test）、评审（Review）、部署（Deploy）、值班（Oncall），每站下方都有一个 Devin 的标记，意思是每一站都由 Agent 执行，人在需要判断时才介入。这句话的另一面是，软件工程师的角色必须跟着变——这是下一节的主题。

■ 软件工厂（Software Factory）：把开发流程当作一条默认自动驾驶的流水线来经营；Bug 报告进、合并与监控出，只在需要人类判断时升级。

3. 小 Pod，纵向负责：工程师的角色变了（约 2:31–3:16）

2026 年 3 月，Cognition 内部开了一次会，结论是：如果一个工程师现在的工作还是从 Linear 看板上挑一张票，扔给 Agent 去实现，那他在 AI 时代不会有好结果——因为任何能被描述清楚、能被实现的东西，都可以交给 Devin。所以每个人都必须换一种开发方式。

执行办法是把大团队拆成小 Pod。每个 Pod 只有两三名工程师，但责任比以前大得多：不仅配了一群 Agent 替他们干活，还要对纵向的一切负责——听客户的 Bug 报告、做 QA 测试、做产品管理；基本上每个工程师管理自己的整块 Linear 看板，再把上面的事交给 Agent 去实现。幻灯片的对比很直观：以前按职能分工，产品、工程、QA 各是一拨人；现在按业务纵向分工，计费、移动应用、集成各成一个 Pod，每个 Pod 下面都挂着一群 Devin 的标记，产品、工程、QA 与值班全包。

Yan 说，这是过去一年里最关键的变化之一，而且 Cognition 也在帮很多大组织照着这个样子改。角色转变的另一面是工作方式的转变：整个开发流程搬到了 Slack 上。

■ Pod：两三名工程师组成的小团队，按业务纵向而非职能分工，对产品、QA 与客服全权负责。

■ Linear：Cognition 内部用的任务看板工具；工程师在上面管理自己的全部待办，再交给 Agent 去实现。

4. 全程 Slack：不用打开 IDE（约 3:16–4:46）

Yan 举了一个客户 Bug 报告的例子。客户在 Slack 上发来一段视频，他直接把报告转发到内部频道，@ Devin 说一句"请修一下"。Devin 马上交出 PR，还附上一段视频，证明修好了——整个过程 Yan 不用离开 Slack，大多数时候连 IDE、甚至 GitHub 都不用打开。

这就是他说的终点状态：整个开发生命周期，不用打开 IDE，也不用打开任何一个编程 Agent。开发被抽象成了证据与视频：修好的证明直接发回给客户。但他马上转折：要走到这一步，底下有大量基建要改，而这正是每个工程团队想做到这一步时最难的部分——不是买一个编程 Agent就够了，得改变建造软件的方式。

“It's not just you purchase a coding agent, you got to go change the way you build.”不是买一个编程 Agent 就够了，你得改变建造软件的方式。

5. 先改基建：全部服务本地跑，每小时重建的虚拟机（约 4:46–7:05）

以前 Cognition 的测试对着云端部署：预发布环境、预发布数据库、线上服务器，工程师手动点一遍流程，确认端到端能跑通。改法是一次大迁移：让每一个服务都能用 Docker Compose 在本地跑起来，所有第三方服务都有能在本地跑的 mock 版本，全部装进一台每个开发者都能访问的虚拟机。从此公司里的每个编程 Agent 测试改动时，完全不需要碰任何线上服务。

而且这些虚拟机每小时重建一次：每小时拉最新代码，从头把整个代码库重建一遍，保证随时能从零快速跑起来。如果构建因为代码库变化太快而失败，Devin 就是第一响应者，立刻去修这些虚拟机快照。于是每次从 Slack 启动一个 Agent，它去到的都是一台全新的机器、最新版本的代码库。

还有一件事得教 Agent：怎么测试你的代码库。好在云端编程 Agent 的好处是能自我维护训练循环——Devin 会自己写技能，记录怎么测这个代码库；代码库会变，测试方法也会变，Devin 就不断更新这些技能，反复去测。最终结果是，人们真的不需要再打开笔记本电脑去测试任何代码改动——Cognition 已经有好几名工程师改用 iPad 做开发。

顺带一提，iPad 还更安全。Yan 说，最近很多安全事件都是 DevOps 与密钥泄露闹的——谁知道你的开发机上散落着多少密钥？当一切都在云端、都在受控的虚拟机里，反而处在更安全的位置。更复杂的测试也能做：开发 Devin 加入语音与 Zoom 通话的能力时，他们让 Devin 在测试里创建多个账号，从同一台虚拟机加入同一个 Zoom 通话、互相发语音备忘录，验证功能是否正常。

■ Docker Compose：用一个配置文件定义并运行多容器应用的工具；Cognition 借此让全部服务在一台虚拟机里本地跑起来。

■ SKILL.md：Devin 为代码库写的测试技能文件，记录"怎么测这个库"；代码变了，技能也由 Devin 自己更新维护。

6. Agent 优化工厂本身：递归自我改进（约 7:05–7:50）

在这一切之上，还有递归自我改进。人们常从模型角度想这件事，但 Yan 说：每一行写出来的代码、每一个生成的 PR、每一个决定，在云端 Agent 的 setup 里都是全程可追踪的——那为什么不也在上面跑 Agent，做数据分析，找出哪里在浪费时间、浪费 Token、哪些东西可以变成脚本、该加什么测试？Cognition 有一个频道，Devin 每天在里面贴想法：改一下 Node 的配置，CI 能省一分钟；改一下 lint 脚本，能在到达 AI 代码评审之前多拦住 20% 的 Bug。

一张幻灯片的标题就叫"Recursive Self-Improvement for Agents"，上面标着 1,289，并举了一个例子：登录流程的计算机操作在 80% 的测试里重复出现，存为技能后，测试时间缩短了 31%。Yan 说，这是巨大的解锁——把这些系统搭起来，Agent 自己就会去优化你的软件工厂。

7. 给 Agent 工作，而不是任务（约 7:50–10:09）

接下来是 Yan 认为没什么人谈、但代表未来方向的一步：从给 Agent 派任务，转向给 Agent 派工作。这是一个范式转变——得开始把这些东西当作同事来对待。

给 Agent 一份工作是什么样子？假设他关心后端性能。未来的开发流程应该是这样：你对 Agent 说，我想改善应用的 P99 延迟。它不应该等你告诉它怎么做，而应该自己说：好，P99 延迟，我先加埋点，看看今天的 P99 在哪里；设好告警，弄清将来要到哪里；把要做的每一项任务拆出来；建 DataDog 告警；每周在 Slack 出报告；每天在手机上告诉你 P99 在哪里、改善了多少。幻灯片把这个循环画成四步：人类表达愿望（"把 P99 端点延迟降下来"）→ Devin 定义目标与 KPI（从 840 毫秒降到 500 毫秒，批了 5,000 个 ACU）→ Devin 扫描并创建任务（14 个 issue：批量查单、补缺失索引、P99 超过 1 秒就告警、周报）→ Devin 监控并汇报（手机上弹出：P99 下降 65%，没有回归）。

“We don't even want you to be prompting your agents most of the time. We want you to just be giving your agent goals that they can work toward over long durations of time.”我们甚至不希望你大部分时间都在给 Agent 写提示词，我们希望你直接给它目标，让它朝着目标长期工作。

Yan 的建议是：公司里任何你觉得不可衡量的东西，想办法把它变成可衡量的。关心应用性能？去量点击延迟；布局跳动多？去量 bounding box，想办法把布局偏移压到最小；还有 P99 延迟、入职留存率。工程师做的事里，有多少能归结为一个数字、一个指标？如果能归结，就应该设一个 Agent，让它 24 小时不停地去优化这个数字。

■ P99 延迟（P99 Latency）：99% 的请求都快于这个耗时；衡量尾部体验的关键指标，Yan 拿它做"给 Agent 一份工作"的例子。

■ ACU（Agent Compute Unit）：Devin 的算力计费单位；目标定下来后，Yan 直接批了 5,000 个 ACU 让它去花。

■ TPM（Tokens Per Minute）：每分钟输出 Token 数；Yan 用它衡量新 GPU 上的推理吞吐。

8. 两个实例：Vera Rubin 推理调优与 44 天的 Android 应用（约 10:09–13:13）

第一个实例是推理延迟。Cognition 有幸成为 NVIDIA 新一代 Vera Rubin GPU 的首批拿到者；拿到卡的时候，还没有现成的 kernel 能跑在这批新硬件上，得从零搭自己的推理栈。做法还是那一套：只给一个高层目标——我们在乎这批 GPU 的吞吐（TPM），去把它推到极限。Agent 分到了一组固定的 GPU，大约用了一周，找出不同的策略、逐一测试，效果最好的送给人类工程师做最终批准。幻灯片上的折线图显示，9 月 18 日到 26 日，单卡输出从约 1 万 TPM 一路爬到 27,336，超过了 GB300 最好成绩 17,185，更是 GB200 最好成绩 8,471 的三倍多；右侧列着 9 行——起步状态之外是 Agent 找到的 8 项改动：合并 GPU 间步骤（+15%）、批量草稿模型猜测（+16%）、分组传入提示（+20%）、预录 GPU 任务（+7%）、一次跑更多对话（72 路，+9%）、更多显存、更少等待（96，+20%）、更快的显存时钟（+8%）、自动调优（120，+16%）——每一项都附带百分比。Yan 说，这一切都是只给一个终点目标换来的。

第二个实例是 Android 应用。Cognition 的工程团队不大，常常没有人力去做想做的事——比如一个 Android 应用。但团队里一位叫 Samuel 的工程师出了个主意：iOS 应用已经做得很好了，能不能拿它当蓝图，让 Devin 去维护 iOS 与 Android 之间的对等？他做的不是开一次 Devin 会话了事，而是设了永久钩子，监控 iOS 应用、监听 Slack 频道里的用户反馈、递归改进应用、对每个细节做 live QA。44 天后，一个能用的应用做出来了，即将上线。时间线显示，大多数日子里人类没有给这个 Agent 发过一条消息；而在那些日子里，它每天合并 40 到 50 个 PR，全部对着 iOS 应用逐像素做 live QA 测试，只把最重要的决定升级给人类。到最后，人类在这个循环里几乎什么都不用做——Yan 还展示了人类在整个过程里到底给 Agent 发了多少条消息，答案是少得惊人。而且他强调，这不是一个凑合的应用，是真的要上线的东西。

■ Vera Rubin：NVIDIA 在 Blackwell Ultra（GB300）之后的下一代 AI 平台，2026 年下半年开始向合作伙伴出货；Cognition 称自己是首批拿到者。

9. 收尾：野心是唯一的上限（约 13:13–14:07）

演讲的结尾只有一句话：如果把 Agent 的循环搭对了，能做出相当了不起的事。所以大多数团队真正受限的，是野心的多少。Yan 说，是时候雄心勃勃了。

“Most teams are limited by the amount of ambition they have. So it's time to be ambitious.”大多数团队受限的，是野心的多少。所以，是时候雄心勃勃了。

回过头看，整场演讲的逻辑是一条链：先有"默认自动驾驶"的目标，再有小 Pod 的组织，再有 Slack 的工作方式，再有本地化与每小时重建的基建，再有 Agent 自我优化的循环，最后才到"给 Agent 工作"的范式。每一步都在为下一步铺路，而每一步的收益都建立在前一步已经完成的前提上——这也是 Yan 反复提醒的顺序：不是买一个编程 Agent 就够了，得先改变建造软件的方式。

先选边界，再选框架：框架们唯一达成一致的事

The One Thing Every AI Agent Framework Agrees On

Speaker: Mislav Ivanda, Daytona

Event: AIE Code Summit, New York

Length: 15 分 35 秒

Source: youtu.be/WWIFiQi9U4w

Technical Monograph · 精读报告 发布 2026 年 11 月 9 日 生成 2026 年 11 月 17 日

Daytona 的开发者体验工程师 Mislav Ivanda 过去一年把沙箱接进几乎所有主流 Agent 框架、编程 Agent 脚手架与工作流工具，途中反复撞见同一个模式：各家框架的标志不同，接入代码却几乎一模一样——创建沙箱、在里面跑代码、删除沙箱，三行。框架们在 Agent 的定义、实现语言与行为归属上什么都谈不拢，却在这件事上一致。本报告按演讲顺序还原三层隔离的比较——本机白名单、嵌入式运行时与另一台电脑；再看 CrewAI、AG2、Claude、OpenAI 与 Mastra 如何删掉本地执行、只留沙箱；最后是选型建议：框架、模型、提示词与供应商都能换，换不掉的是执行边界，先选边界，再选框架。

Key Takeaways

  1. 框架们只在一件事上达成一致：Agent 的代码要在沙箱里跑；接入形态不同，骨子里都是创建、运行、删除三行。
  2. 许可不是隔离：白名单管的是模型该用什么，不是它能用什么；一条 python -c 就能开 socket、改文件系统。
  3. 隔离胶水代码不等于隔离工具调用：嵌入式运行时里的发邮件、查数据库，实际跑在本机上。
  4. 框架、模型、提示词与供应商都能换；换不掉的是执行边界，它决定整个架构与每一件工具怎么写。
  5. 先选边界，再选框架：边界是承诺，不是偏好；本地起步的原型一路走到生产，出事时往往已经太晚。

1. 开场：给模型一台电脑

演讲者先自我介绍：Mislav Ivanda，Daytona 的开发者体验工程师。过去一年，他的主要工作是把 Daytona 接进一切沙箱说得通的地方——Agent 框架、编程 Agent 脚手架、工作流工具与开发者产品。Daytona 本身就是一家沙箱服务商。

■ Daytona：提供沙箱的服务商；演讲者所在的公司，本场演讲的出发点正是把它的沙箱接进各家框架的经历。

在这个过程中，他反复撞见一个模式，让他停下来想了一阵，最终有了这场演讲。他先请观众帮个忙：下一页上是一段接入代码，谁能猜出这是哪家框架？

2. 一道猜不出答案的题

幻灯片上只露一段接入代码，问题是：这是哪家框架？台下有人猜 LangChain，有人猜 LangGraph，也有人猜 Google ADK。演讲者的回答是：说什么都对，也都站得住脚。

因为 Daytona 接进这些框架的代码几乎无法区分：有的接成工具，有的接成可安装的外部插件，有的扩展沙箱客户端类、走框架内部 API——但骨子里讲的都是同样的三行。

“Different logos. Same three lines.”标志不同，三行代码相同。

三行是：sandbox = daytona.create()——一台电脑出现；response = sandbox.process.code_run(code)；sandbox.delete()——然后消失。六种接入形态一一列在幻灯片上：LangChain 接成 tools=[DaytonaDataAnalysisTool()]，CrewAI 接成 tools=[DaytonaExecTool()]，Google ADK 接成 plugins=[DaytonaPlugin()]，Pydantic AI 接成 capabilities=[DaytonaSandbox()]，OpenAI Agents SDK 接成 client=DaytonaSandboxClient()，Mastra 则是 tools: { createSandbox, runCode, … }。

这很奇怪，因为这些框架是竞争对手，在基本概念上几乎什么都谈不拢。分歧有多大，下一节就讲。

这三行就是整场演讲的线索：框架们什么都能争，唯独在这里收敛到同一点。

3. 框架们什么都谈不拢

先说分歧有多大。Agent 是什么？LangGraph 说是一张可遍历的图；CrewAI 说是一群各自干活的角色扮演 Agent；OpenAI Agents SDK 说是绕着 LLM 的循环；Claude Agent SDK 直接给一个成品，拿来就用，不用定制。

实现语言也不同，主要是 Python 与 TypeScript。谁来规定 Agent 的行为，也不同：在 Mastra、LangGraph 里，你显式定义工作流与轨迹；到了 CrewAI，Agent 自己决定怎么做以达成目标。

所以，当这些在什么事上都谈不拢的公司在一件事上达成一致，那恐怕不是时髦，而是一种必需。必需从何而来，下一节回答。

4. 代码必须在某个地方运行

为什么一致？演讲者的解释是：只要你用 AI Agent 做点有用的事，迟早会走到 Agent 需要执行代码、需要 shell 访问的那一步。下一个问题随之而来：这件事发生在哪里，什么执行环境？

大致有三种隔离方式，从最基础的一种开始。

4.1 第一招：本机白名单

最基础的一种，也是本地开发时最常见的：定一份允许运行的命令清单，加上审批提示，再加拦截钩子。审批提示就是 Claude 问你的那句“你确定要运行这条命令吗？”演讲者说，问题在于，大多数人只是点“是”，根本不读它要干什么。

■ 允许列表（Allowlist）：事先划定的可运行命令清单；超出清单的命令不被放行。

■ 审批提示（Approval Prompt）：执行敏感命令前向人确认的弹窗；演讲者指出，多数人看都不看就点通过。

■ 拦截钩子（Interception Hook）：在命令执行前插入检查的钩子；与白名单、审批提示同属第一招的手段。

更深的问题在语义上：你规定了模型应该用什么，却没规定它实际上能用什么。一条 python -c 就能开 socket、改文件系统、执行代码——做一切你没想过的事。模型一旦被攻破，你等于给它开了后门，在你的本地设备上跑恶意命令。

“A permission model is not isolation.”许可模型不是隔离。

这还只是第一招的代价；第二招看起来更高级，毛病也更隐蔽。

4.2 第二招：嵌入式运行时

更高级的做法是把代码执行放进 V8 或 QuickJS 这类嵌入式引擎运行时。好处是确实有了一定的网络与文件系统隔离，看起来像是把执行关进了笼子。

■ 嵌入式运行时（Embedded Runtime）：V8、QuickJS 这类嵌进宿主进程的脚本引擎；代码在其中执行，与宿主有一定隔离。

但古怪之处更微妙：Agent 生成的 Python 脚本会调用工具——查数据库、发邮件——而这些工具实际运行在运行时之外的你的设备上。恶意 Agent 不必直接动手，通过工具就能动手。

“It isolates the glue, not the tools.”它隔离的是胶水代码，不是工具调用。

你隔离的是 Agent 生成的胶水代码，不是真正的工具调用。举例：如果有个删除数据库的工具，麻烦就来了——脚本在笼子里，删除却发生在笼子外。

4.3 第三招：另一台电脑

第三招，也是推荐的做法：用一台单独的电脑或虚拟机。通过 API 与它交互、控制它的生命周期、在里面做任何事。这台虚拟机从不碰你的本地基础设施、网络与文件系统。

■ 沙箱（Sandbox）：与宿主隔离的执行环境；这里指一台独立的电脑或虚拟机，Agent 的代码只在其中运行。

好处写在幻灯片的最后一行：一步被攻破，不等于整个应用被攻破。前两种做法里，工具调用一失常、Agent 一失常，攻破的那一步就是攻破整个应用；在这里，地球上最坏的代码也能在沙箱里跑，却碰不到你的应用逻辑。

“A compromised step is not a compromised app.”一步被攻破，不等于整个应用被攻破。

沙箱用完就扔，再开一个。这就是第三招的全部底气：隔离的单位不是一条命令、一段脚本，而是一整台电脑。

5. 框架们已经投票了

演讲者说，他不是在空谈，框架的动向就是证据。2026 年 4 月，CrewAI 移除了代码解释器工具——原来在本机上执行代码的那件工具，文档现在指向专用的沙箱服务。

AG2 在 1.0 里退役了旧的本地代码执行器，新的 SandboxCodeTool 没有默认后端，环境是必填参数。Claude Agent SDK 默认用沙箱——不过是进程级沙箱，比如 Linux 上的 bubblewrap；对不可信代码，官方指引是一台专用的虚拟机。

OpenAI Agents SDK 自带 SandboxAgent，原生支持沙箱服务商与 Docker，但也允许本地执行，并把这种做法的缺陷明明白白列出来；Mastra 类似。Mastra 的文档更直接写着：你必须有意地选择它的执行边界。

“You must choose its execution boundary deliberately.”你必须有意地选择它的执行边界。

演讲者特意纠正一种误读：框架们不是在加沙箱——它们本来就有沙箱；它们在做的是删掉所有的替代品。

“They're not adding sandboxes. They're deleting the alternatives.”他们不是在加沙箱，而是在删掉替代品。

6. 沙箱的用法也在变

与此同时，沙箱本身的用法也在变。起初沙箱是短命的机器：Agent 按需开一台、跑一段代码或一个任务、关掉。

模型变强之后，人们发现可以把整个 Agent 搬进沙箱当作执行运行时：文件系统、网络调用，什么都有。幻灯片分三步：先是一次工具调用；然后 Agent 搬了进来——代码 Agent 住在里面，有自己的文件与进程、有它读不到的机密、有网络策略；最后，一台电脑变成了一千台。

一千台同时跑，能做的事就变了：并行评估、强化学习 rollout、跨仓库批量重构、Agent 生成子 Agent。演讲者还列出强化学习、微调、事后训练与基准测试——沙箱从执行代码的地方，长成了训练与评估的基础设施。

“Then one computer became a thousand.”然后，一台电脑变成了一千台。

这场迁移让演讲者回到了一个老问题：到底该选哪个框架？

7. “选哪个框架”是问错了问题

这是演讲者自己、也可能是很多观众常被问到的问题。他的结论是：这个问题本身就问错了。因为拿来比较框架的大多数东西，都能换。

幻灯片把能换的列在左边：框架本身——同一种语言里，让编程 Agent 做一次重构就能换，开发者天天这么干；模型与提示词——对特定模型微调过系统提示词会麻烦些，需要再微调与回归测试，但完全做得到；缺失的功能——现在可以直接 vibe code 一个，或以外挂插件接上；评估、追踪与记忆也一样，要么自己实现，要么接外部工具；沙箱供应商也能换，因为大家讲的是同一种语言：创建、在里面跑、删除。

7.1 能换的，和换不掉的

例外只有一个：持久执行——有些框架提供的这项能力不容易复制，一个下午 vibe code 不出来，因为它牵动架构。但除此之外的评估、追踪与记忆，都能自己实现或接外部工具。

■ 持久执行（Durable Execution）：跨越中断仍能续跑的工作流能力；演讲者认为它是唯一不容易现拼的功能。

■ 评估（Evals）：对 Agent 输出打分的测试集；可自建或外接工具。

■ 记忆（Memory）：Agent 跨会话保留的上下文；与评估、追踪一样可自建或外接。

真正换不掉的是执行姿态：代码是在本地跑，还是在外部沙箱里跑。它决定整个系统架构，也决定其他部分怎么写——如果你一开始假定一切都在本地跑，你写的每一件工具都会直接用宿主或应用进程的环境、用没有隔离的文件系统。

问题在于，大多数人以本地起步做概念验证，却一路走到生产，再也不回头改。等坏事发生，往往已经太晚——而他说的坏事，有时真的能要了产品的命。

8. 收束：先选边界，再选框架

所以演讲的建议是：先选执行边界，再选框架。边界决定架构，框架只是观点。

“Pick the boundary before the framework.”先选边界，再选框架。

最后一页只有两行字：框架是观点，边界是承诺。演讲者希望观众带走的就是这一句：框架可以换，边界一旦定下，就跟着你走。

“Frameworks are opinions. The boundary is a commitment.”框架是观点，边界是承诺。

一场十五分钟的演讲，论证其实只有一条链：所有框架都把代码执行收敛到了沙箱；沙箱的用法从短命机器长成了整支舰队；选型时真正锁死你的是执行边界——在它之前，先想清楚代码在哪里跑。

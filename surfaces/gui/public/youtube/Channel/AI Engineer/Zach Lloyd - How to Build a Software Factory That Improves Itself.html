How to Build a Software Factory That Improves Itself

Zach Lloyd 是 Warp 的创始人兼首席执行官，此前在 Google 担任首席工程师，主导 Google Docs 套件做到数亿用户、如今超过十亿。他论证：多数公司仍停留在交互提示阶段——工程师在笔记本上用 Claude Code 或 Codex 与 Agent 一对一交互；而目标是自动化开发：把 Agent 与大模型部署出去，以最低成本拿到最多的业务价值，并且可治理、可审计。本地 Agent 的问题是双重的：安全上，一个被攻破的本地 Agent 能接管登录用户的全部权限；治理上，每个人自配 MCP、技能与工具，无人看得见、无从审计。出路是把 Agent 关进沙箱、搬上云端，建成云端软件工厂：人把工作放进去，Agent 完成分流、写规约、实现与计算机使用验证，循环往复。工厂要当作基础设施来建：开放——任何模型、任何脚手架；适配——与现有基础设施协同；以代码定义——整个工厂的定义版本化进代码库。主权同样关键：数据、算力与推理都要掌握在自己手里。度量则要回到自己的数据上：公开基准不可信，要用在线评分、自改进循环与自有基准来驱动改进。演示环节展示了 Warp 内部的 Wilson 工厂：管理者视图上，每份 PR 平均 16.6 次人工交互，中位周期从启动到合并 13 小时，七天 1,857 次运行；工厂定义藏在一个代码库里，factory.yaml 只有一页；评分器用大模型当裁判，冗余测试一项得分 100%；自改进循环把一处失败 37 次的毛病写成了 PR；WarpBench 0.1 的成本—质量图上，glm 5.3 flash 以 93% 的正确率、每次试验 1.99 美元成为最优选择，而 gpt-5.6-sol 的 94.8% 要花三倍的钱。收束的七层工厂栈自下而上是工厂即代码、数据与上下文、算力、推理、改进、编排与接入。

Key Takeaways

  1. 交互提示已到头，自动化开发才是目标。本地 Agent 瓶颈在人、成本难控、无法治理；目标是以最低成本、受治理的方式拿到 Agent 的全部业务价值。
  2. 把 Agent 关进沙箱、搬上云端。云端软件工厂是人与 Agent 的闭环：人把工作放进去，Agent 完成分流、规约、实现与验证。
  3. 工厂是基础设施，不是产品。开放、适配、以代码定义；版本化之后才能测试不同版本、让 Agent 自己改工厂。
  4. 主权与度量都要抓在自己手里。拥有数据、算力与推理；在自己的数据上评分、建基准，别信公开榜单。
  5. 改进来自闭环，不是来自换模型。在线评分发现失败模式，自改进循环把它写成工厂定义的 PR；WarpBench 证明便宜的模型常常够用。

1. 开场：交互提示的尽头

演讲者先介绍自己：Zach Lloyd，Warp 的创始人兼首席执行官。做 Warp 之前，他在 Google 担任首席工程师，主导 Google Docs 套件的工程，做到数亿用户，如今的使用者据他说已超过十亿。Warp 处在 Agent 开发领域，眼下最出名的是开源的 Warp Terminal，约 65,000 个 GitHub 星标、近一百万活跃开发者；当前重点则是帮公司搭建自己的内部软件工厂，产品叫 Warp Factories。公司的方向始终没变：帮开发者更快地交付更好的软件。

演讲先给现状定位：他接触的大多数公司处在交互提示阶段——已经把 Claude Code、Codex 这类工具发给了工程师，工程师在笔记本上跑 Agent，一次开好几个，交互式地提示它们写功能、修 bug。而这些公司想去的地方是自动化开发：把 Agent 与大模型这项变革性技术部署出去，以最低的成本拿到尽可能多的业务价值，并且全程受治理、可审计。

演进曲线把这条路画成四段：聊天、自动补全、交互提示（今天）、自动化开发（下一步）。演讲者的判断是，交互提示的天花板已经看得见：瓶颈是操作它的人，成本无人统一控制，治理更是无从谈起。想拿到 Agent 的全部价值，必须换一种组织方式。

2. 本地 Agent 的治理困局

演讲者把交互提示的限度拆成三条：第一，人是瓶颈，Agent 的速度受限于操作它的人；第二，成本难控，每个人各有一套配置，账算不到一起；第三，治理困难。第三条他展开讲了两面：安全上，本地 Agent 一旦出问题或被攻破，基本就能接管登录用户的全部权限；治理上，每个人自配 MCP、技能与工具，管理者看不见里面在发生什么，也审计不了。

幻灯片右侧的三篇报道把这种失控写得很具体：福布斯问，“Tokenmaxxing” 崇拜是新常态还是又一阵风；VentureBeat 写道，72% 的企业并没有自己以为的那种控制与安全；福布斯另一篇的标题是，Uber 四个月就烧完了 2026 年的 AI 预算。演讲者的结论是：用量越多不等于业务价值越多，缺的是自动化的系统、成本与质量的优化办法，以及统一的治理与控制层。

“Local agents are ungovernable agents.”本地 Agent 是无法治理的 Agent。

出路只有一条：把 Agent 关进沙箱、搬上云端。沙箱隔断了本地权限的接管风险，云端则让配置、运行与审计第一次有了统一的落点。顺着这个解法长出来的产品品类，就是演讲者所说的云端软件工厂。

■ 沙箱（Sandbox）：与宿主隔离的执行环境；把 Agent 关进沙箱再搬上云端，是切断本地权限接管风险的做法。

■ MCP（Model Context Protocol）：模型调用外部工具与数据源的开放协议；每人自配 MCP、技能与工具，是治理失控的来源之一。

3. 云端软件工厂：人机循环

演讲者对“云端软件工厂”这个已经被用滥的词给了自己的定义：每家公司都将在云端搭一个循环，人与 Agent 在里面一起工作。人负责把工作放进去，Agent 负责软件生命周期的各个环节——分流、与人一起写规约、实现、计算机使用验证。循环的走向是：新想法或故障上报后进分流，再过规约、实现、验证、发布与监控；人在规约、代码与产品三处评审。公司要做的，是在内部搭起这个循环、定好人与 Agent 交互的全部规则，然后持续度量、持续改进——因为把这个概念做对，是组织交付软件能力的关键驱动。

演讲者强调，工厂要当作基础设施来理解，而不是一个产品或一位 AI 队友——它是能往上搭建、可扩展的基础设施栈，有三个特征：开放、适配、以代码定义。开放是指工厂模型要支持不同的模型（开源权重或前沿模型皆可）与不同的脚手架，因为最好的模型与脚手架一直在变；适配是指工厂要与企业现有的基础设施协同工作；以代码定义是指工厂要有严格的定义，包括工作流、技能、MCP 与运行位置。

“Think of this as infrastructure.”把它看作基础设施。

以代码定义的好处是具体的：定义进版本控制之后，可以测试工厂的不同版本，也可以让写代码的 Agent 自己更新工厂。换句话说，工厂的定义本身成了可以被工程化对待的对象，而不是一份写在文档里的流程说明。

■ 云端软件工厂（Cloud Software Factory）：云端由人与 Agent 共同完成软件生命周期的人机循环；人把工作放进去，Agent 完成分流、规约、实现与验证。

■ 工厂即代码（Factories-as-Code）：整个工厂的定义（工作流、技能、MCP、运行位置）以代码形式版本化管理，可测试、可由 Agent 更新。

4. 主权：拥有自己的数据、算力与推理

演讲者说，另一个从企业客户那里反复听到的要求是 AI 主权：进出工厂的全部数据都要掌握在自己手里，Agent 要跑在自己的基础设施上，算力是自己的，推理也是自己提供的。幻灯片把这张清单列成四行：你的数据、你的算力、你的推理网关、任何模型、任何脚手架。背后的逻辑是保留选择权：模型与脚手架一直在变，工厂的核心要素——数据、算力、推理——应当掌握在企业自己手里，而不是锁死在某一家供应商身上。

“AI sovereignty matters.”AI 主权很重要。

演讲者说，这是他合作的大型企业普遍的要求：数据进出可控、Agent 跑在自己的基础设施上、算力自己拥有、推理自己提供，同时保留换模型、换脚手架的自由。对小团队这可能不是首要问题，但对把软件工厂当作核心业务基础设施的企业，它是立项时就要定下来的前提。

■ AI 主权（AI Sovereignty）：拥有进出工厂的全部数据、在自己的基础设施上运行 Agent、掌握算力与推理。

5. 度量优先与两种工程师

5.1 度量先于感觉

演讲者说，建工厂之前要先想清楚一件事：别信公开榜单。每天打开社交媒体，总有人说某个模型最好，Grok 或者别的；SWE-bench、Terminal-Bench 这类公开基准也只能说明模型在别人的任务上表现如何，说明不了它在你的工作流里好不好用。真正要去的世界，是在自己的数据上度量优先：给写代码的 Agent 打分，把分数喂给能改进工厂的 Agent，再用自己真实的编码任务搭基准集，在不同模型之间实测比较。

“You can’t really trust the public benchmarks.”公开基准并不可信。

度量优先意味着工厂模型必须自带三样能力：评分——也就是评估写代码的 Agent 做得怎么样；把评分喂给能改进工厂的 Agent；以及自建基准——把全部真实的编码任务拿出来，在不同模型配置下试跑并度量结果。这三样能力在幻灯片上就是“评分、自改进、基准”的对照，也是后半段演示的主线。

5.2 产品工程师与工厂工程师

工厂世界里，工程分工会变成两种。第一种是产品工程师：仍然负责给客户做有用的东西——写功能、修 bug、做产品工程，只不过是通过工厂来做：把工作放进工厂。第二种是工厂工程师：平台团队或普通工程师要擅长让工厂本身变好——改进技能、调整上下文、更换模型组合；随着工程师越来越多地建设与改进“造软件的系统”，这部分工作会越来越重要。

两种工程师的分工，决定了工厂的改进方向：产品工程师关心的是工作能不能流进工厂、结果能不能出来；工厂工程师关心的是循环本身——技能、上下文与模型组合。演讲者说，后一种工程会随着自动化程度加深而变得越来越重要。

6. 演示：看得见的工厂

6.1 管理者视图

演讲的后半段是演示，用的就是 Warp 自己的产品 Warp Factories，演讲者说其中的通用概念可以平移到任何人自己的工厂。第一个画面是工厂工程师或管理者的视图：想提高团队生产力的人，首先要看三样东西——工厂的自动化程度、周期时间（DORA 指标视角）与花费。实现这三个视图的前提，是团队的一切活动都被记录下来。

演示画面是 Warp 内部真实的开发数据，演讲者说这是在“泄露”自家的开发情况：他能看到每位工程师在做什么、所有自动化在做什么，不仅能看到它们产出的全部制品，还能点进某一次运行，看 Agent 与人的实际对话。重要的是，所有这些数据都被存下来了——Agent 的轨迹就是改进工厂的原材料。

仪表盘上的数字是 Warp 内部 Wilson 工厂最近七天（10 月 8 日至 14 日）的实况：每份 PR 平均 16.6 次人工交互；中位周期从启动到合并 13 小时，从启动到出 PR 40 分钟，从 PR 到第一次人工评审 2 小时，从第一次人工评审到合并 22 分钟；PR 共 310 份，其中 175 份已合并；运行总计 1,857 次，其中顶层运行 797 次，按执行 Agent 类型分为 Foreman、Code、Review、Triage、Spec 与 Custom。

工作进工厂的方式，是通过工程师本来就在用的工具：Slack、任务跟踪器（Warp 用 Linear，也可以用 Jira）、GitHub PR 评论。同样的上下文、同样的工具，但全部工作汇入一个中心位置，有统一视图，并随时间被完整记录下来。

6.2 工作流即代码

演示的第二部分是工厂工作流本身的定义方式。默认工作流里有一个编排器 Agent，负责判断下一步该走分流、写规约、实现还是代码评审；点进其中一步，能看到一份 Agent 定义：密钥、MCP、Agent 提示词、模型，全部列在里面。演讲者强调，真正关键的是这套界面背后有一个代码库：任何时刻，整个工厂的定义都躺在那个库里。

库里的 factory.yaml 只有一页：模式版本 v1alpha1，名字叫 wilson，描述是“为 Warp 代码库服务的自主软件开发工厂”；配置里写明工厂配置检查全部开启，列出所辖代码库与 Agent（foreman、factory-prototypes、implementation、code-review、spec、triage、design），文件树里还有 automations、benchmarks、runners、scorers、skills 与 webhooks。演讲者的意思是：工厂的定义包括 Agent 定义、自动化、基准、运行位置、技能与 webhook，全部进代码库，自动化才有抓手。

■ 编排器（Orchestrator）：决定下一步走分流、写规约、实现还是代码评审的调度 Agent。

7. 评分与自改进闭环

7.1 在线评分

回到管理者视图，除了生产力与花费，演讲者还展示了第三类视图：评分，也就是在线评估。系统里有一组 Agent，逐一看过全部运行记录，用大模型当裁判，判断每一次运行好不好。演示里的一项评分专门盯着写代码的 Agent 常见的失败模式：写了不需要写的冗余测试。大部分时间 Agent 表现不错，但回看历史，能看到个别运行被判定为写了多余的测试。

评分器视图上的数字是最近一段的实况：变更请求 97%（87 次通过、3 次失败）、Slack MCP 回复 96%（79 次通过、3 次失败）、计算机使用询问 98%（100 次通过、2 次失败）、冗余测试 100%（27 次通过、0 次失败）。点进冗余测试一项，能看到每次运行的时间、通过与否、分数、结论（无多余测试、证据不足、存在多余测试）、耗时与成本。演讲者的观点是：每一次失败都是改进系统的机会，关键在于把它变成可行动的信息。

“Every one of these failures is an opportunity for improving how your system works.”每一次失败，都是改进系统的机会。

■ 在线评分（Online Evals）：用大模型担任裁判，持续给经过工厂的每一次运行打分的机制。

7.2 自改进循环

评分的下一步，是演讲者所说的自改进循环：Agent 去看全部失败模式，把它们汇总起来、找规律，再提出如何改进底层工厂定义的想法。人当然也可以自己去看、自己打分，但让 Agent 来做要高效得多。循环的终点，是 Agent 针对某个失败模式提出修改，并以 PR 的形式提交到工厂定义里——发现问题的人，与修复问题的人，是同一套 Agent。

演示里随手点开的一条建议是“动手实现之前，先读仓库里匹配的技能”。建议的依据写得很直白：它看到这个毛病失败了 37 次。修复方式也写得很直白：给工厂定义提一个 PR。演讲者说，这就是闭环：Agent 发现问题，再提出改动，让工厂下一次不再犯同样的错。真正改进开发的方式，不是换一个更强的模型，而是建起这样的循环，让 Agent 发现问题、修复问题。

“I saw this fail 37 times.”我看到它失败了 37 次。

■ 自改进循环（Self-Improvement Loop）：Agent 汇总失败模式、找出规律，并以改工厂定义的 PR 修复它，从而让同一失败不再重现。

8. 自有基准与工厂栈

8.1 自己的成本—质量曲线

演讲的最后一块演示回到基准。演讲者说，公开基准不可信，但自己的基准可以建：拿任何一次历史运行加入基准集——演示里就是在一次运行的菜单上点“加入基准”——攒出一套有代表性的任务，再用不同模型配置重放，得到成本与质量的对照图。Warp 的基准集叫 WarpBench 0.1：29 项任务，10 项简单、9 项中等、5 项困难、5 项极难，覆盖配置、客户端界面、服务端逻辑与跨切面工厂场景，提示词从真实的 foreman 对话记录里提炼，只限定在实现这一步，与其他 Agent 类型无关。

成本—质量图上，横轴是平均成本、纵轴是正确率：glm 5.3 flash 正确率约 93%、每次试验 1.99 美元，同时是最优选择与最低成本选项；gpt-5.6-sol（high）正确率 94.8%、平均成本 6.23 美元，贵了三倍多；grok 4.6（high）正确率约 93%、成本约 9 美元；gemini 3.7 flash 正确率约 89%、成本约 5 美元；claude opus 5（high）正确率约 91%、成本约 13.5 美元。演讲者的结论是：拿着这张图，才能为自己的代码、自己的技术栈定一条真正有信心的模型路由策略，而不是照搬通用推荐。

问答环节补充了这套做法的三个操作细节。第一，正确率由大模型当裁判评出；人工打分同样合理，只是系统里还没加上；任何一个已定义的评分器都可以作为基准的评判标准。第二，基准集可以手工搭——挑一组小、中、大、有代表性的任务起步；也可以让工厂自己搭，因为工厂知道全部历史会话、一切都存在代码里，它能自己挑出值得测的会话。第三，预算要这么算：先量出每份 PR 的成本、其中多少比例花在评分与基准上，再外推到整个项目；关键是先搭起一套能量化、能改进的东西。

“Set up something that you can measure and improve.”搭一套能量化、能改进的东西。

■ WarpBench：Warp 工厂里从真实历史任务提炼的自有基准集；按成本—质量重放任务、比较模型。

8.2 七层工厂栈

收束时，演讲者把整场演讲叠成一张七层栈：最底层是工厂即代码（FactoryYaml、Agent 定义、自动化定义、启动配置、代码库配置）；往上是数据与上下文（运行记录与转录、Agent 记忆、Agent 制品、MCP 与内部知识、访问控制）；再往上是算力（沙箱、Agent 运行器、计算机使用）；推理层（Warp 托管推理、自带推理、自定义模型路由）；改进层（指标、评分器、基准、自改进）；编排层（原生编排、多 Agent、人在环中、自动化）；最顶上是接入层（经由工厂 MCP、通讯平台、任务跟踪器、代码托管、任意设备、编程接口）。他说，无论按什么路子建工厂，基础设施大概都会长成这个样子。

问答还补了两条落地建议。关于测试与验证：Agent 批量出 PR 时容易堆积，要靠规约驱动开发——先验证改动是否贴合规约；再加上计算机使用验证，让 Agent 从用户角度拿出东西确实能用的证据，这能大大减轻代码评审的负担。关于平台本身：Warp Factories 不是开源的，但很开放——任何现有工具都能接进来；不只面向企业，小团队与个人项目也能用，只是对个人来说有点杀鸡用牛刀，十人以上的团队最合适。

“Once you can truly measure in a closed-loop system, you can do all of these things in a way that’s just never been possible before.”一旦你能在闭环系统里真正度量，你就能以从前不可能的方式做到这一切。

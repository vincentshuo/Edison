一个创始人如何同时管理 20 个 AI 编程 Agent

How One Founder Manages 20 AI Coding Agents at Once

Speaker: Ryan Carson, Untangle

Event: AIE Code Summit, New York

Length: 15 分 28 秒

Source: youtu.be/BTtyguoPvBU

Technical Monograph · 精读报告 发布 2026 年 11 月 9 日 生成 2026 年 11 月 17 日

离婚几乎触及每一个人。Ryan Carson 创办的 Untangle 是一家为家庭法律所服务的 AI 助理公司，而他管理工程的方式与管理人别无二致：人定优先级、见客户；一个从不写代码的“工程师经理”Agent 会话管着约 20 个 builder Agent，每张 Linear ticket 对应一个 PR；每 15 分钟一次的确定性自动化强制经理巡查所有子会话；评审三轮封顶，QA 另起子进程；每个功能必须录一段演示视频，人看完才说 ship it；招聘也完全变了样——不要简历筛选、不要视频面试，候选人先交一段约 45 分钟自己操作 Agent 交付功能的录像，由排序 Agent 排出名次，前五名再做 16 小时带薪实战。这套做法在他口中迭代了上百次，明天就可能过时，但今天管用。

Key Takeaways

  1. 管 Agent 就是管人：人定优先级、见客户；经理 Agent 只做协调，从不写代码。
  2. 一个经理管约 20 个 builder：上限不在模型，在人能听懂多少汇报；硬推只会失控。
  3. 别指望 Agent 自觉巡查：每 15 分钟一次的确定性自动化，强制经理读遍所有子会话。
  4. 验收必须用人眼看视频：每个功能录一段演示，人看完才说 ship it，这是产品负责人不能外包的瓶颈。
  5. 招聘只看一件事：候选人能不能操作 Agent——45 分钟录像加排序 Agent，前五名再做 16 小时带薪实战。

1. 开场：离婚、110 人与“管人就是管 Agent”

演讲从现场一个举手调查开始：谁离过婚？谁认识离过婚的人？到最后全场都举了手。Carson 的两个姐妹离过婚，父母也离过婚，离婚是人生中最痛苦的事之一，他想让它不那么痛苦。Untangle 由此而来：一家专做家庭法的 AI 助理，起初面向消费者，很快转向 B2B，卖给家庭法律所，如今有了产品市场契合度，增长很快。

这是他创办并卖掉的第四家公司。上一家创业公司，他把团队扩到约 110 人，学到了很多管理人的经验。而他的核心论点是：管理人与管理 Agent 是一回事。整场演讲就是这句话的展开——他在 Untangle 如何管理 Agent，以及管理人时学到的一切如何原样适用。

“managing people is like managing agents.”
管理人就像管理 Agent。

演讲分三块：Untangle 如何管理 Agent；招聘在 Agent 时代如何彻底变样；以及一段现场演示。他先说明，管理 Agent 的组织架构并不复杂，真正难的是执行中的纪律——而这正是管理人的老问题。

2. 组织架构：人、经理 Agent 与约 20 个 Builder

组织架构图只有三层。最顶层是人：定优先级、见客户，做所有“人的事”。中间是经理 Agent，下面是 builder Agent。Carson 用的工具是 Devin，全部工程都在云端跑。他说自己一路走来，从手写代码，到用 Cursor，再到 Devin——而 Devin 里真正关键的东西只是一个会话。

■ Devin：Cognition 公司的云端 AI 软件工程师，在隔离的云端会话里写代码、改代码、跑测试。

这个会话就是“工程师经理”。它从不写代码，只负责协调一群“孩子”——builder Agent。Carson 主要用语音跟它说话，因为他自认读得不快，听音频反而吸收得更好。经理 Agent 的工作方式很具体：它主要对着一张 ticket 看板工作。Untangle 用 Linear，但他说用什么工具不重要，重要的是看板是“什么需要被建造”的唯一事实来源。

■ Linear 看板（Ticket Board）：需求的唯一事实来源；每张 ticket 对应一个 PR，经理按依赖关系决定先拉哪张。

每张 ticket 应该对应一个 PR，经理按依赖关系决定拉哪张票。这是相当基础的工程经理工作。真正有意思的是下一层：每个经理 Agent 同时管着约 20 个 builder Agent，这个数字在 5 到 25 之间浮动。上限不是模型能力，而是人跟经理 Agent 对话、理解发生了什么的能力。Carson 说，推得太猛，很快就会失控；他自己的经验是，同时管约 25 个 builder 是可行的。

“I find we can concurrently manage about 25 builders.”
我发现一个人能同时管约 25 个 builder。

关键在于，经理在跟这些 builder 对话，而人永远不进 builder 的会话。人不跟它们说话、不管理它们、什么都不做，一切都经过经理 Agent。经理平时做的，大多是回答那些不需要 Carson 亲自回答的技术问题，或者打通一些小阻塞。

2.1 经理 Agent 从不写代码，只做协调

“从不写代码”不是一句口号，而是角色的边界。经理 Agent 的全部工作是读看板、拉 ticket、回答问题、推进进度。Carson 用语音跟它对话，问一个问题、得到一个建议，再决定下一步。这种“一个人对一个会话”的交互方式，正是整个组织能跑起来的前提：人的注意力只花在一个对话上，而不是二十个。

他还特意说明，经理会话不是什么特殊的东西，就是 Devin 里的一个普通会话。他给会话起名字，为的是自己能分清谁是谁。架构本身没有魔法，魔法在纪律里。

3. 确定性自动化：每 15 分钟强制巡查一次

经理 Agent 有一个不能信任的弱点：它不会自己定期检查孩子。Carson 的原话是，你不能指望经理 Agent 自己去做这件事，因为它不是确定性的。所以他建了一个自动化：每 15 分钟强制经理读遍每一个子会话，推进进度、保持运转。

幻灯片上写的是每 10 分钟巡查一次，Carson 现场纠正：设置上写的是 10 分钟，但他决定 15 分钟才合适。这是一个脚本，Devin 里有自动化功能，你告诉它每 15 分钟读一遍每个孩子，推动事情前进。任何问题都回到经理 Agent 那里。

这个自动化是整套系统里唯一“确定性”的部分。其他一切都可以交给模型去判断，但巡查这件事必须用定时器钉死。没有它，builder 会在某个角落里悄悄卡住，而经理永远不会发现。

4. 评审三轮封顶与 QA 子进程：便宜就多开，别堵合并队列

每个 builder Agent 都会调用一个评审 Agent。Devin 内置评审功能，Carson 说大概每个代码脚手架都有内置评审。Untangle 的规矩是评审最多三轮：builder 与评审来回循环约三次，如果三轮之后仍有重要的 bug 没修掉，就上报给经理 Agent；经理如果需要，再上报给 Carson。

■ 评审 Agent（Reviewer Agent）：builder 调用来自审代码的 Agent；三轮封顶，修不掉的重要问题上报经理。

代码加测试之外，还有一个 QA Agent。这是一个额外的流程：它实际是 builder 派生出的一个子进程，专门跑 QA。Carson 的态度很直接：Agent 很便宜，能开多少就开多少，只要别堵住合并队列就行。最近加入的一位叫 Dale 的工程师帮团队装上了这套 QA 流程，目前运转得不错。

“y'all, this is cheap. Like you should be spinning up as many agents as you can as long as you're not holding up your merge queue.”
Agent 很便宜，能开多少就开多少，只要别堵住合并队列。
■ QA Agent：由 builder 派生子进程跑质量检查的 Agent，与评审 Agent 分开。

但便宜也有代价：大家迟早都会遇到合并队列变慢。这是精细的平衡——把 PR 一个个抠死，还是让它们尽快合入。评审三轮封顶、QA 另起子进程，都是在为这个平衡服务：既不让坏代码溜过去，也不让好 PR 在队列里等死。

5. 验收：视频是人必须亲自看的瓶颈

演讲中 Carson 最强调的一点是视频。每个 builder 都会录一段视频，展示功能实际被使用、测试通过的样子。如果是面向界面的功能，你必须亲眼看它。Devin 内置了这个能力：它会构建测试用例、录制视频，并按测试结果给出绿色或红色。拿到一段全绿的视频，你就能知道你以为发生的事确实发生了，而且视觉上看起来是对的。

这就是人必须参与的环节：人必须说 ship it。经理会话会告诉 Carson 有视频等他看。看视频是难的部分：你得放大、弄明白这个 PR 到底做了什么、你在看什么。Carson 的做法是先读一段摘要，弄清这东西应该做什么，再看视频、投入注意力。

“You got to watch the video.”
视频必须看。

这是最容易偷懒的地方，也是产品负责人必须亲自参与的瓶颈。视频通常得在笔记本上看。Carson 坦承，就在演讲之前，他还在手机上跟经理 Agent 通话，经理说有段视频等他看；他在手机上看不清，差点就想说“算了，就这样吧”。但他没有：回到电脑前，认真看完视频。这套流程迭代了上百次，PR 以高质量大量交付，他对这套做法相当有信心——同时他也笑着承认，这套做法明天就会变，一周后可能就没用了，但今天它管用。

“this will change tomorrow and probably will be useless a week from now, but it works well today.”
这套做法明天就会变，一周后可能就没用了，但今天它管用。

然后他给出全场最强硬的一句：如果还在本地写代码，停下来。你真的需要用云端 Agent 写代码，不管是 Devin 还是别的什么；如果还在跑本地开发，你就是在搞砸——拖自己的后腿、拖团队的后腿、拖一切的后腿，因为本地开发做不到这种并行。

“if you're running local dev, you are screwing up.”
还在本地开发，你就是在搞砸。

6. 规模化：会话彼此对话，合并队列经理收口

十个人的团队怎么跑这套架构？通常每人一个工程师经理会话，有时两个——Carson 自己现在就跑着两个。美妙之处在于，这些会话彼此对话。Devin 内置了这一点，大概任何脚手架都有。会话之间需要能互相说话、彼此认识对方是谁，而且它们很擅长这个。

放大任何一个会话，你会看到它们在互相发消息：清晰、直接、快速，而且说的是正事——不是闲聊，是为了解除彼此的阻塞而必须知道的重要信息。Carson 说，你应该让会话彼此对话；如果不让，就是在拖自己的后腿，交付的软件也会更差。

但光靠会话互相对话还不够，还需要一个合并队列经理（merge queue manager）。十个经理会话同时出 PR 时，需要有人协调这股 PR 的浪潮。数据库迁移号就是典型例子：如果所有 Agent 都去抢迁移号，就会不断碰撞。合并队列经理让这些问题消失，同时对合并队列的进展也更聪明一点。

■ 合并队列经理（Merge Queue Manager）：协调多个经理会话的 PR 流与数据库迁移号等共享资源的会话。

这些仍然只是会话，没什么特别的，Carson 给它们起名字以便分清。他还引用了 OpenAI 一位演讲者的话：要“松绑”（unhobble）——设定好角色，然后把模型放开。让合并经理去说“把这一切做得更好”，确实管用。再往上就是 GitHub 合并队列，没什么高深的，但运转得很好。

7. 招聘：45 分钟录像、排序 Agent 与 16 小时带薪实战

演讲的后半段转向招聘。Carson 问现场谁在招工程师或员工，不少人举手。他的判断是：关于招聘员工的一切都过时了，全都不合理。他建议大家换一套做法。

“Every everything you used to do about hiring employees is over.”
招聘员工那一套，全都过时了。

Untangle 的做法是：第一，不做任何形式的预筛；第二，不做任何视频聊天。在大部分流程里完全不跟人接触，因为接触只会带来偏见——你会喜欢他们的爱好、喜欢他们说话的方式、觉得他们有意思，而这些全是噪音，没有一点信号。唯一重要的是：他能不能操作 Agent？

“All that matters is can they operate an agent, right?”
唯一重要的是，他能不能操作 Agent？

具体做法是：请候选人提交一段约 45 分钟的视频，全屏录制，内容是在自己已经维护的 app 上交付一个功能，通常是一个 PR。没有指令、没有指导、什么都没有，只想看这个人作为 Agent 操作者有多强。这一步是免费的，不付钱，算是进门的门槛。

然后把这些视频喂给一个排序 Agent，让它看视频、看转录，把人排出名次。Carson 说，他第一次做这件事时并不信任结果，不喜欢它给出的排名；讽刺的是，它其实是对的——排第一的那个人，正是他本该招的人，只是他当时被自己的偏见蒙住了。

■ 排序 Agent（Ranking Agent）：观看候选人录像与转录，按 Agent 操作能力把候选人排出名次。

这一步的设计本身就是一道筛选：45 分钟全屏录像要求候选人拿出自己真正维护的项目、真实交付一个功能，没有模板可套，也没有面试官可以讨好。排序 Agent 看到的不是简历上的关键词，而是完整的屏幕操作与口头表达——候选人如何调用 Agent、遇到卡点时怎么处理、会不会边做边说出思路。Carson 说，这些录像里的细节，才是判断一个人能否操作 Agent 的真实信号。

看这么多视频当然很花时间，你可以自己全看，但一个足够聪明的模型其实很擅长判断一个人有多强。有意思的是，候选人有时会含糊其辞，有时不边做边说，你很难知道他们在想什么、做什么；也有人话很多。这些都是需要注意的信号。

然后挑出前五名，邀请他们参加一个带薪项目：固定费用、16 小时的工时、一个 Devin 座位、签 NDA，任务是把一个真实的 PR 做到可合并。全部过程都录下来——16 小时的视频，用 Loom 录制，再把视频全部喂给 Agent，问它该选谁。

Carson 说，上一轮他真的看完了全部 16 小时的视频，很残酷，但确实让他对人有了准确的判断。最后挑出 finalist；关键在于，在这之前不要打电话——你会产生偏见、会困惑、会选错人。只跟 finalist 通电话，说“我们想录用你，聊聊吧”。这通电话给出最后一点“人的感觉”，但你已经看了这些人好几个小时的视频，其实不太需要这通电话；不过其中有一点人与人之间的连接很重要。

他认为这就是所有人未来招聘的方式。他职业生涯里招过成百上千人，而这套做法就是更简单、更好，而且是大家正在走向的方向。

8. 收束：管理 Agent 就是管理人

演讲提前三分钟结束。Carson 的收束很短：想了解 Untangle，去 untangle.us；他在 X 上几乎全天在线，在 X 上待了 20 年，想了解顶级公司如何管理 Agent，就去那里找他。对家庭法、让离婚不那么痛苦有热情的人，可以直接联系他。

整场演讲的论点可以收成一句话：管理 Agent 的组织架构并不复杂——人定方向，一个从不写代码的经理会话居中，约 20 个 builder 在下面干活，确定性自动化钉死巡查节奏，三轮评审与 QA 子进程守住质量，一段视频守住验收，一个合并队列经理守住收口；招聘只看操作 Agent 的能力。复杂的是纪律：不进 builder 的会话、不在手机上草草放行、不在招聘里让偏见插手。Carson 的经验是，这些纪律与管理人时学到的完全一样——而这正是他四次创业、管过 110 人团队后，觉得最值得分享的东西。

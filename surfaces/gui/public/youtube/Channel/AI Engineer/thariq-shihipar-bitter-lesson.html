苦涩教训的甜蜜一面

The Sweet Side of the Bitter Lesson — Thariq Shihipar, Independent

Speaker: Thariq Shihipar, Independent（前 Anthropic Claude Code 成员）

Event: AI Engineer Code Summit 2026

Length: 19 分 08 秒

Source: youtu.be/xRJMiaUoD_8

Technical Monograph · 精读报告 发布 2026 年 11 月 19 日 生成 2026 年 11 月 20 日

离开 Anthropic 之后，Thariq Shihipar 回顾了自己对 AI 的几处错判：他曾以为 Bash 与 React 会是 Agent 唯一的出路，以为扩散模型会吃掉艺术，以为模型终将以一种异质的方式做事、而人只能顺从——结果全错了。模型不是越变越疏远，而是越变越顺手；能力的前沿固然锯齿嶙峋，前沿之下的内部却是一片平滑的广阔地带。AI 同时是一场工业革命与一场文艺复兴：今年做的是前者，把软件变成可靠的流水线；明年要做的，是后者——而他给出的办法，是把引擎代码与人能读懂的规约分开，让开发者重新拿回控制权。

Key Takeaways

  1. 苦涩教训也有甜蜜的一面。模型没有把人逼进一种异质的工作方式，反而越来越能按人想要的方式做事。
  2. 前沿锯齿，内部平滑。基准上最亮眼的突破只是前沿的锯齿，真正改变工作的是前沿之下那片宽广而平坦的能力。
  3. AI 同时是工业革命与文艺复兴。今年的主题是把软件变成可靠的流水线，明年的主题是把软件做得值得一场文艺复兴。
  4. Vibe coding 的毛病不在模型，在控制权。当开发者说不清自己的角色会做什么、为什么这么做，再快的生成也做不出好软件。
  5. 把引擎与可读的规约分开。引擎交给 Agent，规约写成人能读、能改的文字，控制权就回来了，软件文艺复兴才有落点。

1. 开场：离开 Anthropic 之后的反思（约 0:00–1:27）

Thariq Shihipar 上台先报身份：他不久前离开了 Anthropic。这是一次回顾——过去一年里，他对 AI 的判断有对有错，而他要讲的，恰恰是错的那部分。他先说了自己猜对的三件事：大约 2025 年 6 月，他就说模型能剪辑与生成视频；他说模型能用 HTML 理解自己的工作；他说模型能帮人弄清未知、做规划与学习。这三件都应验了，听众里不少人大概已经在工作中用上了。

但他紧接着转折：AI 圈有个坏习惯，猜错的事就悄悄忘掉，假装自己一直都看好 AI。他要反过来，把错判摊开讲——因为他这场演讲的结论就藏在那些错判里：他管它叫"苦涩教训的甜蜜一面"。

Shihipar 不是旁观者。他在 Anthropic 的 Claude Code 团队工作了一年多，2026 年 10 月 24 日在 X 上宣布离职；此前他创办过 Y Combinator 支持的游戏公司 One More Multiverse，也参与创办过学术出版平台 PubPub。这场演讲的底色，是一个既造过游戏、又造过 Agent 的人，对"人还怎么掌控软件"的追问。

2. 三处错判：Bash、React 与扩散模型（约 1:27–4:04）

第一处错判是"Bash 就够了"。有一阵子，Agent 特别擅长用 Bash，而 Claude Code 正是围绕 Bash 工具建造的，于是人们觉得：一切都会变成命令行界面，Bash 与 CLI 将接管世界。结果并不是这样。Shihipar 现在更喜欢 MCP，而不是 CLI；除此之外，还有代码模式、技能与渐进式披露等多种让 Agent 作用于世界的方式。Agent 用 Bash，不过是训练方式留下的一点残余。

■ MCP（Model Context Protocol）：Anthropic 推出的开放协议，让模型通过结构化接口调用外部工具与数据源，而不必把一切都包成命令行。

■ 渐进式披露（Progressive Disclosure）：只在需要时才把信息与工具交给模型的做法，避免把全部上下文一次性塞进提示词。

第二处错判是"React 就够了"。也曾有一阵子，模型写 React 写得特别好，人们觉得要做 AI 应用，就得用 React、React Native，总之都得上网。结果也不是这样：模型现在写 HTML、写 React、写 Swift、写 Figma 的专有 JSON 格式，写出来的东西看起来都差不多。Shihipar 一度担心，模型在 React 上被训练得太多，React 会变成"最后一种语言"；现在看来几乎肯定不会——很多人已经在写自己的语言了。

第三处错判是"扩散模型会吃掉艺术"。他曾担心，模型会造出最美的东西，而人对它毫无控制。但事实是，语言模型通过写代码、操控电脑、用 Blender、Photoshop 或 Figma 来作画，控制权始终在人手里。扩散模型没有吃掉艺术，艺术只是换了一种做法。

■ 苦涩教训（The Bitter Lesson）：Richard Sutton 2019 年的短文，主张能随算力扩展的通用方法（搜索与学习）最终胜过注入人类知识的方法；成功来得苦涩，因为它战胜的是人们偏爱的人类中心做法。

■ Shoggoth（修格斯）：AI 圈借用的克苏鲁意象，指模型内部那种不可名状、异质的智能；Shihipar 用它代指"模型自有其怪异做法，人只能顺从"的恐惧。

这三处错判背后是同一种恐惧，也是"苦涩教训"常被读出的那一面：模型会有自己的一套做法，异质、陌生，人只能顺从这种外来智能。Shihipar 的回答很干脆：事情不是这样发生的。模型没有把人逼进一种做法，恰恰相反，人能要求的东西越来越多。

3. 以人为中心：软件工程师站在采用的最前沿（约 4:04–4:40）

于是问题回到他反复问的那一句：怎样才能既拥抱 AGI，又以人为中心？这件事之所以重要，是因为软件工程师站在 AI 采用的最前沿：发生在软件身上的事，会发生在知识工作与经济的其他部分；我们怎么对待 AI，别人也会怎么对待。他还提到同场演讲里谈到的"对抗 slop"与"更有野心"——软件工程师是抵御低质内容的第一道防线，也是野心的第一批实践者。

4. 工业革命与文艺复兴同时发生（约 4:40–5:53）

Shihipar 对 AI 的定位是一句话：它同时是一场工业革命与一场文艺复兴。今年是工业革命的一年：大家常说"软件工厂"，把软件从一门不可靠、难以执行的技艺，变成不再是限制因素的东西——这种工业化确实在发生。但与此同时，也有一场文艺复兴在发生：人们想要越来越高质量的软件，往软件里多放的每一点创造力、效用、精神与灵魂，都有经济价值。

“AI is both at the same time an industrial revolution and a Renaissance, right?”AI 同时是一场工业革命与一场文艺复兴，对吧？

两件事很难同时装在脑子里，但 Shihipar 坚持它们都是真的，而且我们正在同时做这两件事。工业革命解决"能不能可靠地造出来"，文艺复兴追问"造出来的东西值不值得"。今年的演讲季大多在谈前者；他的演讲要把后者推到台前。

■ 软件工厂（Software Factory）：把开发流程当作一条默认自动化的流水线来经营；Bug 报告进、合并与监控出，人只在需要判断时出场。

5. 锯齿前沿与平滑内部（约 5:53–9:19）

谈到 AI 能力，人们常说"锯齿前沿"：两年前是"替我写这个函数"，一年半前是"做个功能"，然后是"做个待办应用""给我克隆一个 Slack"，现在是"从零做个马里奥赛车，再把它移植到 Wii 上"。评测与基准上看到的，就是这条不断抬升的锯齿线——每次突破都发生在前沿最凸出的那一点。

但 Shihipar 更想谈另一面，他叫它"平滑内部"。幻灯片上的动画画了一条锯齿线，中间套着一个圆圈：圆圈代表模型聪明到足以做到的全部事。会写 React，就会写 Figma、写 JSON——前沿之下的能力不是锯齿，而是一片平坦的广度。人们只盯着前沿的凸点，却忽略了凸点之下，模型已经能把一大片任务都做得很好。

这对他来说比前沿更重要，因为他不再关心模型能不能从零做出马里奥赛车；他关心的是，我们做的软件质量够不够高、配不配得上一场文艺复兴。做原型时，他可以要 HTML、要 React、要 Figma 文件，甚至让模型操控电脑、用 After Effects 做视频——终点一样，路有很多条。曾经他害怕模型只喜欢一种做法、大家只好跟着那一种走；现在看来，那种担心落空了。

推到极限，这幅图景会变成：完美的模型不需要验证自己的工作，也不用扫描安全漏洞——它写完代码就说"我做完了"，人按规约与目标一核对，就确认它做对了。脚手架、软件工厂、给模型做 QA，这些都是过渡形态；模型越聪明，"平滑内部"越大，人类要做的就越不是检查，而是定规约、定目标。

■ 锯齿前沿（Jagged Frontier）：模型能力边界的形状——某些任务上极强，相邻任务上却可能很弱，评测分数随任务起伏如锯齿。

■ 平滑内部（Smooth Interior）：Shihipar 的对照概念：前沿之下，模型的能力是一片平坦而宽广的地带，会做一件事，就能把相邻的一片事都做好。

“I don't really care that they can build Mario Kart from scratch anymore. What I really care about is, hey, is the software that we're building, is it high quality? Is it worthy of a Renaissance?”我其实已经不在乎它们能不能从零做出马里奥赛车了。我在乎的是，我们做的软件质量够不够高？配不配得上一场文艺复兴？

6. 模型知道多少：陆地还是海洋（约 9:19–10:38）

除了基准，还有一种办法可以直观地看到模型知道多少：给模型一个经纬度，问"是陆地还是水"，把答案画成一张世界地图。幻灯片上是 12 个盲测 Claude 的结果：每 2° 取一个点，全球共 16,200 个点，不给图、不给工具，白色代表模型答"陆地"。Sonnet 4.5 只有 60.5%，Haiku 4.5 为 81.3%，Opus 4.5 为 82.6%，Opus 4.6 为 91.2%，而 Opus 5.5 达到 99.0%——几乎画出了一张完美的世界地图。

Shihipar 说，这张图让他觉得，锯齿前沿对我们越来越不重要，重要的是模型头脑里的通用知识。Opus 4.6 的地图还模糊，Opus 5.5 已近乎完美——变化不在某一次突破，而在知识本身的广度。由此他引出明年的主题：用智能来理解并塑造我们如何使用智能。今年是把软件工业化、做成可靠的东西；明年要回答的，是工业化之后，软件该长成什么样子。

7. Vibe coding 让人失去掌控（约 10:38–12:54）

他举的例子是自己的游戏：一款 2D 等距格斗游戏，受《降世神通》与《任天堂明星大乱斗》启发，他在 X 上发过进展。做起来很有意思，也很让人沮丧：他常常不知道每个角色到底会做什么。让角色"扔一块石头"，模型会顺带决定一堆事——这个角色还能召唤一堵墙，石头穿不穿墙？速度多快、体积多大、蓄力多久？模型替他做了选择，他试玩时完全不知道这个角色到底会什么。

更糟的是工作状态：他很容易分心，很少进入心流——发个提示就去干别的，回来一看，进展反而更少。有一阵子他以为，这就是跟 AI 一起工作的样子，只能接受。但回头一想，他觉得不对：AI 应该按我们想要的方式工作；如果现在的样子做不出好软件，那就不该接受。

“I have no idea what this character actually does.”我完全不知道这个角色到底会做什么。

他引用同场另一位演讲者 Dex 的话：好作品来自一个 messy 的过程，关键不在于包含了什么，而在于做了哪些选择、排除了哪些东西。按这个标准，vibe coding 的问题就清楚了：要做出值得文艺复兴的东西，得先成为专家、真正懂自己的东西；而当模型替你做了所有选择，你连"懂"都谈不上。

■ Vibe Coding：凭感觉向 Agent 描述想要的东西、让它直接生成代码的做法；快，但开发者往往说不清生成物内部的逻辑。

8. 引擎与可读规约分开（约 12:54–13:47）

他的办法是把代码库分成两部分。一部分是引擎——Agent 写的代码，他坦言自己并不懂相机怎么工作，也不必懂。另一部分是一个文件夹，他叫它 spec，或者干脆叫 human——那是他读的代码：有 lint、有给 Claude 的规则，读起来像英文，密度刚好让他读一遍就知道发生了什么、能改、能调。更重要的是，它是游戏样子的基准真相：读这份规约，就知道游戏是什么。

这个分法把控制权还给了人。引擎可以交给模型去写、去改，因为规约在人手里：人看得懂、改得动，模型也按规约办事。规约不是文档，而是代码的一部分——一份人能读的代码。

9. 现场演示：给游戏写一门脚本语言（约 13:47–16:40）

演示从 Zed 编辑器开始。项目叫 bending-game，左边是 game 文件夹——那是 Agent 的代码；右边打开的 hero.ts，是角色 Kesar 的规约：扔石头这个招式有三种方式，可以从地面抓起、也可以从墙上抓起；注释齐全，用的都是人能读的单位——步行速度 3.1 米/秒，走完一步 0.22 秒，转向 344 度/秒，体重 1.15 倍，而不是 0.5 这种裸数字。按键也很直白：A 扔石头，B 造墙，Move 是 shatter（碎裂），回复招式是 pillar（石柱）。

然后他在浏览器里把游戏跑起来：圆形竞技场上，Kesar 与 Ondo 对峙。石头可以蓄力变大再扔出；召唤一堵墙、把它排队成一个动作，Cursor 的 Tab 补全会接着写。这就是他说的规约驱动开发：规约本身就是一门脚本语言。他承认这未必是写游戏的最终方式——复杂的东西仍需请 Claude 做原语——但他现在能看懂发生了什么，也更有掌控感；Claude 干活的时候，他能一边审一边一起干。

■ 规约驱动开发（Spec-Driven Development）：先写一份人能读、能改的规约，再让 Agent 按规约实现；规约是开发的基准真相，而不是事后补的文档。

演示的要点不在游戏本身，而在工作方式的改变：他不再受限于模型的能力、也不再受限于模型喜欢用什么语言写代码；他想的只是，怎样交付高质量的软件。规约让他把注意力从"模型会什么"移回"软件该是什么样子"。

10. 设计一场软件文艺复兴（约 16:40–19:08）

收尾回到明年的主题：如果把这个思路内化，明年将是软件的文艺复兴。值得做的事很多：新语言——要快、表达力强、可热重载，像 Rust 这样高效，也要模块化、可读；新原语——新型数据库、新型服务器、与操作系统交互的新方式；新的交互范式——很多旧的人机交互研究现在值得重访；新的美学——软件的使用与设计方式可以大变；还有他一直在 vibe coding 的个人软件，会摆弄操作系统。幻灯片把七项列在一起，其中"可塑软件"被标成橙色。

■ 可塑软件（Malleable Software）：可以由使用者在使用中直接重塑的软件；Shihipar 收尾幻灯片上被标亮的一项，代表文艺复兴的方向之一。

他最后说，这些想法并不新鲜，同场几乎每位演讲者都谈过野心。但重点只有一个：我们要决定未来工作的样子、决定理想的体验是什么样子——因为模型不是那种要把人逼进某种工作方式的异质智能，它们什么都能做，也确实会什么都做。我们的工作，是带来这场文艺复兴。

“The models are not this alien intelligence that's trying to force us into a specific way of working.”模型并不是那种要把人逼进某种工作方式的异质智能。

讨论问题

1. 如果模型的能力内部是平滑的，评测的锯齿前沿还值得追吗？什么指标更能反映你手头工作的真实难度？

2. "Bash 就够了""React 就够了"这类判断，是怎样从训练方式的残余变成行业共识的？你现在的工作里还有类似的默认答案吗？

3. 工业革命与文艺复兴同时发生时，怎样判断一份工作属于哪一边？你的团队现在更缺流水线，还是更缺灵魂？

4. Vibe coding 让你失去掌控的那一刻，具体是哪一个决定被模型替你做了？把它写下来，会改变你下一次提示的方式吗？

把智能放出来

What It Takes to Set Intelligence Free — Fabian Hedin, CTO, Lovable

Event: AI Engineer Code Summit 2026

Technical Monograph · 精读报告 发布 2026 年 11 月 19 日 生成 2026 年 11 月 20 日

2023 年，Lovable 差点因为 Agent 把公司做死：当时 GPT-4 的智能撑不起复杂的多 Agent 框架，精心搭建的主 Agent 派生前端、后端 Agent 的体系反而把产品做得更糟。公司在钱花完之前退回了简化系统，等到智能到位才重新出发——如今这套系统每分钟跑过十亿 token。联合创始人兼 CTO Fabian Hedin 在这场演讲里拆解了“解放智能”的三件套：能让 Agent 连续工作十小时以上的运行时、能检查点与分叉的电脑、内外两层验证反馈环——以及把 Vite 的开发服务器用 Rust 重写成的 OJ。

Key Takeaways

  1. 2023 年 Agent 来得太早。GPT-4 时代的智能撑不起复杂的多 Agent 框架，Lovable 差点因此倒掉；退回简化系统、等到智能到位，才重新出发。
  2. 重要的不是代码，是结果。用户要的是生意与价值，平台因此把 Agent、云端托管基元与商业能力做在一起。
  3. 让 Agent 工作十小时以上的三件套。能长时间运行的 Agent 运行时、能检查点与分叉的电脑、内外两层验证反馈环。
  4. 任务历史照 Git 的样子设计。追加式日志、每个事件指向父事件、分叉不复制共享历史；但 Agent 的历史没法像 Git 那样合并。
  5. 电脑也可以被检查点与分叉。黄金检查点 230 毫秒复活一台虚拟机，每天约一百万个沙箱；Vite 的开发服务器用 Rust 重写为 OJ，预览从 14 秒降到 3 秒。

1. 开场：差点死在 2023 年的 Agent 梦（约 0:00–3:52）

Fabian Hedin 上台先报身份：Lovable 联合创始人兼 CTO。过去几年，他和团队做的事是让任何人都能创建软件、运营软件、部署软件。这场演讲的主题是“把智能放出来需要什么”，而他开场先说，自己跟 Agent 的关系“有点复杂”——因为 Lovable 差点就死在 Agent 手里。

2023 年，团队觉得 Agent 就是未来，那就现在为它们而建。事后看，关于“未来”的那一半判断是对的，关于“现在”的那一半全错了：那还是 GPT-4 的年代，智能根本没到能撑起复杂 Agent 系统的地步。现在到了——智能已经处在一个可以围绕它搭建更复杂系统的位置。

第一版产品就叫 GPT Engineer，界面与今天大同小异：左边一个聊天框，右边一个预览。但当时的 AI 很简单：一个提示、一次 LLM 调用，只做一页应用和比较简单的东西。团队觉得智能会一路进化，必须提前准备好，于是去建了一个 Agent 框架。

那个框架按 Hedin 自己的话说，“非常精致，甚至可以说很美”：一个主 Agent 跟用户说话，再派生出实现 Agent、前端 Agent、后端 Agent，各有专长，互相发消息。当时也有论文说这种做法能行。结果是“完全不行”——产品反而更糟了。台下响起笑声，Hedin 承认：“这一次我们确实失败了。”

“We almost failed as a company because we thought back in 2023 that hey, these agents are the future, so let’s build for them now.”2023 年我们差点因为 Agent 把公司做死：当时我们觉得，Agent 就是未来，那就现在为它们而建。

好在钱花完之前，团队想明白了：回到更简单的系统。2024 年底的版本是几个小模型做知识检索，再由一个主 LLM 在同一条消息里既回复用户又写代码——响应快、可靠，用户也愿意在里面跟模型来回迭代。关掉那个框架之后的故事，Hedin 只用了一句话收尾：“我们回来了。这一次，Agent 真的行了。”这套系统如今在生产环境里每分钟跑过十亿 token。

2. Lovable 是什么：左边聊天，右边预览（约 3:52–7:48）

在讲技术之前，Hedin 先把 Lovable 是什么说清楚。把界面简化到极致，左边是一个聊天框，人进来描述想建什么；右边是一个预览，也就是建出来的结果。2023 年这套界面只能做简单的东西，如今在这一层抽象上已经能建很复杂的东西——连面向开发者的工具也在往这种界面迁移：人不再天天盯着代码，而是看架构、看输出。

这背后是 Lovable 一以贯之的核心论点：人不必再像以前那样在意代码。行业眼下处在一种中间状态：有人说完全不用在意代码了，也有人持不同意见。Hedin 自己从小写代码，难免对代码有感情，但到头来重要的不是代码，是结果——他念到幻灯片上“重要的不是代码”这一句时还笑了一下，说还以为这句已经删掉了。

“In the end what matters is actually not the code… what matters is the outcomes.”到头来，重要的不是代码，是结果。

结果是什么？对 Lovable 的用户来说，是创办一门生意、变现、为他人创造价值。平台因此由三部分组成。第一是 Agent：它能做相当任意的事，专长是建软件，能用浏览器验证自己建的东西，接 GitHub，写出的代码归用户所有。第二是云端：数据库、认证、存储、后端算力、安全扫描、备份、日志等托管基元，Agent 都能检查，不用再去不同的服务之间东拼西凑。第三是商业能力：收款、发邮件、优化 SEO、在 Google 与 Meta 上投广告、通过分析看转化并优化——Agent 在所有这些环节里都在场。

■ 托管基元（Hosting Primitives）：平台直接提供给 Agent 的后端能力——数据库、认证、存储、算力、备份与日志等，不用用户自己去接不同的服务。

3. 拆掉时长上限：让 Agent 连续工作十小时以上（约 7:48–8:51）

Lovable 曾经把 Agent 限制在只工作 30 分钟，因为团队觉得 Agent 再长就不可靠了。现在这个限制被拆掉了：时长完全没有上限，Agent 可以连续工作 10 小时以上。为此要解决的，是三件事：第一，Agent 运行时本身，怎样让它长时间运行；第二，电脑——Agent 真正干活、跑开发服务器、验证自己工作的地方；第三，验证本身——想让 Agent 长时间工作，必须有反馈环，不然它会一路走偏。

这三件套就是这场演讲后半段的结构：运行时、电脑、验证。每一件都不是单个功能，而是一组互相咬合的设计——运行时决定 Agent 怎样被唤醒、怎样记住自己做过什么；电脑决定 Agent 的工作以什么速度、在什么代价下发生；验证决定 Agent 走偏的时候谁来把它拉回来。

■ Agent 运行时（Agent Runtime）：让 Agent 持续工作的那一层系统：接收消息、读历史、调模型、跑工具、写结果，循环往复。

4. 收件箱与任务历史：向 Git 借来的设计（约 8:51–11:10）

先看运行时。有三种来源能跟一个 Agent 互动：人（发提示）、其他 Agent、按计划唤醒它的系统。Lovable 的做法是给每个 Agent 一个独立的收件箱，任何来源都往里面投消息，比如一句“进度怎么样”。Agent 是常驻的：它可能已经做了几个动作——发请求、调工具、拿到结果——到了可以接收消息的点，它自己把收件箱里的消息复制进自己的轨迹，也就是任务历史。这是整套运行时背后的第一条设计原则。

■ 收件箱（Inbox）：每个 Agent 独有的消息入口；人、其他 Agent 与定时系统都往里面投消息，Agent 在合适的时机自己取走。

轨迹是 Agent 工作的历史，也是它记忆的基础。Lovable 设计轨迹时借用了 Git 的思路：它是一条追加式日志，每个事件都指向父事件，也就是上一个事件。正因为如此，它天然就能分叉——两个事件指向同一个父事件，就形成一个分叉；可以在历史的任何一点并行启动 Agent，而不必复制共享的历史。

■ 任务历史（Trajectory）：Agent 至今为止做过的一切的完整记录，是 Agent 记忆的基础；Lovable 用它来渲染提示词、重放运行、支撑分叉。

■ 追加式日志（Append-Only Log）：只追加、不改写的事件记录；每个事件指向父事件，像 Git 的提交链一样可以分叉，但不能像 Git 那样合并。

但分叉之后会发生什么，语义上并不清楚。跟 Git 不一样，Agent 的目录没法合并——分叉出去的 Agent 可以互相交谈，但它们的目录合并不回来。Hedin 把这一点说得很坦白：这是设计里有意留下的不对称，分叉是免费的，合并是不存在的。

“Unlike Git, we cannot merge agent directories, but we can kind of spawn them out.”跟 Git 不一样，我们没法合并 Agent 的目录，但可以把它们分叉出去。

5. 提示词与任务历史分开：按模型渲染提示词（约 11:10–13:03）

轨迹里装的是完整历史：每一次工具调用、成功还是失败、平台上发生的其他事——其中很多跟提示词并不完全相关。所以 Lovable 把两件事分开了：一条是追加式日志本身，另一条是真正喂给 LLM 的提示词，后者是从日志里现渲染出来的。

为什么要分开？历史一长，就想做压缩、把前面的步骤摘要掉；但摘要的时机因模型而异——不同模型的上下文长度不同，什么时候该摘要、什么时候不该，想法也不同。分开之后，就可以为任何模型、任何任务渲染出最合适的那份提示词，而不是让一份提示词迁就所有模型。

为了展示这套事件历史的实际样子，Hedin 现场打开了一个调试工具：一段他拖动滑杆的录像，右边的 UI 随着滑杆同步更新——156 个事件，每一个都是事件历史里的一件事。在任何一个时间点，UI 都能按历史原样重现。这套历史之所以值得做，就是因为它让平台对正在发生的一切都有完全的控制。

6. 无状态进程：每天部署 700 次也不打断 Agent（约 13:03–14:30）

运行时的最后一块，是跑 Agent 的进程与任务历史的分离。进程几乎完全无状态：每次调用、每次工具调用、每轮之间，它只把状态持久化进任务历史；进程本身可以来去自如。

为什么要在意这一点？Lovable 每天向这套系统部署 700 次，约每两分钟一次。一个为客户连续工作 10 小时的 Agent，不能因为部署而被打断；同时它又必须跑在最新部署上——可能是一个新功能，也可能是 Linux 内核的安全漏洞，必须马上更新。

历史与进程分离之后，同一个任务可以一直工作，而背后的算力由不同的进程接手——10 小时，甚至更久，部署照常进行，Agent 察觉不到自己身后的进程已经换过几轮了。

7. 给电脑做检查点：230 毫秒复活一台虚拟机（约 14:30–16:16）

第二件是电脑——真正干活的地方。Lovable 试过很多轮迭代、很多家提供沙箱的供应商，最后落到自己花大力气开发的系统：给整台电脑做检查点。

新项目从一个“黄金检查点”开始：操作系统、系统服务、常用工具、随时可以启动的开发服务器，一次准备好。检查点包含磁盘、内存乃至正在运行的进程的全部内容；复制到一个新项目手里，只要约 230 毫秒。

■ 黄金检查点（Golden Checkpoint）：预先准备好的电脑快照，包含操作系统、系统服务、常用工具与就绪的开发服务器；新项目从它启动，约 230 毫秒完成复制。

项目自己的代码与依赖也会随着 Agent 工作不断被检查点化：每轮结束存一个检查点，需要时亚秒级拉起。用户离开 10 分钟再回来，电脑已经悄悄关掉又悄悄拉起，毫无察觉——连在途的请求都不会丢。复用配置在这种规模上不是锦上添花，而是必需：幻灯片底部的数字是每天约一百万个沙箱。

8. 分叉沙箱：写时复制与流式内存（约 16:16–18:02）

检查点化的另一个好处，是电脑也能像任务历史一样分叉。Lovable 有个叫 Drafts（草稿）的功能，让用户在同一项目的不同环境里并行工作，背后就是分叉电脑：从最新快照出发，草稿 A 在应用内改排期、草稿 B 按邮件改排期，各改各的。演示里同时跑两个，可以想象成百上千个。

为此做的第一个优化，是内存的写时复制：创建一个分叉在内存上基本是免费的；只有当某个进程真正往内存里写时，那一页才会被复制过去，新的内存才开始分配。

■ 写时复制（Copy-on-Write）：分叉时不真正复制内存，只在进程第一次写入某一页时才复制那一页；分叉本身几乎不占内存。

第二个优化针对启动：每个沙箱需要几百 MB 内存，从冷对象存储流式传输到磁盘、再进虚拟机内存要花几秒；但因为内存可以流式传输，机器可以在全部内存就绪之前就启动——操作系统用的内存先到，进程随内存到达陆续启动，又省掉一部分启动时间。

9. OJ：把 Vite 的开发服务器用 Rust 重写（约 18:02–19:13）

还能更快吗？Vite 是 JavaScript 生态里多数主流框架都在用的开发服务器；Lovable 把它分叉出来，用 Rust 重写——这就是 OJ。幻灯片上的标题就是“认识 OJ：用 Rust 重写的 Vite”。

效果按幻灯片上的数字：冷启动快 2 倍，拿到一个可用的预览从 14 秒降到 3 秒。关键的改动是 Vite 用 Node.js，而 OJ 只是单个 Rust 二进制文件，底下没有 Node.js；内存占用少 6.5 倍。掌控了电脑里跑的应用，也就掌控了内存的写法——这又反过来优化了分叉时的写时复制，于是可以极高效地并行跑大量 Agent，让它们探索不同的修 bug 方案、不同的性能优化路径。

■ OJ：Lovable 把 Vite 的开发服务器层用 Rust 重写的开源项目（github.com/lovablelabs/oj）；单个二进制文件，不依赖 Node.js，冷启动更快、内存占用更小。

值得留意的是幻灯片与转录稿的一处出入：自动字幕把预览时间听成了“40 秒”，幻灯片上写的是 “14s → 3s”，正文以幻灯片为准。OJ 也不是整个 Vite 的重写，而是开发服务器这一层——Vite 的作者 Evan You 在公开讨论中也做过同样的澄清。

10. 验证与收尾：内外两个反馈环（约 19:13–22:25）

最后一件是验证。Agent 行动之后需要知道：这一步走得对不对。Hedin 把反馈环分成内环与外环：内环在一轮之内——构建能不能过、有没有 lint 与类型错误、预览里有没有运行时错误、还有无头浏览器里探索正在建的 Web 应用，以及轮内评判、领域扫描、后端日志、护栏与用户触发的修复。外环在每轮之间——一轮是 Agent 把控制权交还给用户的那一刻；轮次之间可以拿到产品本身的生产反馈：生产信号、访客行为、用户在网上的反馈、自动 A/B 测试（改一句文案，看转化率是否提升）。

■ 内环（Inner Loop）：一轮之内的验证——构建、lint、类型错误、运行时错误、浏览器与视觉检查、轮内评判等，Agent 当场看到、当场修复。

■ 外环（Outer Loop）：轮次之间的验证——生产信号、访客行为、用户反馈、自动 A/B 测试与交易、转化等业务指标，下一轮再反馈给 Agent。

外环的终点是业务指标：收款、交易与转化。Lovable 控制着这些能力，所以能让 Agent 不只优化代码，还能优化产品背后的商业策略。幻灯片底部还有一句值得单独记下的话：生产结果只作为下一轮的发现反馈给 Agent，绝不作为训练信号。

收尾回到开头的三件套：这套编排 LLM 的 Agent 系统，每分钟跑数十亿 token；每台电脑随 Agent 一起拉起，多个 Agent 可以共用一台电脑；Agent 与 Agent 交谈、互相编排——这一次是真的在规模上跑起来了。Hedin 最后的邀请很简单：去 lovable.dev 试试，界面很简单，不用在意这些幕后的东西。

讨论问题

1. 2023 年的 Agent 框架“完全不行”，是智能不够，还是框架本身的思路错了？如果智能再晚两年才到位，Lovable 该怎么活？

2. Hedin 说“重要的不是代码，是结果”。在你的工作里，哪些“代码”其实是结果的代理指标，哪些已经成了目的本身？

3. 任务历史照 Git 的样子设计，却明确“没法合并”。Agent 的历史在什么意义上可以分叉、在什么意义上不能合并？这对多人协作意味着什么？

4. 提示词与任务历史分开之后，摘要的时机可以按模型调整。你的系统里，提示词与历史是绑在一起的吗？分开会带来什么新的 bug？

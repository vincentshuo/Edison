谁来评审机器人：六成数据 PR 无人评审合入

60% of Our Data PRs Now Merge With No Human Review

Speaker: Chetas Joshi, Robinhood

Event: AIE Code Summit SF 2026

Length: 28 分 00 秒

Source: youtu.be/MQiojLnK-E0

TECHNICAL MONOGRAPH · 精读报告 发布 2026 年 11 月 10 日 生成 2026 年 11 月 17 日

Robinhood 的数据平台每天要回答一个问题：一份在 CI 里全绿的 PR，真的可以合入吗？AI 编程助手让 PR 以机器速度到来，评审却还停留在人的速度。团队建了一个混合评审员：确定性脚本对照事实来源证明能证明的事，Agent 走查代码判断记录之外的风险，人守住三类受保护的决定。截至 2026 年 8 月 31 日，约 60% 的数据管线 PR 在无人评审的情况下合入，人工评审工作量减少约 75%，每月省下约 132 个工程小时，相关事故减少约 30%，漏检率约为 2%。这份报告跟着一份 PR 走过三层：脚本说安全，Agent 在血缘之外找到一个会坏掉的消费者，人确认它真实存在，先修下游、再合入。

Key Takeaways

  1. 能证明的别动用判断：凡是事实来源能证明的事，让脚本证明，又干净又便宜。
  2. 脚本管事实，Agent 管判断，人管受保护的决定：合入要检查通过与评审批准同时点头。
  3. 已登记的血缘不是全部的血缘：Agent 的价值，在于走查代码找到记录之外的消费者。
  4. 没找到不等于不存在：Agent 只能说在搜过的地方没找到，永远不能声称一切安全。
  5. 漏检与误升级要一起量：只防漏检的关卡会把一切推给人，并没有省下时间。

1. 问题：PR 以机器速度到来，评审还停留在人的速度

演讲从一张看似无害的 PR 切入：它改动数据管线里一张表的模式，在 CI 里全绿，测试通过，lint 也满意，一切看起来都干净。问题是：它真的可以合入吗？这样的改动仍可能破坏下游——冲掉新鲜度 SLA、打断三个团队之外从未露面的消费者，或者暴露本不该被触及的数据。CI 通过与变更真正安全之间的空隙，就是演讲者团队每天要填补的空隙。

范围先说清。AI 编程助手让开 PR 变得廉价：一条新查询、一次模式变更、一项数据授权，现在只要几分钟；助手开 PR 的速度超过任何人类团队。演讲讨论的 PR 是生产数据管线的 PR：模式变更、管线代码、配置变更，以及授予他人数据访问权的授权。数据平台团队负责评审这类 PR，PR 堆积时就堆在他们面前。

“Pull requests to our production data pipelines now arrive at machine speed. But reviewing them safely still runs at human speed.”
PR 以机器速度到来，评审还停留在人的速度。

旧的安全网并非无效。CI 检查加人工评审一直能抓到不少真问题：坏掉的代码、低效的查询、下游破坏或敏感数据泄露的风险。但人工那一半只跑得出人的速度，而且只依赖某个人头脑里恰好装着的上下文：谁在读这张表？它有多大？里面的数据有多敏感？PR 以机器速度到来，而懂得什么能安全合入生产数据管线的人数一点没涨。队伍就在这少数人面前越排越长，事情开始从这里滑落。

2. 答案：三层分工——脚本、Agent 与人

演讲先给出整场答案：三种职责，三个主人。脚本证明能证明的；Agent 判断需要上下文的；人做只有人应该做的决定。这就是混合做法：脚本管事实，Agent 管判断。演讲者特意说明，不想让 AI 评审每一处变更——有些问题本来就有权威答案。

“Scripts prove what can be proven. An agent judges what needs context and people own the calls only they should make.”
脚本证明能证明的，Agent 判断需要上下文的，人做只有人能做的决定。
■ 混合评审员（Hybrid Reviewer）：脚本、Agent 与人三层分工的 PR 评审系统，脚本管事实、Agent 管判断、人管受保护的决定。

第一层是确定性脚本，对照模式注册表或数据目录这样的事实来源做检查。检查失败，CI 变红，PR 被拦下，直到修好。第二层是 Agent。Agent 的规则会告诉它第一层已经覆盖了什么，于是它集中精力处理那些检查抓不到的风险。它评审 PR、给出风险评分，然后批准，或升级给人。两层评审同一份 PR；合入既要求检查通过，也要求评审批准。

这样分工也压低了 AI 的成本。AI 只用在判断上，不必重新发现脚本一查便知的事实。演讲全程有三个线索可追：脚本管事实、Agent 管判断、人管受保护的决定，结尾还会回到这三条。

3. 一张贯穿全场的 PR：加一列，拓宽一列

为了讲具体，演讲拿出一份 PR，跟完全场。这份 PR 改动数据湖里一张表的两处：新增一列，并把已有的一列从整数拓宽为大整数。这类 PR 团队天天见。上游有一张源表，注入管线从中读取，写入数据湖里的表——就叫它我们的表。

第一处变更：源表多了一列，PR 让注入把这列带进湖里的表。第二处：把已有列的类型从整数拓宽为大整数，好容纳更大的值。单看这处变更完全无害——拓宽类型大约是最安全的模式变更。

但只要一列发生变化，真正的问题就是：下游谁在读它？有些读者登记在血缘工具里，所以团队知道它们。但第二个问题要留在脑后：这些就是全部了吗？记住这张图，PR 每向前走一步，演讲都会回到这张图。

■ 血缘（Lineage）：记录一张表、一列数据被哪些下游任务读取的关系图谱。

4. 第一层：确定性检查只证明注册过的事实

第一层是脚本，整项工作就是核对实时系统里的事实——代码本身说不出来的事。先看其中两项检查，以及它们对这份 PR 的结论。

第一项，数据契约。PR 改动模式时，脚本把模式与键对照事实来源——模式注册表——比对。对这份 PR，问题很简单：新列在上游是否真实存在，如注册表所登记的那样？存在，检查通过。

■ 数据契约（Data Contract）：以模式注册表为权威来源，核对表结构与键是否与上游一致的检查。

第二项，标签要求。每张表都要有负责人，任何个人信息都必须在目录里打标签。脚本直接查目录：这张表有负责人吗？有。个人信息打标签了吗？打了。再次通过。

两项中任何一项失败，都没有商量余地，也不涉及模型。CI 像任何其他检查失败时一样变红，PR 被拦下，直到修好。

4.1 下游影响与性能也在第一层

契约与标签只是第一层的两项检查。另外两项看下游影响与性能：越过表本身，看下游会发生什么，以及任务是否还能按时跑完。

第一项，血缘爆炸半径。列发生变化时，脚本沿着血缘工具记录的该列全部下游任务走一遍，只问一个简单问题：其中有任务会坏掉吗？这是对照真实系统的真实检查。但要注意演讲者画出的边界：它只能看到血缘记录里的东西，它对下游的视野与那份记录的完整程度完全一致，不多不少。

■ 爆炸半径（Blast Radius）：一次变更波及的全部下游任务范围。

第二项，性能。正确的变更也可能太慢或太贵。CI 性能测试用与生产相同的数据量、在预发布环境以模拟数据跑这处变更。合入之前就能知道两件事：集群是否为这项任务配得合适，以及任务是否还能赶上新鲜度 SLA。这类问题否则会在几周后以事故的形式出现。

■ 新鲜度 SLA（Freshness SLA）：数据任务必须在约定时间内产出新鲜数据的服务等级约定。

回到这份 PR。数据契约检查问注册表，新列是否真实存在于上游：存在，通过。血缘爆炸半径检查走遍拓宽列的全部已登记消费者：没有一个会在列从整数变大整数时坏掉，看起来都正常。标签通过，性能通过。每一项检查都是绿的。就脚本所能看到的而言，这份 PR 是安全的——但演讲者特意斟酌了措辞。幻灯片上的每一句话都是关于已登记图景的陈述：系统有记录的任务与列。而这不是全部的故事。

“As far as the scripts can see, this PR is safe.”
就脚本所能看到的而言，这份 PR 是安全的。

5. 第二层：Agent 走查代码，找出血缘之外的消费者

现在看 Agent 如何面对 diff。PR 描述与提交信息解释作者的意图，但意图永远不能抵消一个真实的发现。如果描述说安全而代码说不是，以代码为准。

“If the description says it is safe and the code says otherwise, the code wins.”
描述说安全而代码说不安全时，以代码为准。

文件工具让 Agent 在整个仓库里读、搜、列出文件。它跟随变更走出 diff，进入管线定义与授权，寻找作者可能漏掉的关系。

但这些只是仓库工具。Agent 不能查询实时目录、血缘工具或生产状态。实时事实仍是第一层的工作。Agent 推理的对象是代码。为什么要为一次模式变更走查代码？因为已登记的血缘不是全部图景。

■ 代码走查（Code Walk）：Agent 沿着仓库里的管线定义与授权记录，逐段追踪数据消费者的搜寻方式。

规则划定判断的归属。规则按 PR 的变更类型配置，并且知道第一层已经覆盖什么。它们盯住查询反模式、敏感数据请求，以及血缘之外的消费者。举例：一次无分区的交叉连接可以跑得正确，却照样拖垮集群；一项授权看起来平常，却照样打开敏感数据。对模式变更，Agent 走查仓库里的管线定义与授权，找出未登记的消费者——这是一项人本来要手工做的枯燥搜索。

回到这份 PR。第一层说，拓宽列的已登记消费者看起来都正常。现在 Agent 走查代码，发现了一个血缘从不知道的任务。它就在仓库里：它从湖里的表读拓宽后的列，却从未登记进血缘——这正是第一层检查看不到它的原因。而这个任务取到值后写进另一张表，那张表里的列仍然是整数。顺着走下去：我们的列是大整数，第一个超过整数上限的值一到，那次写入就会失败。一处有效的模式变更，CI 全绿，通过全部已登记检查，下游任务照样坏掉。Agent 在评审意见里把整条链与推理原样标出，让人能一眼看到从我们的列到失败写入的完整路径。

血缘为什么漏掉这个任务？因为企业数据世界很乱。工作负载跑在不同的查询引擎上，每个引擎都要自己发布血缘；有一个不发布，这段关系就从图景里消失。没有任何一个目录能自动看到一切。已登记的图景有用，但不是全部图景。

5.1 代码走查的边界：找不到不等于不存在

演讲者不想把代码走查说得过头。它确实有用，但看不到一切。Agent 能搜索仓库里的东西：管线代码、授权，以及在那里定义的、读取我们表的任务——未登记的任务就是这样被找到的。但大量数据使用发生在代码库之外：有人手工跑的临时查询、仪表盘，这些对仓库搜索完全不可见。

外面还有消费者，无论 Agent 多仔细都不会出现。所以团队让 Agent 对这个限度保持诚实：如果它什么都没找到，它不能说不存在下游消费者，只能说在它搜过的地方没找到。没找到不等于不存在，Agent 永远不能声称一切安全。

“None found is not the same as none exist and the agent never gets to claim an all-clear.”
没找到不等于不存在，Agent 永远不能声称一切安全。

Agent 走查完代码，到底产出什么？一份与优秀人类评审员给出的评审同样形状的评审。

6. Agent 的产出：评论、评分、批准或升级

第一，针对关键行的行级评论，每条附带推理。不是含糊地说看起来有风险，而是这一行改动了这列，这是读取它的任务。第二，风险评分：发现的问题有多严重。严重程度决定下一步。

■ 风险评分（Risk Score）：Agent 对所发现问题的严重程度打分，分值决定批准还是升级。

然后它做决定。没有严重风险，它可以批准；有需要人的风险，它升级给人，评论与推理一并送达，让人带着上下文调查，而不是从零开始。

至于合入条件，要说清楚：第一层检查必须通过，评审必须批准——无论是 Agent 批准，还是升级后由人批准。两者都得点头。再看这份 PR 的结局。

同一张图。已登记消费者看起来正常，代码走查发现一个未登记任务，把拓宽后的列写进一列仍是整数的表。Agent 发现真实的下游破坏，风险评高分，带着整条链升级给人。人做 Agent 做不到的那部分：Agent 只推理仓库，看不到这个任务是否真的在生产运行。人类评审员核查后确认，Agent 发现的消费者确实在运行、确实活跃。这不是理论风险。PR 等了一等；修复不在拒绝变更，而在顺序：先更新下游表，让它的列能容纳更宽的类型，然后 PR 才合入并部署。没有事故。第一层的脚本说安全，Agent 找到空隙，人做了决定。

7. 三类变更永远升级，Agent 只标记、不放行

这不是一次性事件。大多数变更 Agent 可以自行清除：检查通过、Agent 对自己的结论有信心时，它自己批准。但有一整类变更，Agent 无论听起来多自信都不能说批准。

第一类，触及敏感数据的授权。谁能接触敏感数据，是团队希望每次都由人来做的决定。第二类，看起来改变意图而不只是改变机制的迁移。如果一项变更改变数据的含义而不只是它如何移动或存储，由人决定。第三类，Agent 对自己的结论没信心。它不能因为没有具体的东西出错就四舍五入成批准。

在这三种情形下，它的工作只是浮现风险与推理，决定权留在人手里。

8. 反馈闭环：人的纠正每周变成规则

一份 PR 讲完了。这套评审在所有 PR 面前站得住吗？它又如何随时间变好？从 Agent 的结论与评审意见里的推理开始。一个人回复，同意或不同意，并解释原因。解释才是让反馈有用的东西，而不只是一张赞成票。

这些回复每天收集。值班人员每周读一次反馈，手工更新评审规则。规则塑造下一次评审。演讲者承认，今天这仍是手工的：没有任何东西自我再训练，也没有任何规则自动改变。团队有个想法，让事故调查 Agent 帮忙做每周这一轮，但还没建成。没有反馈，每次规则改动都会是猜测。

看一个人类纠正 Agent、反馈改进下一次评审的真实例子。注意角落的标签：这是另一个例子，不是那份模式变更 PR。一列在源数据库里被标为个人信息；但数据落进湖里之前，注入管线已经把它加密。PR 提议在湖里把它标为非敏感，即便上游数据仍是个人信息。

■ 个人信息（PII）：可识别到个人的数据，受更严格的访问与标注管控。

Agent 标出了它。从 Agent 的位置看，上游说个人信息，非敏感标签看起来就错了。作者反驳，请 Agent 看看其他表上类似的列已经如何分类，而不是只凭上游标签。人类同意作者：写入前加密，让这列的非敏感标签说得过去。这类纠正正是教会规则变聪明的信号：下次类似的列再来，这段上下文可以拦住一次不必要的升级。

但要小心：这取决于具体那条管线在写入前加密，而不是一条通用规则——加密并不总能让数据变成非敏感。

9. 衡量评审员：漏检率约 2%，误升级没有干净数字

怎么知道评审员是不是真的做得好？看两类错误：它批准的坏 PR，和它不必要地推给人的好 PR。这个矩阵分出四种可能。

好 PR 获批与坏 PR 被升级，是两种正确结果。坏 PR 获批是漏检，很危险，因为变更会发布。好 PR 被升级是误升级，耗费人的时间。一道什么都升级的关卡或许能避免漏检，但并没有减少评审负担。

■ 漏检（Miss）：本应升级却被批准的坏 PR，变更随之发布。

截至 2026 年 8 月 31 日，团队的漏检率约为 2%，多数源于规则里的空隙，而非判断失误。误升级没有一个干净的单一数字；最主要的成因是缺少上下文，就像刚才加密列的例子。

“A gate that escalates everything may avoid misses, but it has not reduced the review load.”
什么都升级的关卡或许能避免漏检，但并没有减少评审负担。
■ 误升级（False Escalation）：本可批准的好 PR 被不必要地推给人，耗费人的时间。

漏检带来新规则，误升级指出评审员需要的上下文。这里就有一处漏检。同样注意标签：这是另一个例子，不是那份模式变更 PR。

有一份数据的公开副本，其中几列将被重新打标签；一个下游读者正从公开副本读这些列。隐私部门把这些列重新标为个人信息后，它们移进一份受限更严的副本，从公开副本里消失。这次重新打标签看起来没问题，合入了。但没人检查下游是否还有东西在从旧的公开副本读这些列。有。列一消失，那个读者就坏了。这就是一次漏检：一份本应升级的 PR 获批了。

这不是判断失误，是规则里的空隙——一个从没人写下来的边角情形。于是它变成一条新规则：当一列被重新标为敏感时，去代码库里搜，还有谁在从即将失去它的副本读它。漏检就是这样被找到、变成新规则的。

10. 结果：约 60% 的 PR 无人评审合入

把一切收拢。还记得开头那份 CI 全绿的 PR 吗？它身上发生了三件事：第一，脚本证明了事实来源能证明的事——契约、标签、已登记血缘与性能全部通过。第二，Agent 读了代码，找到脚本看不到的东西：一个血缘从不知道的任务，静静等着在一列拓宽时失败；它标出整条链并升级。第三，人确认那个任务是活的，先修下游表，PR 再合入。没有事故。而在这背后，评审员不断变好，因为人做的每一次纠正都可能变成一条规则。

这些结果截至 2026 年 8 月 31 日。演讲者问：这套办法管用吗？可以。约 60% 的数据管线 PR 在无人评审的情况下合入；人工评审工作量减少约 75%；Agent 具体、有推理的评论帮助聚焦评审，而不是让人从零重建每处风险。省下的时间约为每月 132 个工程小时；与这些 PR 相关的事故减少约 30%。

这不等于无人评审。受保护的决定按设计仍会到人手里。目标是减少评审工作，不是取消问责。

“The goal is less review work, not removing accountability.”
目标是减少评审工作，不是取消问责。

11. 做错了什么：两层彼此看不见，与三条经验

这些是结果。现在看架构上做错了什么。第一层与第二层是两个独立系统，各自独立触发、并行运行，各自产出自己的结果。建的时候这看起来是显而易见的设计，但任何一方都看不到另一方的通过、失败或故障状态。第二层知道脚本配置上覆盖什么，不知道它们运行时发生了什么。合入仍然要求检查通过加评审批准，但没有任何一个系统掌握完整的运行时图景。

Agent 也不能调用实时的第一层检查。它的工具只读、搜、列仓库文件。如果判断需要来自实时生产系统的一个实时事实，它自己取不到这个事实。一边完不成时，就等人类。没有自动兜底。这些是当下的限度，也正是提案的动机。

下一页是平台团队正在探索的方向：一个入口点。这是一个提案，不是今天跑着的东西。左栏是当前设计，右栏是想去的地方。分类器先看整份 PR，再决定哪些变更分开评审、哪些一起评审——这是整份 PR 的决定，不是每份文件独立分流。Agent 还会把第一层检查当作可调用工具，与仓库工具并列；判断需要实时事实时，它可以请求相应的检查。

目标是一个对整份 PR 有完整视野的系统。还没建成。所以这只是方向，不是结果。

“We haven't built this yet. So, it's a direction, not a result.”
还没建成，所以这只是方向，不是结果。

最后是演讲者会带走的三条经验。第一，先做确定性评估：如果一件事能对照事实来源证明，就让脚本证明。别把判断花在是非分明的事实问题上。这不只是更干净，也更便宜：脚本证明的每个事实，都是永远不需要 AI 的评审工作，运行成本就这样降下来。

第二，只标记、不放行——不是对每份 PR，而是对真正吓人的变更：敏感授权、意图迁移、低信心结论。在那里，Agent 的工作止于浮现风险与背后的推理，决定每次都留在人手里。第三，数一数误升级。什么都升级的关卡并没有真正帮任何人省时间，只是在搬运工作。误升级的代价，要和漏检一样去量度。

演讲从一份 CI 全绿的 PR 开始，问题是 PR 以机器速度到来、而懂得安全合入的人太少。团队建了混合评审员：脚本管事实、Agent 管判断、人管受保护的决定；带着一份 PR 走过三层，看它变轻而没有变得无人负责，看它如何从纠正中学习；讲了做错的地方，留下三条经验：便宜证明、吓人变更只标记不放行、误升级也要计数。

“Prove what you can cheaply. Flag and never clear the scary changes. And count the false escalations.”
能便宜证明的就便宜证明；吓人的变更只标记、不放行；误升级也要计数。

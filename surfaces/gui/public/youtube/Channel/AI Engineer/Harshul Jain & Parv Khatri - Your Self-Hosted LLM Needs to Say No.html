当 40 个请求在两秒内涌向你自己托管的模型，推理层会照单全收——直到先到的请求被后来的埋掉。Harshul Jain 与 Parv Khatri 的论点是：自托管推理真正的缺口不在引擎，而在门口——没有任何一层在问“还有位置吗”。这份报告按演讲顺序还原四件事：推理为什么一次 yes 就是一份占用到结束的承诺；两次公开事故的后续行动为什么都指向更早做决定；放行、缓一缓与拒绝三个答案各自怎么回、客户端又该怎么接；以及怎么证明你的准入策略真的管用——用 goodput 计分，用 admit-perf 把策略声明的信号与跑出的结果全部留档。

Key Takeaways

  1. 一次 yes 是占用到请求结束的承诺：预填充建起 KV 缓存，解码一路写一路长大，内存不到请求结束不释放。
  2. 决定只能发生在说 yes 之前：放行（200）、缓一缓（503 + Retry-After）、拒绝（429 管调用方、529 管池子），仅此三个答案。
  3. 计数不是成本：限速管公平不管 GPU；按会话准入、按 KV 内存与 token 数估算成本，才能在占用前说不。
  4. 规则越贵越慢：阈值几十微秒、优化器 5 秒——40 个调用 2 秒到齐时，5 秒的决策到场时派对已经散了。
  5. 计分要算分母：goodput = 达标请求 ÷ 所有到达的请求；拒绝 95% 再把剩下 5% 伺候好，goodput 只有 5%。

1. 推理：模型写答案时才知道答案有多长

演讲从最底层讲起。推理就是有人发一个提示词、模型回一个答案的时刻：提示词进来，模型一个 token 一个 token 地写答案——token 大致相当于一个词。它先写第一个词，再用这个词选第二个，再用前两个选第三个，如此继续；它不能一次写完，因为每个词都依赖前一个词。写完的词流回给提问的人，一次提示词加一次答案就是一个请求。有一个细节要先记住：模型事先不知道答案会有多长，只有写到最后一个 token 时才知道。这在几分钟后会变得关键。

模型从不直接挂在网上。每个请求要走一条短管线：先到你的应用或 Agent，再到 API 网关——网关核对 API 密钥、计数；然后路由器挑一个副本，也就是模型的一份运行拷贝；最后请求落在推理引擎上。常见的引擎有 vLLM、SGLang、TensorRT。引擎把模型权重载入 GPU，把许多请求编成一批让 GPU 保持忙碌，并为每个请求维护一份 KV 缓存——白话说，就是请求在写答案的过程中不断积攒的内存；答案越长，这份内存越大。把这张图记在脑子里：每个框都会做某种决定，但有一个决定缺失了。

■ 推理（Inference）：提示词发给模型、模型逐词生成答案并流回的过程；一次提示词加一次答案就是一个请求。

■ KV 缓存（KV Cache）：请求在生成答案的过程中积攒的内存；答案越长，缓存越大，直到请求结束才释放。

每套部署都有上限，来自三个互相拉扯的目标：质量是模型多大、多准；延迟是首个 token 多快到达、之后每个 token 多快；吞吐是 GPU 同时能伺候多少请求。老话说好、快、便宜只能选其二，这里也一样，三者不能全要，每种产品都得选两个。交互聊天要质量加延迟——用户对这两项最敏感；异步 Agent 要吞吐加质量——质量不够就得重做，而后台任务的重做非常贵；自动补全这类高并发实时系统则要延迟加吞吐，可以牺牲质量，因为补全不需要昂贵的模型。不管放弃哪个角，在满足 SLO 的前提下，能扛的最大负载仍然存在——比如这套部署同时只能接 8 个请求。

平常的一分钟里你永远注意不到这个上限。但 40 个请求在同一两秒内到达时，情况就变了——这不是假设，它在全球最大的服务商身上都发生过。更重要的是，到门口的流量本身已经变了：以前是一个人在聊天，一次发一个请求，中间隔着几秒阅读时间，答案慢慢回来；现在是编程 Agent 接管了：一次“修这个失败的测试”，要读约 14 个文件、跑约 10 个测试，合起来就是 40 到 50 次 LLM 调用，其中有的长、有的短。集群必须对每个调用做出明智的取舍。

一个任务，四十个请求同时到。Agent 说“修这个认证测试”，引擎按到达顺序照单全收，8 个槽位在跑、32 个在排队先到先得——而 Agent 最先需要的那四个调用，排在了队尾。问题不只在量大，还在于顺序错了。

为什么这是“我们”的问题，而不是只属于 OpenAI、Anthropic 这些自建推理基础设施的大团队？因为有团队出于隐私要把模型托管在自己的 GPU 上，出于成本也要这么做，同时还得保护这些 GPU 不被烧穿——他们必须在整个推理生态里有效决定服务哪些请求。而门口流量的性质已经变了，旧的“一个人一次发一个请求”的假设不再成立。

2. 两次公开事故，后续行动都指向前门

2023 年 11 月 8 日，OpenAI 在经历一天异常沉重的流量后，路由服务器耗尽内存，开始健康检查失败。团队加了更多副本，又不得不回滚。最后的出路是削减入站流量，再慢慢 ramp 回来。他们的后续行动是：优雅的负载 shedding。2026 年 1 月 21 日，Anthropic 的 Sonnet 4.5 层级先变慢，随后约 90 分钟里开始返回错误；给出的原因很简单：算力不够应付需求。他们的后续行动是：更早发现容量上限。

把这两份后续行动倒推回去，它们指向同一个地方：前门。两份后续行动没有一份说“我们需要更快的引擎”，说的都是同一件事的不同说法——更早决定哪个请求进门。管线补上缺失的那一步就成了：客户端、准入层、队列、路由器、引擎；客户端永远不直接对着引擎或队列说话，中间总有一个准入环节。附录里还链接了更多事故，演讲者请有兴趣的人自行去读。

3. 一次 yes 就是一份承诺：放行、缓一缓、拒绝

推理分两个阶段。先是预填充：引擎读提示词、建起请求的 KV 缓存；然后是解码：引擎一个 token 一个 token 地写答案，每写一个，缓存就长大一点；全部内存一直保留到请求结束。所以一次 yes 不是一个瞬间，而是一份持续到请求整个生命周期的承诺。看 A、B、C 三个请求：A 答案短，B 答案长，C 又短——C 要等多久没人知道，因为 B 已经占住了内存。接纳每个请求都有成本，准入本身就可能让你错过 SLO。

“A yes is not a moment. It’s a commitment that lasts the request’s whole life.”一次 yes 不是一瞬间，而是一份持续到请求结束的承诺。

内存满了对 GPU 意味着什么？每个运行中的请求都在让缓存长大，总内存一路爬升；到顶时引擎有三种切法：等一等、把请求换出到等待态，或者直接说伺候不了、返回错误。每一种都会拖慢处理、错过 SLO，同时浪费内存。准入就是在请求占用任何 GPU 内存之前做的决定，只有三个可能的答案：放行是现在就开始；缓一缓是接受但让它等；拒绝是现在不行。直到策略说放行之前，请求不花你任何成本、不占任何 GPU 内存。

先看放行。服务器回 200，响应开始流式传输；那一刻引擎里同时发生三件事：为整个提示词提交 KV 缓存，请求加入运行批次、与其他请求一起每步解码一个 token，并一直占住内存，直到完成或客户端断开。这是第一部分那个承诺的 HTTP 形式——所以准入决定必须发生在 200 之前，绝不能在之后。客户端这边，如果我们在写 Agent，该这样处理 200：盯着流而不是状态码——超时时钟要在首个 token 到达时才启动，而不是发请求时，因为重载下光是预填充就可能花几秒；如果决定放弃，要真的关掉连接——服务器只在请求完成或客户端断开时才释放 KV 缓存，一个超时却不断开的 Agent 还在占着 GPU 内存；第三，流可能中途失败，那时没有状态码，只剩半个答案，得自己决定重试还是将就。

“200 promises to start. It’s not a promise to finish.”200 承诺的是开始，不是完成。

第二个答案是缓一缓：服务器回 503 并带 Retry-After 头，告诉客户端等多少秒。这个数字由策略从引擎里取——比如运行中的批次还要多久才能结束并腾出足够的缓存。容量很快会回来时才缓——那是一次突发，不是一条趋势；如果容量一时半会回不来，缓一缓只是在把问题往后踢，那就该老实拒绝。Agent 这边处理缓一缓很简单：睡够 Retry-After 的时间再加一点随机抖动，然后重试。抖动的意思是多加一小段随机延迟，让客户端不要在同一时刻全回来。看看服务器在没有 Retry-After 时看到的景象：10 次重试，每家 Agent 自己挑延迟——通常是零——于是全在同一刻回来，40 个调用就变成了 80 个。有了 Retry-After 和抖动，重试就摊开在服务器要的时间窗口里。

第三个答案是拒绝，两个码对应两种原因。429 是请求太多：这个客户端或 Agent 会话用的超过了自己的份额——策略看到了按客户端计的负载、并发调用数或配额，问题在调用方。529 是供应商过载：Anthropic 在用这个码——每个副本都满了，现在谁也进不去，问题在池子不在调用方。Agent 该怎么反应？遇到 429，减少自己的负载，限制该 Agent 同时在途的调用数；遇到 529，越重试越糟——等久一点、换模型或供应商，或者把任务先搁置。无论哪种，都要留一个重试预算：指数退避加抖动，也就是每次失败后等得更久；试几次之后告诉用户发生了什么——因为一个全速重试的拒绝，正是开场那两起事故的成因。

■ 预填充与解码（Prefill & Decode）：预填充读提示词、建 KV 缓存；解码逐词写答案，缓存随之长大，直到请求结束才释放。

■ 重试间隔（Retry-After）：503 响应里带的等待秒数，由策略从引擎状态里取；配合随机抖动，避免所有客户端同一时刻回来。

4. 决策放在入口：唯一不用改引擎的位置

回到那条管线，问每一层同一个问题：这个请求还有位置吗？Agent 说不归我管；网关说我看不见；路由器说不归我管；引擎说我只有在已经说了 yes 之后才知道。准入的盒子就缺在中间。现在有三个可能的安放时刻：入口，就在引擎前面——策略看到请求本身加上引擎暴露的指标，只需要一个代理或网关，引擎原样不动；队列边界，决策发生在引擎调度器挑下一批运行时；解码中途，调度器可以在答案写到一半时暂停某个请求或收回它的缓存。

后面的时刻看得更多，但代价是改引擎调度器——那意味着自己维护一份 vLLM 或 SGLang 的分支，每次上游一变就得跟着改，永远改下去。所以入口是唯一一个能让引擎按出厂状态工作的时刻，演讲其余部分都待在这里。入口处坐着什么？可以把它想成一个函数：输入它对请求的了解和系统的当前状态，输出三个答案之一——放行是请求现在进引擎、内存即刻提交；缓一缓是等一等再回来；拒绝是附上原因的“不”。

要做好这个判断，策略必须同时看到两个视图。请求这边：输入有多长、哪个客户端或租户发的、属于哪个 Agent 会话、有没有截止时间。引擎这边：KV 缓存用了多少、队列里最老的请求等了多久、提示词前缀命中的频率、每个副本池有多满。回头看管线：网关只有左边的视图，引擎只有右边的，没有谁同时有两边——这正是准入必须自成一层的原因。

八个信号可以变成简单的规则：每个信号对一个阈值，越过就推向对应的结果。请求这边：输入太大、装不进剩余内存就缓一缓；客户端或租户超过份额就回 429；一个 Agent 会话同时在途的调用太多就缓一缓；等下去反正会错过截止时间就拒绝。引擎这边：KV 缓存低于高水位就放行；最老的请求等得超过目标就缓一缓；提示词已经缓存过就优先放行——因为伺候它最便宜；每个池子都满了就回 529。一条经验：挑那些以秒为单位变化的信号，比如 KV 使用率，而不是一分钟平均值——编程 Agent 两秒发 40 个调用，一分钟平均值根本注意不到。

5. 计数不是成本：四个选择

大多数团队已有的东西是计数。最简单的想法是在网关做限速：给每个 API 密钥一个预先定好的额度。这对保持客户端之间、租户之间公平很有用，但对保护 GPU 毫无作用——它不随 GPU 或集群上的负载变化。代理上的固定上限近了一步：它数每个副本上有多少请求在途；问题是，一次快速 grep 和一次长规划调用数起来完全一样，而 GPU 的真实容量随每个批次都在变。实践中它大多只是在排队，客户端超时，最后是超时在替你拒绝。两种计数都不知道那 40 个调用是便宜还是贵。

成本感知策略知道：它用引擎的实时状态估算每个请求实际要花多少 KV 内存和多少 token，在请求占用内存之前就说不。简短版就是：计数不是成本。

“Count is not a cost.”计数不是成本。

■ 准入控制（Admission Control）：在请求占用 GPU 内存之前做的决定：放行、缓一缓或拒绝；直到放行之前，请求不占任何内存。

怎么搭建自己的策略？有四个选择。第一是单位：你准入的是什么——单个请求、一个 Agent 会话，还是一个租户？第二是信号：策略盯着什么做决定——KV 压力、队列深度、截止时间余量、预测输出长度都可以，但它必须在系统忙起来时真的动起来。第三是规则：信号怎么变成决定——可以是从几微秒的简单阈值，到花几秒的完整优化器。第四是行动：规则给出决定后怎么办——客户端会受到什么影响，也就是前面说的放行、缓一缓、拒绝。每个选择都限制下一个：截止时间信号只有在请求真的带截止时间时才管用。

先看第一个选择：准入单个请求，还是准入整个会话？假设有两个 Agent 任务，各 20 个调用，位置只够一半。按请求准入：每个任务大约一半的调用进去了，但哪个任务都完不成——每个都在等没进来的调用；容量全用掉了，什么都没完成。按会话准入：会话 A 拿到全部调用、顺利完成，会话 B 得到一个明确的答复：晚点再来。这张图是示意，但逻辑成立：我们的 40 个调用就是一个会话。编程 Agent 发的是会话，可大多数已发表的策略只准入单个请求。

盯哪个信号，取决于你要防什么问题。想防缓存溢出，就盯 KV 压力；想避免白白重算，就盯 KV 用量加缓存命中率——缓存满了没关系，只要它在被复用；想让等待变短，就盯队列深度；想守住延迟目标，就盯截止时间余量；想给长答案留出计划，就预测输出长度。最后一列最值得看：它写着每个信号在什么时候失灵。KV 压力在缓存永远填不满时失灵——记住这一行，第四部分它会回来咬人一口。

信号变成决定有四种办法，从最便宜到最贵。阈值只拿一个数对一个上限：Fluid-WAIT 看 KV 用量，每次决策几十微秒，报告提升 10–20%。双门要两个信号同时同意才行动：CONCUR 看 KV 用量加缓存命中率，不到 100 微秒，报告吞吐是 SGLang 的 4.09 倍——但只在离线测过。优化器把所有队列当成一个大规划问题一起解：QLM 很彻底，但每次决策约 5 秒，报告提升 40–90%。形式界直接算最坏情况：这个请求还能赶上截止时间吗？Chronos 用首 token 时间做界，微秒级延迟，截止时间错过率从 99% 降到 0。

“A 5-second decision shows up after every party is over.”5 秒的决策到场时，派对已经散了。

把成本那一列贴到我们的 Agent 身上：它两秒发 40 个调用，5 秒的决策到场时，每个派对都散了。

■ 双门（Dual Gate）：要两个信号同时同意才行动的规则，如 CONCUR 的 KV 用量加缓存命中率。

■ 形式界（Formal Bound）：用数学算最坏情况的规则，如 Chronos 的首 token 时间界：这个请求还能赶上截止时间吗？

6. 四篇论文，没有一篇正好合身

把四篇论文当作完整的策略看：Fluid-WAIT 准入单个请求，用 KV 用量的阈值，报告提升 10–20%；CONCUR 准入 Agent 会话，用双门，报告吞吐是 SGLang 的 4.09 倍，但只在离线测过；QLM 准入请求，跨所有队列做规划，报告提升 40–90%，每次决策约 5 秒；Kronos 准入请求，用截止时间余量的形式界，截止时间错过率从 99% 降到 0。成就都很了不起，但每篇用的模型、引擎与工作负载都不同——不要把它读成排行榜。

对这个房间真正重要的问题是：有没有一篇合身编程 Agent？答案是没有。把每篇论文放到两根轴上：一根是它优化什么——截止时间还是吞吐；另一根是它准入什么——单个请求还是 Agent 会话。编程 Agent 需要的策略是：准入整个会话、在线处理真实流量、跑在你没改过的引擎上——没有一篇干净地落在那里。CONCUR 不用改引擎，但只在离线测过；Continuum 在线，但要改引擎；ThunderAgent 最接近：按 Agent 准入、在入口处、按程序持有 KV。所以实际做法是挑最接近的一篇，再自己搭。

决策树帮你挑：请求带截止时间吗？带，就上某种形式界，微秒级延迟。没有，再问：KV 缓存在峰值会填满吗？会，就用双门或 KV 阈值——同时要能识别缓存前缀的复用。不会，就在队列层面设阈值。策略定下来，就到了第四部分：怎么证明它管用。

7. 计分：分母要算被拒绝的请求

既然没有已发表的策略能干净合身，你要么采用一篇、要么自己搭——然后得证明它真的管用。测试策略需要四样东西：集群、策略、轨迹与分数。集群是先量容量：不做任何准入时，副本自己能扛多少负载；此后每个负载水平都写成这个数的倍数。策略是它读哪些信号、用哪些上限、说不时做什么。轨迹是真实流量的记录：拿编程 Agent 的流量重放，从一半容量 ramp 到两倍容量。分数是同一条轨迹跑两遍——一次有策略、一次没有——再比较结果。

分数是最容易错的地方。推荐的分数叫 goodput under admission：分子是达到 SLO 的请求——答案准时开始、token 之间从没有卡太久；分母是所有到达的请求，包括被拒绝的。分母为什么这么重要？试试这个：拒绝 95% 的流量，把剩下 5% 伺候得完美无缺——只算放进来的请求，SLO 达成率是 100%，看起来棒极了，直接发布吧。但 goodput under admission 说是 5%。只算留下来的请求，削峰看起来是免费的；其实不是。

“Shedding looks free if you only count what you admitted. It is not.”只算放进来的请求，削峰看起来是免费的——其实不是。

■ Goodput（有效产出）：达到 SLO 的请求 ÷ 所有到达的请求（含被拒绝的）；只算放进来的请求会把削峰的代价藏起来。

第二件要做对的是工作负载：基准只有像真实流量时才说明问题。重放带扇出、重试与会话的 Agent 轨迹，而不是均匀随机到达；负载写成已测容量的倍数，从一半扫到两倍；截止时间写成无负载延迟的倍数。记住：一个从不超过容量的基准永远测不出策略，因为策略从不需要说不。

“A benchmark that never goes past capacity never actually tests the policy.”从不超过容量的基准，永远测不出策略的好坏。

第三件是披露：每份准入结果应该披露七件事——负载是已测容量的几倍；截止时间是无负载延迟的几倍；信号是否存活——没有一篇论文报告这个；跑了多少次、结果波动多大，而不是一次走运的运行；每个参数从哪来——在这套配置上调过、从别处借来，还是留在默认值；被拒绝的请求算不算进 goodput 的分母；完整配置——模型、引擎、版本、硬件、工作负载、SLO 与基线。这不是要求谁改变评估方式，只是要求说清楚自己做了什么。读论文时拿它当清单，给自己的策略做基准时也一样。

手工做齐七件很痛苦，所以他们建了一个工具，默认就把这些都记下来：admit-perf，一个仓库里两样东西。生产里它是一个库，放在 vLLM 或 SGLang 前面，为每个请求在入口处决定放行、缓一缓或拒绝；基准里它是一个 harness，在真实 GPU、真实引擎上跑任意策略，报告策略的代价。两边调用同一个函数 policy.decide——你基准测的策略，就是你部署的策略。建它的原因之一是，在他们对照的 16 篇论文里，没有两篇共享同一基线、引擎、工作负载或 SLO，横向比较无从谈起。

它的命令行有五个：infra up 在真实 GPU 上启动一个真实的 vLLM；infra smoke 检查它确实在服务；bench 把每个策略各跑若干次；bench compare 告诉你哪个策略赢了、赢了多少；infra down 把一切关掉、让你不再付钱——这是演讲者最喜欢的一个。部署与基准刻意分成两个命令：加载模型要花几分钟，而每个策略必须面对完全相同的部署；如果每个策略之间重新部署，你就改变了自己想保持不变的东西。部署是常量，策略是变量。

策略还必须声明它读的信号：这是 admit-perf 对付上面那个陷阱的办法。一个 KV 缓存阈值策略要声明“我需要 kv_used_fraction”；如果引擎报不出这个信号，运行在启动时就报错停下。没有这道检查，缺失的信号会被读成零——一个永远看到零的 KV 阈值策略会放行一切，悄悄退化成无准入基线，而结果看起来完全正常。看不见自己信号的策略，应该大声失败，而不是悄悄失败。

“A policy that cannot see its signal should fail loudly, not silently.”看不见自己信号的策略，应该大声失败，而不是悄悄失败。

■ admit-perf：演讲者团队的开源工具：生产里是 vLLM/SGLang 前面的准入层，基准里是在真实 GPU 上跑策略的 harness；两边共用同一个 policy.decide。

每个决策都会连同它看到的状态一起记下来；每次运行留下一个文件夹，里面有四份文件：manifest.json、summary.json、decision.json 与 outcome.json，可以打开检查。

8. 实测：信号比阈值重要

下面是在真实 GPU 上的四行结果。配置是 Qwen2.5-0.5B 模型、A10G 显卡、一次最多 4 个序列、80 个请求以每秒 15 个到达、重复两次。不做准入时，首 token 时间的 P95 约 2285 毫秒、上下波动约 725 毫秒；队列上限策略（最多等 2 个请求）只放行 63.1%，P95 降到约 951 毫秒——2.4 倍的提升，goodput 完全相同，都是 0.319。削掉 37% 的请求，尾延迟降了 2.4 倍，goodput 一点没少。

同一份运行里还有三行值得逐行读：无准入放行 100%，P95 约 2285 毫秒、波动 ±725 毫秒；队列上限放宽到最多等 8 个，放行 88.1%，P95 约 1668 毫秒，goodput 反而跌到 0.300——放进来更多，分数却更低；收紧到最多等 2 个，放行 63.1%，P95 约 951 毫秒，goodput 回到 0.319。被拒绝的请求反正也会错过截止时间；没人管的排队不是慢，是不可预测。

但演讲者最喜欢的是另一组数字：同一份运行里，KV 缓存用量峰值只有 0.5%，从来没动过；队列却深到了 24 个。小模型上，KV 缓存相对四个短序列来说太大了，永远填不满；全部压力都出现在了队列里。一个看 KV 压力的策略会读到一条平线、放行一切。哪个信号扛着压力，取决于你处在什么工况——这正是策略要声明自己需要什么信号的原因。

今天就能试，不需要 GPU：有一个假引擎，说着 admit-perf 用的三个端点，在负载下也会像真引擎一样忙起来，整套东西可以在笔记本上跑通。如果策略是你自己的包，admit-perf 会自动发现它，不用改仓库。欢迎贡献：新策略、工作负载、引擎适配器或指标。

如果只记住一页，就记住这一页：在推理集群里接请求时，你需要一个在入口处早点说不的机制——在说 yes 之前，在请求进 GPU、占走你的内存之前；还要处理好准入策略返回的那些错误码。演讲由此收束：他们的工作都源于《LLM Inference at Scale》手册的调研——发现缺口后做了 admit-perf；源码公开，欢迎去试验、提 issue、做贡献，目标是建好自己的准入策略、跑好基准，并确信它能让集群保持稳定。

“Say no early. Say it clearly. Check that your no ever fires.”早点说不，说清楚，还要确认你的不真的生效过。

“At some point, a harness becomes the product.”

Agent 没坏，坏的是它周围的一切

The Agents Were Fine. Everything Around Them Broke.

Speaker: Joey Wang, Harvey

Event: AIE Code Summit SF 2026（线上）

Length: 12 分 58 秒

Source: youtu.be/ktbAVYsAxpk

Technical Monograph · 精读报告 发布 2026 年 11 月 10 日 生成 2026 年 11 月 17 日

Harvey 内部的云端 Agent 平台 Spectre 在一个月内由约 10,000 个任务增长到约 45,000 个，Agent 撰写的 PR 合并超过 10,000 个。本报告按演讲顺序还原其演进：平台不再与 Claude Code、Cursor 等 Agent 应用竞争，而是作为云端层运行它们，统一持有密钥、真实技术栈、警报与工单与同一套规则；代码写完后的六个环节——触发、端到端验证、跟进循环、评审策略、提醒与合并——决定了 Agent 能否把活干完，其中跟进循环覆盖了十月合入后端 PR 的五分之四；一条“人能点的，Agent 都能调”的规则使命令行月启动任务从 1 个涨到约 6,500 个，也两次引发过载：900 个 Agent 追同一只虫、一名工程师三小时启动 950 个任务填满集群，公平启动队列把任务列表的 p95 延迟从 1.7 秒降到 71 毫秒，十一月四日任务量翻倍至约 4,400 个、完成率反而更好；瓶颈随之移到合并环节，全公司 PR 单月涨约 60%，合并耗时超过一小时，至今未解；增长最快的已是自动化，从五月约 2,700 个涨到十月约 13,000 个，而只有二十分之一的合并带有“证明它能用”的证据。

Key Takeaways

  1. 写代码不是瓶颈，代码写完之后才是。触发、验证、评审与合并，以及密钥、真实环境与容量，决定了 Agent 系统的上限。
  2. 不要与 Agent 应用竞争，要运行它们。云端层统一持有密钥、真实技术栈、警报与规则；到某个时候，脚手架本身就成了产品。
  3. 只建一个环节，就建跟进循环。CI 失败后自动读错再推修复；十月合入后端的 Agent PR 中，五分之四走过它。
  4. 能力必须同时是接口，入口必须同时设上限。人能点的，Agent 都能调；但一次 900 个 Agent 追同一只虫、一人三小时 950 个任务填满集群都表明，没有上限的入口本身就是故障。
  5. 瓶颈会移动，证明必须前置。PR 单月涨约 60% 后合并成为新瓶颈；今天只有二十分之一的合并带有“证明它能用”的证据，事前证明是下一道关。

1. 规模现状：每分钟一个 Agent 背后的平台

演讲的起点不是模型能力，而是一个看似平静的数字：上个月，平均每分钟启动的 Agent 超过一个。上线以来，Agent 撰写并合并的 PR 超过 10,000 个，覆盖 7 个应用仓库。任务量从五月的约 10,000 个涨到十月的约 45,000 个，月活用户从约 30 人涨到约 460 人。这些数字说明的不是某次演示的成功，而是平台已经成为日常工作的一部分。

“On average, more than one agent has started every single minute of the last month.”上个月，平均每分钟启动的 Agent 超过一个。

用法也超出了最初的设想。写代码、修 bug、写测试、搭新服务、改配置这些预期用途之外，Agent 还在写内部文档、整理与外部供应商的往来邮件、从合同里提炼并执行任务，以及把研究论文转化成可供实验的任务清单。最意外的一例：市场团队请 Agent 评估产品是否符合 HIPAA（美国医疗数据隐私法规）的合规要求。演讲者说，这不只是少数人在试水，而是全公司在用 Agent 处理真实的工作。

2. 基础设施下沉：为什么 Harness 会演变为核心产品

报告的中心论点出在开场后不久：难的不是 Agent 本身，而是 Agent 周围的一切。给笔记本上的 Agent 一个任务很容易；真正的难题在它身后——密钥、真实技术栈、监控告警、权限、复现环境、持久身份、审计日志、数据留存，这些必须有人管。单个人偶尔用一次可以不管，但全公司每分钟启动一个 Agent 时，这些问题都会变成瓶颈。

Harvey 为此建了一个叫 Spectre 的内部平台，并把它做成了一个产品。演讲者的结论是：Agent 平台的竞争从来不是模型本身，也不是 Agent 应用，而是在这些系统性问题上，基础设施最终会下沉、合并，成为新的核心产品。他的原话是：一个薄薄的包装层没问题，直到你需要耐用性、共享可见性、重试语义、成本核算、多供应商支持和协作界面——到那时，脚手架就成了产品。

“At some point, a harness becomes the product.”到某个时候，脚手架本身就成了产品。

Spectre 的立场因此也很明确：它不跟 Claude Code、Cursor 这些应用竞争，而是运行它们。工程师用自己喜欢的应用写代码，云端层持有密钥、真实环境、告警与工单，用同一套规则管理任务。不管 Agent 是谁，工作方式必须一致：任务描述必须被记录，审计轨迹必须存在，执行规则与安全检查必须统一。用户可以选择 Agent，但不能绕开这些规则。

■ 脚手架（Harness）：包裹 Agent 的运行层，负责密钥、环境、监控、重试、成本与协作等系统性能力。

■ Spectre：Harvey 内部的云端 Agent 平台，运行各家 Agent 应用，统一持有密钥、真实环境、告警与工单。

2.1 选你喜欢的 Agent：在笔记本上开始，把会话推上云

演讲者给出的工作流是先在笔记本上开始，再把会话推上云。工程师可以让 Cursor、Claude Code、Codex 或 Gemini 生成 PR；当他们选择 Spectre 时，系统会把整个会话，连同所有历史，同步到云端，并附上真实技术栈与云端模型。云端的 Agent 会继续跑测试、修问题，并在完成时发送消息。

■ 会话（Session）：一次 Agent 任务的完整上下文与历史记录；推上云端后由云端 Agent 接续执行。

笔记本上的 Agent 一次只能跑 5 到 10 个任务，云端则没有这个上限，工程师可以同时跑数百个。演讲者说，工程效率来自两方面：写代码时不再等待，写完之后还有一个系统替你把活干完。

3. 代码写完之后：六个环节与跟进循环

演讲者对一个具体场景做了拆解：凌晨两点，监控系统发出页面告警。一位工程师可以让 Agent 去处理它；但 Agent 不是魔法，它需要一系列配套环节来保证任务真的被完成。演讲者列出了六个环节：触发、端到端验证、跟进循环、评审策略、提醒与合并。

跟进循环是其中最重要的一环。当 CI（持续集成）失败时，系统会自动读取失败信息，生成修复补丁并重新提交。十月初，它面向全公司启用；当月合入后端的 Agent PR 中，五分之四经过了这个循环。演讲者说，这个功能上线之前，Agent 的 PR 只有一半能自己完成合并；上线之后，这个比例超过了 95%。他的原话是：CI 失败时，跟进循环会读取报错日志，生成修复并重新提交。

“When CI fails, the follow-up loop reads the failure, generates a fix, and resubmits.”CI 失败时，跟进循环读报错、生成修复、重新提交。

■ 跟进循环（Follow-up Loop）：CI 失败后自动读取报错日志并推送修复补丁的闭环机制。

■ 持续集成（CI）：代码合入前自动跑测试与检查的流水线；失败即触发跟进循环。

演讲者还点出了其他环节的意义：触发让任何人都能在任何渠道启动 Agent；端到端验证用真实环境与真实数据库做检查；评审策略让人类只在必要时介入；提醒保证任务不会静默失败；合并则处理多个 Agent 同时修改同一段代码时的冲突。他的结论是：写代码是最容易的一步，写完之后的工作才是真正的工程。

3.1 知识的沉淀：项目、技能与审计轨迹

演讲者认为，Agent 系统真正有价值的部分不是每次任务本身，而是任务执行过程中沉淀下来的知识。Spectre 有三个机制来积累这些知识：项目、技能与审计轨迹。项目是共享的代码库，存放 Agent 在工作中总结出的最佳实践；技能是可复用的工具与工作流，Agent 可以调用它们来执行重复性任务；审计轨迹则记录了每一次任务的完整过程，供人类复查与学习。

■ 项目（Projects）：存放 Agent 总结出的最佳实践的共享代码库。

演讲者的原话是：不管选哪个 Agent，审计轨迹与检查标准都应该是一样的。这说明，Agent 平台的真正价值在于沉淀下来的知识与流程，而不是某一次任务的成功。

4. 接口化：人能点的，Agent 都能调

演讲者说，Spectre 的一条基本规则是：人能点的，Agent 都能调。平台把内部工具、文档与系统全部做成 Agent 可调用的接口。这条规则的直接结果是：命令行工具在五月只启动了 1 个任务，到十月已经每月启动约 6,500 个任务。演讲者说，这条规则让 Agent 真正融入了公司的日常工作流。

“If a person can click it, an agent can call it.”人能点的，Agent 都能调。

■ 沙箱（Sandbox）：隔离的执行环境；Agent 在其中凭有时限的令牌调用工具，执行结束即失效。

4.1 协调员实验：一个会话，十个里程碑

演讲者介绍了一个实验：把一个大任务拆成 10 个里程碑，交给多个 Agent 并行处理。实验的结果是：一个会话在 10 个里程碑中完成了 9 个，剩余 1 个由人类接手。演讲者说，这个实验说明，Agent 已经可以承担大型任务的协调工作，但人类仍然需要在关键节点介入。

实验的另一个细节是：任务的分配与执行全部由 Agent 自己完成，人类只需要在任务开始时给出目标，在任务结束时检查结果。演讲者说，这种模式让工程师可以同时处理多个大型项目，而不用逐个盯着每个任务的进展。

演讲者还提到一个细节：一位工程师通过私信向他反馈，说现在只用让 Cursor、Claude Code 或 ChatGPT Dots 去批量提交 Spectre 任务就行了。演讲者说，这说明 Agent 已经成为工程师日常工作的一部分。

4.2 性能剖析：最慢的一步是拉取代码仓库

演讲者说，平台最慢的一步不是模型思考，而是拉取代码仓库。每次任务开始时，系统都要把全部仓库拉取到本地，平均耗时超过一分钟。演讲者说，这个问题在任务量小的时候不明显，但在任务量大的时候会成为瓶颈。

“The slowest step wasn’t model thinking.”最慢的一步不是模型思考。

解决方案是：在每台机器上保留全部仓库的裸副本，并在后台定期发布不可变版本。任务开始时，系统只需按引用克隆，只拉取自己分支的最新提交。结果是：拉取时间从平均约 76 秒降到约 5 秒，最坏情况此前超过 700 秒。演讲者说，这个优化让任务的启动时间大幅缩短，也让平台的扩展性得到了提升。

5. 失控与治理：两次过载

5.1 九百个 Agent 追同一只虫

演讲者讲了八月中旬的一次事故。一个 bug 被错误地配置为按 workspace 触发告警，结果约四小时内约 900 个 Agent 都在追同一个 bug。平日全天约 50 个任务由机器人触发，那天则有约 1,300 个。演讲者说，这次事故说明，Agent 系统的故障模式与传统系统完全不同：一个小小的配置错误，就能让数百个 Agent 同时失控。

“900 agents are chasing the same bug.”900 个 Agent 在追同一只虫。

解决方案是：把重复的警报合并到已经打开的调查中，避免多个 Agent 重复处理同一个问题。演讲者说，这个机制上线后，类似的事故再也没有发生过。

5.2 公平启动队列

十月，另一名工程师在三小时内从命令行启动了约 950 个任务，把集群填满了。演讲者说，这次事件说明，Agent 系统需要公平的资源分配机制，不能让一个人占用全部资源。

解决方案是公平启动队列：键盘前的人优先（40 个位置），每人同时 25 个任务，可借到 50 个，排位可见。四天后，公平启动队列上线。演讲者用一组对比数据说明了它的效果：在 300 个任务的突发测试中，同时运行的任务数从 240 降到 20，任务列表的 p95 延迟从 1.7 秒降到 71 毫秒，任务页面的 p95 延迟从 1.7 秒降到 43 毫秒，心跳的 p95 延迟从 5.3 秒降到 19 毫秒。演讲者说，这不是用户的问题，而是平台的问题。

“That’s not a user problem. That’s our problem.”这不是用户的问题，是我们的问题。

■ p95 延迟：95% 的请求在该时间以内完成；衡量系统在高负载下尾部体验的常用指标。

5.3 验证：下一次突发更大，完成得却更好

演讲者用一组对比数据验证了这些改动的效果：每月最忙的一天，七月约 1,100 个任务、96% 完成；八月十四日约 2,000 个任务、89% 完成；九月约 1,500 个任务、98% 完成；十月约 2,600 个任务、97% 完成；十一月四日约 4,400 个任务、94% 完成。改动的时间线是：九月十五日警报去重上线，十月二十四日管理员批量取消上线，十月二十七日公平启动队列上线，十月二十九日增加沙箱节点。每月任务量自五月起涨了 4.5 倍。

演讲者说，十一月四日的任务量是八月十四日的两倍多，完成情况却更好。但他也坦承，多项改动同时上线，无法归因到某一个具体措施。他说，我无法告诉你哪一项修复最重要。

6. 未解的瓶颈：合并

演讲者说，Agent 写代码的速度越来越快，但合并的速度却跟不上。全公司的 PR 单月涨了约 60%，合并时间从 15 到 30 分钟涨到 1 小时以上。演讲者说，这个问题至今没有解决。

旧的流程是：全队列逐个重测，每个 PR 都要等前面的 PR 合并完才能开始测试。新的流程是：变基、重跑 CI、变绿就合。演讲者说，这个流程让合并速度有所提升，但仍然不够快。他说，如果主分支出问题，所有人的 CI 都会跟着出问题。

演讲者还提到一个细节：当队列关闭时，有 80 多个 PR 在等合并。演讲者说，这个问题需要全公司一起解决，不是某一个团队能单独完成的。

7. 自动化：增长最快的工作来源

演讲者说，增长最快的工作来源不是人类工程师，而是自动化。自动化的任务从五月的约 2,700 个涨到十月的约 13,000 个。十月的分工是：警报分流约 4,200 个，PR 评审约 3,800 个，报告摘要约 1,700 个，测试与 CI 约 1,300 个，清理约 400 个。演讲者说，约 290 个自动化在跑，约 110 人参与。

演讲者说，自动化的护栏是：连续失败 5 次自动关闭，可带预算与过期时间。演讲者说，这些护栏让自动化可以安全地运行，而不用担心失控。

■ 护栏（Guardrail）：自动化的安全约束，如连续失败 5 次自动关闭、可设预算与过期时间。

8. 未解之题与三条经验

演讲的结尾回到一个未解的问题：今天只有二十分之一的合并带有“证明它能用”的证据。演讲者说，证明工作的方式不应该只在事后检查，而应该在任务开始之前就定义清楚。他说，工程师可以用自己喜欢的 Agent 写代码，但丢失的工作是运行它、检查它、让它合并的脚手架。

“Today only one merge in 20 carries that kind of proof.”今天只有二十分之一的合并带有这种证明。

演讲者总结了三条经验：第一，Agent 平台的真正价值在于沉淀下来的知识与流程；第二，公平的资源分配机制比单纯的性能优化更重要；第三，证明工作的方式必须前置，不能只在事后检查。演讲者说，这些经验来自 Harvey 内部的实践，也适用于任何想大规模使用 Agent 的团队。

“Engineers can write code with whichever agent they like. The work that’s lost is the harness that runs it, checks it, and gets it merged.”工程师可以用自己喜欢的 Agent 写代码；丢失的工作，是运行它、检查它、让它合并的脚手架。

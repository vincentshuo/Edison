软件工程正在变成工厂工程

Engineer Your Coding Agents Like Any Other System — Zach Lloyd, Warp

Zach Lloyd 说，软件工程正在变成工厂工程：大多数开发者今天还在本地一个一个地交互式提示 Agent，这种做法撞上了人的吞吐量、成本与治理三重天花板。他给软件工厂下一个很具体的定义——代码定义的闭环系统，持续度量并改进云端写代码的 Agent——然后自下而上铺开七层基础设施栈：工厂即代码、数据与上下文、算力、推理、改进、编排、接入；最后用 Warp 工厂的现场演示收尾：工厂写成 YAML，团队里每个 Agent 的运行都看得见，成本精确到每个 PR，在线评估给每次运行打分，自我改进以 PR 的形式改写工厂定义，而判断哪个模型、哪个技能、哪种配置更好，唯一可靠的办法是在自己的数据上跑基准。

Key Takeaways

  1. 本地交互式提示扩不上去。每个 Agent 都要人逐句提示就无法自动化；各人自选配置又让成本、效率与安全治理失控。
  2. 软件工厂有严格定义，不是松散自动化的集合。代码定义、闭环、持续度量与改进三条缺一不可，AI 队友、共享技能与个人 Agent 群都只是原材料。
  3. 工厂即代码是地基。用声明式代码写死 Agent、触发器与工作流，才能分支测试、回滚，并让 Agent 自己提 PR 改进工厂。
  4. 没有度量就是盲飞。成本精确到每个 PR、在线评估给每次运行打分，改进才有依据；只凭感觉部署，最优质量与最低成本都无从谈起。
  5. 别信公开榜单，信自己的基准。哪个模型、哪个技能、哪种配置更好，只能把真实任务重跑一遍，在自己的数据上见分晓。

1. 开场：从 Google Docs 到 Warp（约 0:00–0:57）

Zach Lloyd 上台先报身份：他做工程师很多年，曾是 Google 的首席工程师，主导 Google Docs 套件的工程，把这款产品做到数亿用户规模；现在是 Warp 的创始人兼 CEO。Warp 在做的，是帮公司搭建自己的内部软件工厂，他今天要现场演示其中一部分。Warp 还有一个广为人知的开源 Agent 终端，约 65,000 个 GitHub 星标，近百万开发者在使用——这两个数字是演讲者自述，公司使命始终没变：帮开发者更快地交付更好的软件，只不过随着世界变化，做这件事的方式也在演进。

演讲的题目就点明了转向：软件工程正在变成工厂工程。Lloyd 的意思不是说写代码这件事消失了，而是说，围绕写代码的 Agent，长出了一整套值得用工程方法对待的新问题：怎么组织、怎么度量、怎么改进。这场演讲就是沿着这条线展开的：先讲现状为什么走不通，再给软件工厂下定义，然后铺开基础设施栈，最后用演示证明这套工具真的在 Warp 内部运转。

2. 现状：大多数人还在本地交互式提示（约 0:57–1:42）

Lloyd 先描述了眼下的常态：他接触到的大多数开发者与平台团队，仍然是每个人在本地跑自己的写代码 Agent，一次可能同时跑好几个，通过终端或 Agent 开发环境交互式地提示。他现场问了一句：有多少人主要就是这么工作的？举手的人仍占多数，但已经不是全部——他认为这种局面正在改变，而且已经开始变了。

这张幻灯片只有一个词配一张照片：“Interactive prompting”，旁边是一张摆满多台显示器的书桌。画面本身就是论点：一个人、一台机器、几块屏幕，就是今天大多数人与 Agent 协作的全部装备。Lloyd 没有贬低这种做法，他只是指出，它是起点，不是终点——接下来他要讲的，是它扩不上去的三条理由。

3. 本地 Agent 的三重天花板（约 1:42–3:12）

第一重天花板是人的吞吐量。如果 Agent 的主要工作方式是本地交互式提示，那么每一次动作都要人开口，自动化就无从谈起——人的 throughput 就是系统的 throughput。Agent 再聪明，也只能以人的提示速度前进。

第二重天花板是效率。平台团队与工程负责人常向他抱怨：每个人自选本地配置、自选模型、自选技能，组织就很难确信自己在高效地使用这些 Agent——从成本角度是这样，从生产力角度也是这样。没有统一的度量，“用得好不好”就只能凭感觉。

第三重天花板是安全与治理。每个人自己搭建、自己运行本地 Agent，安全与治理问题随之而来。Lloyd 没有展开讲具体的事故，但把这一点与前两点并列：它不是事后补救的合规手续，而是本地模式本身的结构性代价。三重天花板合在一起，指向同一个结论：该换一种组织方式了。

4. 软件工厂不是什么（约 3:12–3:57）

接下来要登场的东西，Lloyd 宽泛地称之为软件工厂——但他先花一整节说它不是什么。幻灯片上四项各打一个叉：不是一堆松散的自动化；不是一群 AI 队友的集合；不是一套共享的技能与 MCP 配置；也不是个人的 Agent 群。现场举手调查的结果颇能说明问题：当他问有多少人正在搭建、使用自己的内部软件工厂时，举手的人几乎比还在本地交互式提示的人还多。

这四项被否定，不是因为它们没用。Lloyd 的判断是，它们都是有用的原材料，但都不是应该瞄准的终态。把自动化攒在一起、把技能共享出来、给每个人配一群 Agent，都还停留在“让 Agent 更好用”的层面；而软件工厂要回答的是另一个问题：怎么把一群云端写代码的 Agent 当作一个系统来经营。先划清边界，定义才站得住。

5. 定义：代码定义的闭环系统（约 3:57–4:42）

Lloyd 给出的定义只有一句话，但每个词都有分量：软件工厂是一个代码定义的闭环系统，用于持续度量并改进云端写代码的 Agent。他随即拆开三个关键词。第一，代码定义：要建软件工厂并真正把它扩上去，第一件事是把整个工厂完整地编码进声明式语言——跑哪些写代码的 Agent、怎么触发、活儿进来以后从分流到写规格走什么工作流、哪些 MCP 可用、Agent 在哪里跑，尽量都写进类似 Terraform 风格的声明式代码文件里。

“A code-defined, closed-loop system for continuously measuring and improving cloud coding agents.”一个代码定义的闭环系统，用于持续度量并改进云端写代码的 Agent。

第二，持续改进的闭环：想法可以来自人，也可以来自自动化信号，Agent 把议题从分流一路做到实现、验证、监控；关键在于闭环本身——Agent 跑得越多，这个循环就能变得越高效。第三，一切都必须可度量：如果部署写代码的 Agent 全凭感觉，就无法确信自己得到了最优质量的输出、付了最合适的成本，也无法确信自己把吞吐量拉到了最大。度量不是报表的点缀，而是定义的第三条腿。

■ 软件工厂（Software Factory）：代码定义的闭环系统，持续度量并改进云端写代码的 Agent；不是松散自动化的集合。

■ 工厂即代码（Factories as Code）：用声明式代码定义工厂的全部配置——Agent、触发器、工作流、MCP 与运行位置，类似 Terraform 的做法。

6. 闭环：从想法到监控的软件开发生命周期（约 4:42–5:27）

闭环的典型形态就是软件开发生命周期本身。幻灯片上画了一个圆环：新的产品想法或上报的缺陷进来，先分流，再写规格、实现、验证、发布、监控，然后回到起点。圆环中央写着“云端软件工厂”，三个虚线框标出人在环上的位置：评审规格、评审代码、评审产品。

Lloyd 强调，闭环的价值不在图的形状，而在它越转越快的特性：Agent 每多跑一圈，组织就多一份改进循环的机会。这个环节他讲得很快，因为真正的干货在后面——闭环要转起来，需要度量、需要新工具、需要一整套基础设施。但方向已经定下来了：工厂不是一条流水线，而是一个越用越好的循环。

7. 度量一切：凭感觉部署等于盲飞（约 5:27–6:57）

度量一节，Lloyd 把话说得很直白：如果只凭感觉部署写代码的 Agent，你不可能确信自己得到了最优质量的输出、付了最合适的成本，也不可能确信自己把吞吐量拉到了最大。“凭感觉”在这里不是谦辞，而是指一种真实存在的工作方式：凭印象觉得某个模型好、某个技能有用，就一直这么用下去，没有数字支撑，也没有对照。

“If you’re just going on vibes in terms of how you deploy coding agents, you can’t be confident that you’re actually getting the best highest quality outputs at the best cost.”如果你部署写代码的 Agent 全凭感觉，你不可能确信自己得到了最优质量的输出、付了最合适的成本。

所以他希望听众带走的核心观念是：对待写代码的 Agent，要像对待一个全新的工程基本单元那样。过去一年大家手里多了一个神奇的新原语——智能 Agent；问题是，怎么围绕它建一个系统，把它用得最有效。这不是种花，也不是照菜谱做菜，而是工程师的老本行：从第一性原理出发，系统地解决问题。一旦把 Agent 看作工程原语，接下来的做法就自然了：度量它、改进它、给它搭基础设施。

■ 闭环（Closed Loop）：想法经分流、实现、验证、发布、监控回到起点的循环；Agent 跑得越多，循环越高效。

8. 工厂工程的新工具箱（约 6:57–7:42）

新的工程问题需要新的工具。Lloyd 回忆自己在 Google 学做更好的工程师时，真正拉开优秀与平庸差距的，是调试器、性能分析器、Chrome DevTools 这类手艺工具——不是所有工程师都会用，但会用的人明显更强。在工厂工程的新世界里，也有一套对应的工具，每个人都应该努力掌握：评估、能跑通的自我改进循环、写基准、给工厂做 A/B 测试。

他顺手区分了两种工程：产品工程是造产品本身，工厂工程是改进造产品的工厂。幻灯片把这句话写成两行等式：产品工程等于造产品，工厂工程等于改进造产品的工厂。两种工程都要做——工程师仍然要对自己交付的产品是否真正解决了用户的问题负责——但最好的工程师，每一位工程师，都需要学会第二套工具：怎么改进系统，而不只是造产品。

“There’s a really cool fundamental new engineering problem, which is how do you take this magic new primitive that we all have… and engineer a system around them to use them most effectively?”这是一个很酷的全新的根本性工程问题：我们手里有了这个神奇的新原语，怎么围绕它建一个系统，把它用得最有效？

■ 工厂工程（Factory Engineering）：改进造产品的工厂本身的工程实践，区别于直接造产品的产品工程；核心工具是评估、自我改进循环、基准与 A/B 测试。

9. 基础设施栈：自下而上的七层（约 7:42–10:42）

从第一性原理出发，围绕 Agent 的工程系统会长成什么样？Lloyd 给出的答案是一座七层基础设施栈，幻灯片编号 00 到 06。最底层是工厂即代码：工厂的 YAML、Agent 定义、自动化定义、启动配置与仓库配置；它的价值在于可以分支测试不同的工厂配置、可以回滚，更关键的是，它为自我改进打开了大门——写代码的 Agent 自己可以提议改动工厂的运转方式。

往上是数据与上下文层：运行记录与转录、Agent 记忆（向量库）、Agent 产物（PR、报告、附件）、MCP 与内部知识、访问控制（基于角色的权限与归属）。Lloyd 强调，在组织里大规模跑写代码的 Agent，必须记录 Agent 产出的一切——对话、产物、视频、截图——因为这些就是日后改进工厂的原材料。再往上是算力层：沙箱（Docker 镜像、Kubernetes、任意远程环境）、Agent 运行器（Mac、Linux、Windows，可配磁盘、内存与 CPU）与计算机使用（视频与图像）；沙箱提升安全性，也让工厂可重复。

■ 沙箱（Sandbox）：隔离的执行环境；Agent 在其中运行，环境可复现、可配置磁盘、内存与 CPU。

推理层是第四层。Lloyd 对模型与推理的看法是：它们是用来测试的自由度。所以工厂应当支持多个模型，也应当支持多个写代码的 Agent——Claude Code 在某些事上更好，Codex、Warp 各有不同的特性，团队也可以写自己的 harness，把组织上下文沉淀进去；还可以自带推理（Bedrock、Vertex）或自定义模型路由。编排层在它之上，负责把活儿搬过工厂：原生编排（分流、写规格、实现、评审、验证）、多 Agent、人在环中（实时引导与交接）与自动化（触发器与定时任务）。Lloyd 说编排在某种意义上是最不性感的一层，但缺了它不行。

最顶上是接入层：工厂应当 API 与 MCP 优先，既能被人用，也能被其他写代码的 Agent 用，并且走到活儿所在的地方——Slack、Teams、Jira、Linear、GitHub、GitLab、网页、手机、API 与 SDK。幻灯片左侧还标了一句：00 到 03 层可以由 Warp 托管，也可以由客户自己托管。七层合起来，就是“像对待任何其他系统一样”对待写代码的 Agent 的具体形状。

■ 推理层（Inference Layer）：模型与推理在工厂里被当作可测试的自由度；工厂应支持多模型与多 Agent harness。

■ 编排（Orchestration）：把工作搬过工厂的层：分流、写规格、实现、评审、验证，以及多 Agent、人在环中与自动化。

10. 演示之一：工厂即代码（约 10:42–11:27）

理论讲完，Lloyd 转入现场演示，用的都是 Warp 工厂的真实界面，但他强调，这些工具在自建工厂时同样适用。演示的第一站回到地基层：工厂即代码。屏幕上是 GitHub 上的 warpdotdev/factory-dev 仓库，打开的文件是 eng-factory-slim/factory.yaml，共 316 行：模式版本 v1alpha2，工厂名 eng-factory-slim，描述是“由协调领班与持久生命周期工作者执行的生产级软件开发运营”，凭证策略为 CREATOR，网络策略列出允许访问的主机——OpenAI 的 tokenizer 词汇表下载、Vercel 的部署 API、Loom、Terraform 注册表等等。

仓库的目录结构本身就是工厂的形状：agents、automations、benchmarks、runners、scorers、self-improvement、skills、stages，再加一份 factory.yaml。Lloyd 的潜台词是：工厂即代码不是一句口号，落实下来就是这样一份看得见、改得了、能进版本控制的定义。他还特意说，这段代码本身没什么好看的，熟悉 Terraform 的人一眼就能明白——重点是“声明式地说出这就是我的工厂”这件事本身。

11. 演示之二：全队实时视图与成本、在线评估（约 11:27–14:27）

演示的第二站是数据与上下文层：工厂里的一切都应当在全队范围内被追踪。屏幕上是一个类似 Google Docs 的实时视图：Warp 团队里每位工程师的 Agent 此刻在做什么，一目了然。Lloyd 随手点开一位叫 Maggie 的同事：她正在从 Slack 发起一个任务，用高配方案实现 Opus 5.5，还能看到这次运行的产物与完整对话。实时看见本身很酷，但更重要的是，这些信息被集中收集起来，成为改进工厂的原料。

有了集中存储的数据，理解 Agent 的工作方式就变得容易：既可以看传统的产出指标，比如 DORA 指标里的周期时间，也可以看自动化程度——每个 PR 平均要人交互几次、吞吐量是多少、成本是多少。演示的成本面板上写着：每个 PR 成本 10.68 美元，七天里 342 个 PR 总计约 3,651.68 美元，按来源拆分则为 4,697.41 美元，来自 Slack、Warp 网页、评分器、工厂 MCP、GitHub、自我改进、API 与定时任务八个来源。Lloyd 的评价是：没有这些数据，就是在盲飞。

■ DORA 指标（DORA Metrics）：衡量软件交付效能的一组指标，演讲中以周期时间为代表，用于看 Agent 产出的快慢。

■ 在线评估（Online Eval）：在 Agent 会话运行时，由另一个 Agent 回看其输出并按某个维度打分，以判断它做得好不好。

同一层数据还支撑在线评估：Agent 会话在运行、输出被记录下来之后，可以让另一个 Agent 回看并按某个维度打分。Lloyd 举了一个具体的评估：检查冗余测试——写代码的 Agent 常见的失败模式之一是写出不必要的测试，这个评估就是来抓它的。演示的评分面板上，四项分数分别是：阶段转换合规 71%（5 次通过、2 次失败）、自我改进质量 69%（29 次通过、13 次失败）、人工反馈 70%（394 次通过、169 次失败）、啰嗦程度 67%（70 次通过、34 次失败）。看到分数之后，下一步自然是问：它为什么写了太多测试？工厂里有没有哪个机制可以改一改，让它变好？

■ 评分器（Scorer）：给已完成的 Agent 运行打分的评估器；演示中的四项包括阶段转换合规、自我改进质量、人工反馈与啰嗦程度。

12. 演示之三：自我改进就是给工厂提 PR（约 14:27–15:57）

有了记录、有了评估，就可以做 Lloyd 所说的自我改进：不再由人去看分数的输出，而是由 Agent 去看。自我改进的思路是：它看分数输出，发现有若干次失败的运行，就去找这些失败里的模式，再提议一个可能的解法；而这个解法的形式，就是针对工厂定义的一份 PR。这正是工厂即代码的美妙之处：既然工厂是代码，写代码的 Agent 就能诊断自己工作方式内部的问题，并提议修复。

演示里蓝图页面的另一面也值得一提：工作流被画成一张图，research 节点之下是 work 节点，work 里嵌套了分流、设计探索、写规格、实现、评审五个阶段，右侧列出 9 个阶段与 28 条转换，整张图由一位“领班”编排。Lloyd 没有展开讲这张图的每个细节，但它说明了一点：自我改进不是一句空话，它发生在一条看得见的工作流之上——Agent 知道自己在循环的哪一步，改进才有落点。

■ 自我改进（Self-improvement）：由 Agent 而不是人去看评估分数，找出失败运行的模式，并以 PR 的形式提议修改工厂定义。

13. 演示之四：在自己的数据上做基准（约 15:57–17:27）

最后一件工具是基准，而且 Lloyd 说它同样必不可少。网上每天都在争论哪个模型最好、哪个技能最新、哪个 harness 最强，唯一能真正回答这些问题的办法，是在自己的数据上测试。做法是：用真实数据建一个基准集，把任务重跑一遍，对照不同的配置——换一个模型、换一个 harness、改一改工厂配置——看结果会怎样。演示里还出现了一个小插曲：他一度点错了页面，又点回来继续讲。

基准长什么样？像 SWE-bench 或 Terminal-Bench 那样：横轴是成本，纵轴是质量，不同模型的取舍画在一张图上，目标是落在左上象限——成本低、质量高——但这次用的全是自己的真实数据。而且能测的不只是模型：也可以测，如果去掉这些技能，工厂是变好还是变坏。演示的基准列表上，既有按阶段分的默认模型选择（分流、写规格、评审、领班），也有针对具体任务的基准，比如 Warp 服务器界面实现 Agent 基准、warp-bench-ui-1.0、warp-bench-ui-1.0-mini、warp-bench-smoke-test 与 warp-bench-1.0，列表里各项的更新时间都是 28 天前。

■ 基准（Benchmark）：用真实任务重跑不同配置、比较成本与质量的对照测试；公开榜单回答不了“对我的代码库哪个最好”。

14. 结语：去工程化你的 Agent（约 17:27–18:30）

回到大概念：这套做法在 Warp 内部已经跑通了。Lloyd 说，靠着这些工具，他们大幅提高了吞吐量、降低了成本——他没有给出具体数字，只说这件事对他们非常重要，因为成本真的很重要；他们一直在循环：建立性能基线、打分、跑基准、做测试，这就是工厂工程的日常。终场幻灯片是蓝底白字三行：“提示你的 Agent”与“管理你的 Agent”被划掉，只剩最后一行——“去工程化你的 Agent”。

“Engineer your agents.”去工程化你的 Agent。

他最后回到工程师的身份焦虑：现在大家不写代码了，当工程师到底意味着什么？他的回答是，自己仍然在用整个职业生涯学到的全部工程技能——只不过对象变了。这仍然是一个令人兴奋的时刻。演讲在掌声里结束，最后一页留了一个了解更多工厂的入口。整场演讲没有一句多余的话：它先给了一个定义，再给了七层栈，最后用四段演示证明定义与栈是同一回事——把写代码的 Agent 当作系统来工程化。

“We’re all engineers. We’ve spent our careers learning how to solve problems from an engineering mindset.”我们都是工程师。我们整个职业生涯都在学习用工程思维解决问题。

讨论问题

1. 你们团队今天的 Agent 用法更接近本地交互式提示，还是已经有了云端闭环？三重天花板里，哪一道先撞上你们？

2. 按 Lloyd 的定义写出你们工厂的一句话定义：哪些部分今天还只是松散自动化的集合？

3. 如果把工厂写成声明式代码，哪三项配置最值得先上版本控制：触发器、工作流，还是模型与技能选择？

4. 选一个你们反复出现的 Agent 失败模式，为它设计一个在线评估：由谁打分、按什么维度、多少分算失败？

5. 自我改进以 PR 形式改工厂定义时，人应该在哪一步把关？哪些改动可以自动合入，哪些必须人工评审？

6. 在自己的数据上建基准：挑十个真实任务，先跑一遍基线，再换一个模型或去掉一个技能，对比会说明什么？

代码是最容易的部分

Code is the easy part: building Home Assistant in the open — Franck Nijhof, GitHub Universe 2026

Speaker: Franck Nijhof（Frenck），Home Assistant 负责人，Open Home Foundation

Event: GitHub Universe 2026 演讲

Length: 15 分 21 秒

Source: youtu.be/q-dvPBfZuGs

Technical Monograph · 精读报告 发布 2026 年 11 月 19 日 生成 2026 年 11 月 20 日

十五分钟的演讲，讲的是一件反直觉的事：把代码放到 GitHub 上，是开源里最容易的一步。Home Assistant 负责人 Franck Nijhof 在 GitHub Universe 2026 的舞台上，先让全场举手——有代码在 GitHub 上的人几乎全场，代码开源的人少了一截，路线图也公开、且每个用户都能公开评论的人只剩寥寥几个。然后他讲了两次翻车：2025 年 1 月全量加密备份，锁住了用户想找回单个自动化的路；2023 年 12 月重新设计的登录页，把住户的脸和名字亮给了互联网上的陌生人。两次都是聪明人想了很久才做的决定，错只错在一点：做决定的人不在用户的家里。2026 年 4 月 8 日，Home Assistant 在荷兰乌得勒支的 State of the Open Home 上把路线图彻底公开——任何人都能读、能评论、能领活。自那以后，错误没有消失，只是变便宜了。

Key Takeaways

  1. 代码是最容易的部分。把代码放到 GitHub 上毫不费力，难的是决定往哪儿开——方向、体验与路线图都在写代码之前。
  2. 两次翻车都出在会议室里。加密备份与新登录页都是聪明人想了很久的决定，错只错在做决定的人不在用户的家里。
  3. 路线图彻底公开。2026 年 4 月 8 日，State of the Open Home，乌得勒支——任何人都能读路线图、评论、领活。
  4. 需求变成机会，再变成史诗。GitHub Discussions、Issues 与 Projects 串起一条公开流水线；自 4 月以来已交付 50 多个机会，公开拒绝 12 个并给出理由。
  5. 错误没有消失，只是变便宜了。窗帘控件的七个月返工与“What the heck”月证明：越早让人进来，付出的代价越小。

1. 开场：举手测试——代码是最容易的部分（约 0:00–1:59）

Franck Nijhof 走上 GitHub Universe 2026 的舞台，没有先讲产品，而是先让全场举手。第一问：有代码放在 GitHub 上吗？几乎全场的手都举了起来。第二问：代码是开源的吗？手少了一截。第三问：路线图也是公开的吗？只剩寥寥几个勇敢的人。第四问：每个用户都能公开评论那份路线图吗？举着的手几乎没有了。四轮举手下来，全场只剩几个人还举着手。

这个开场不是暖场游戏，而是整场演讲的论证结构。Nijhof 的判断很直接：第一问举手的人多很正常——这里是 GitHub Universe；但后面几问几乎没人举手，实在可惜。作为工程师，他说第一问的答案本来就容易：把代码放到 GitHub 上，GitHub 已经让这件事变得非常容易；到了 AI 的时代，每一周都变得更容易一点。他特意说明，这场演讲不谈 AI——接下来的几天里，AI 会被谈得够多了。

他给代码在 GitHub 上的状态打了一个比方：行车记录仪。每一转弯都被录下来，可以倒回去看，可以逐帧检查，甚至可以针对录像提 issue。这很好，但行车记录仪只会告诉你已经开到了哪里。等画面出现在录像里，那个弯已经转完了。难的从来不是开车，而是知道往哪儿开。第一轮举手与最后几只手之间的落差，就是他接下来十五分钟要讲的东西。

■ 行车记录仪（Dash Cam）：Nijhof 在本场演讲里对“代码已公开”状态的比方——公开的代码像录像一样完整记录了走过的路，却无法告诉团队下一步该往哪儿走。

“Code on GitHub is like a dash cam. Every turn we ever took is being recorded… But the dash cam will only show you where you already drove.”

GitHub 上的代码就像行车记录仪，每一转弯都被录下来……但它只会告诉你已经开到了哪里。

比方之后他补了一句收束：难的部分从来不是开车，而是知道往哪儿开。这句话在演讲结尾还会再出现一次，首尾呼应——只不过结尾的版本从“记录仪”换成了“上车”。

2. 自我介绍：数百万家庭与每年两万多名贡献者（约 1:59–2:54）

Nijhof 的自我介绍只有三句话：我是 Franck，Open Home Foundation 的 Home Assistant 负责人；如果你不知道 Home Assistant，它是一个开源的智能家居平台，任何人都可以免费使用，数百万人正在用它；每年有超过 20,000 名贡献者帮我们把这个产品做出来。数字没有展开，但幻灯片把它们放大到了整屏：“Millions of homes run it”（数百万家庭在用它）、“20,000+ people contribute every year”（每年 20,000 多人参与贡献）。

他顺带把开场的举手测试收了尾：最后一问，他自己的手也会举起来。把路线图公开、让每个用户都能评论，这件事“有点吓人”，但他接下来要讲的，就是为什么团队还是这么做了。规模在这里不是炫耀，而是论证的前提：一个每年两万多人参与、数百万家庭在用的项目，方向一旦走错，代价比小项目大得多——而这正是他要讲的翻车故事的背景。

■ Home Assistant：开源智能家居平台，用户在本地运行、自主控制家中的设备与自动化，强调隐私；隶属于非营利组织 Open Home Foundation。

■ Open Home Foundation（开放家庭基金会）：Home Assistant 的母组织，以隐私、选择权与可持续性为宗旨的非营利基金会。

介绍完自己，他向台下预告了接下来的玩法：请大家把手捂热一点——接下来的几分钟，台下所有人就是 Home Assistant 团队。他会拿出团队真正要做的决定，让大家举手表态：要不要发布这个？记分牌已经摆好，他会在心里记分。

3. 第一回合：加密备份，2025 年 1 月（约 2:54–4:02）

第一回合回到 2025 年 1 月。Home Assistant 是一个重视隐私的平台，隐私是团队最看重的价值之一。于是团队决定：把每一份备份都完整加密——你的数据应该是安全的、属于你自己的。问题很简单：要不要发布？台下举手的人相当多。团队当时的决定和台下一样：发布。

结果出乎意料。人们打开备份，往往不是为了把整个智能家居恢复原状，而是为了找回某一个自动化——比如某个周二晚上随手删掉的那一个。加密之后，这件事做不到了。团队从来没有想过这个用法。一个版本之后，他们修好了它。Nijhof 给出的比分是：用户 1 比 0。

这个回合的教训不在技术上。加密本身没有错，隐私的出发点也没有错，错的是团队对“备份是用来干什么的”这件事的想象。用户打开备份的真实场景——找回一个删掉的自动化——从来没有出现在团队的会议室里。备份的用途不是由设计者定义的，而是由使用者在真实生活里定义的。团队以为自己在保护数据，用户却发现自己被锁在了自己的数据外面。

值得注意的是，Nijhof 在讲这个回合时没有为团队辩护，也没有把责任推给任何人。他只是把顺序摆出来：决定、发布、发现、修复，一个版本之后。一个回合只花了一分多钟，但它立住了整场演讲的论证方式：让台下先投票，再公布真实结局——台下的多数意见，和团队当年的决定一样，都是错的。

4. 第二回合：登录页，2023 年 12 月（约 4:02–5:39）

第二回合回到 2023 年 12 月。原来的登录页是用户名加密码，能用、好用、一眼就知道是什么。但没有人会说它好看。于是团队重新设计了它，做得像一台笔记本电脑：屏幕上出现住在这个家里的每个人，点一下自己的脸，输入密码，就进去了。设计师喜欢它，团队喜欢它，X（Twitter）上的人也喜欢它。要不要发布？台下举手的人还是不少，但比上一回合少了一些。Nijhof 的评价是：你们学得比我们快多了。

问题出在很多人到达 Home Assistant 的方式上。不少用户通过一种叫反向代理的东西从外网访问自己的 Home Assistant，而从代理到 Home Assistant 的流量看起来像是本地流量。于是，崭新的登录页突然对互联网上的陌生人也可见了——陌生人能看到这个家里住着谁，带着脸和名字。这是一个失误。八天之后，团队把它撤掉了。比分变成 2 比 0，这一次还多了一个安全漏洞。

■ 反向代理（Reverse Proxy）：部署在服务器前方的中转服务，对外接收请求再转发给内部应用；许多 Home Assistant 用户用它从外网访问家中的实例，而代理转发的流量在应用看来像是来自本地网络。

两个回合讲完，Nijhof 把结论说得很克制：两次做决定的人都很聪明、很谨慎，在会议室里想了很久。台下的人也一样聪明。但问题不在智力上——“你们只是不在他们的家里”。这句话是整场演讲的转折点：错误的原因不是团队不够好，而是团队不在场。用户家里的真实用法——怎么打开备份、怎么从外网进门——在会议室里是看不到的。唯一的办法，是把做决定的人和用产品的人放到同一个房间里。

5. 转折：路线图公开（约 5:39–6:44）

团队的办法，是把用户请进自己的房间。六个月前，在荷兰老家的一场活动上，他们把路线图彻底公开了，完整地贴在 GitHub 上。任何人都能读，任何人都能评论，任何人都能从上面领活。幻灯片上写着日期：2026 年 4 月 8 日——“Our roadmap goes public”（我们的路线图公开了），配图是乌得勒支 State of the Open Home 活动现场，屏幕上写着“Building in the open isn’t (always) easy”（公开地建造并不（总是）容易）。

第一个问题总是：你们不会被淹没吗？Nijhof 的回答是：会的，而且相当开心。团队收到成千上万条功能需求，对每一件事都有非常强烈的意见——毕竟这是互联网。但开放的关键不在处理数量，而在不把任何人锁在对话之外。就算全部公开，团队照样会走错路，只不过目标是更早发现。路线图公开不是为了不出错，而是为了让错误在更便宜的时候被发现。

“Openness isn’t about handling volume. It’s about locking nobody out of the conversation.”

开放不是为了应付数量，而是为了不把任何人锁在对话之外。

这里需要把两个“公开”区分开。代码公开是第一问的答案，路线图公开是第三、四问的答案。代码公开记录的是已经走过的路，路线图公开讨论的是还没走的路。前者是事后透明，后者是事前共治。Nijhof 的论点是：只有后者才能回答“往哪儿开”这个问题——因为方向不是在代码里决定的，而是在路线图的评论区里决定的。

6. 从需求到史诗：公开流水线如何运转（约 6:44–8:26）

接下来他用一个正在做的功能演示这条流水线：让人能像人一样思考的自动化触发器——“当门打开时”，而不是某种数据库查询式的语法。这件事从一条功能需求开始。在 GitHub Discussions 里，团队目前有 5,000 多条待处理的需求；被挑中的需求会被放进一个叫“机会”（Opportunity）的东西里，有时多条需求会合进同一个机会。机会本身就是公开项目板上的一条 issue；获得批准的机会会成为“史诗”（Epic），下面再挂若干 issue 作为具体任务，横跨前端与后端等多个项目。

他连放三张幻灯片，把链条走了一遍：Discussions 里关于自动化触发器的功能需求；变成机会——一条带“机会”类型与自定义字段的 issue；最后落进路线图本身——就是一个公开的 GitHub 项目，所有机会都在里面。没有定制工具，没有特殊平台，只有 Issues、Projects 与 Discussions，全部摆在明处。自 4 月以来，团队已经交付了 50 多个这样的机会；另外有 12 个被公开拒绝了，而且拒绝时写明了理由。

■ 机会（Opportunity）：公开项目板上的一条 issue，类型标为“机会”，附带自定义字段；一条或多条功能需求被收拢进同一个机会，获批后升级为史诗。

■ 史诗（Epic）：由多个 issue 组成的较大工作单元，下挂具体任务，横跨前端、后端等多个项目；熟悉 Jira 的人对这个词不会陌生。

这条流水线的关键不在于工具，而在于评论的形态。任何人都能去评论每一条，不只是点一个赞，而是讲清楚“这在你家里行得通，还是行不通”。而且他们真的会这样评论。拒绝也是公开的：12 个机会被公开拒绝并附上理由——拒绝本身也成了一份公开记录，让后来的人知道这条路为什么没走。

7. 在写代码之前拦住错误（约 8:26–10:16）

公开路线图最划算的一次回报，发生在写代码之前。团队想给 Home Assistant 里一个叫“开发者工具”（Developer Tools）的东西改名——“开发者”这个词让很多人望而生畏。有人提议叫“sound sandbox”（听起来像“沙盒”，又带点双关），听上去挺合适。接着另一位用户回复：在沙盒里，你做的每件事都不是真的；但在这个面板上点一下鼠标，真的会把睡着的孩子的卧室里的灯打开。

这个反对意见一针见血：沙盒的隐喻是“所做皆非真实”，而这个面板的每一次点击都是真实的、有后果的。团队最终采用的名字很简单，就叫“工具”（Tools）。Nijhof 的总结只有一句话：这是在一行代码写出来之前就被拦住的。

“This was caught before a single line of code was written.”

这是在一行代码写出来之前就被拦住的。

他还展示了一个真实的史诗：自动化触发器的那条史诗下面挂着所有 issue，issue 下面还有子 issue，规模相当大；但其中每一条任务都可以领走。已经有人通过这条路做出了自己对 Home Assistant 的第一次贡献——一个吸尘器回到充电座时触发的触发器。对一个新贡献者来说，第一份贡献就是这样一个实实在在的任务，本身就是路线图的价值：它不仅告诉大家方向，还把方向拆成了可以上手的具体活。

大的机会还有一层保护：团队会把它们在早期、未完成的状态就放出来，藏在一个叫 Home Assistant Labs 的功能开关后面。用户可以主动加入、试用、反馈，团队再据此迭代。自动化触发器这条史诗从立项到正式发布花了将近一年，之后才成为所有人的默认功能。慢，但每一步都有人在真实家里试过。

■ Home Assistant Labs：Home Assistant 内置的实验功能开关；未完成的大功能先放在它后面，供用户主动加入试用并反馈，成熟后再成为默认功能。

8. 第三回合：窗帘、百叶与卷帘，正在进行（约 10:16–13:24）

第三回合不是历史，而是正在发生的事。窗帘、百叶、窗帘布与卷帘——今天在 Home Assistant 里，它们全都显示为一个滑块，拖到百分之几，窗帘就开到百分之几。团队重新设计了它：每一种窗帘都有自己的小图、自己的画法；白天窗后是日光，晚上是夜色，百叶随着家里真实的窗帘一起动。看起来很美。团队甚至给它做了估算：因为现在有了“机会”机制，基本没有风险，引用的话也不多，耗时最多一到两周。问题照例是：要不要发布？台下举手的人相当多。

这一次团队学聪明了：他们把原型放到了 GitHub 上，让所有人都能玩、都能看。然后反馈就来了。遮阳篷是反的——打开它，它反而卷进去。在波兰，卷帘是实心的，而原型里画得像威尼斯百叶，有点奇怪。在德国，遮阳帘在 20% 开度时就已经到底了，帘片之间还有透气缝；但在演示里，20% 看起来还像是开着的。他们甚至有一个专门的词来形容这件事——Nijhof 说他就不尝试发音了，请台下想试的人自己试。

这些东西在会议室里找不到，在提示词里也找不到。而“一到两周最多”的估算，到现在已经过去了七个月。上一周，团队把最新定稿的设计又放上了 GitHub，一小时之后第一条评论就来了。比分变成 3 比 0。但 Nijhof 强调的不是比分，而是价格：这些错误没有一个进入正式版本。同样的错误，完全不同的代价——唯一的区别，是他们让人进来了。

第三回合与前两个回合的区别，正在于时间点。前两个回合的错误是在发布之后才被发现的，修复要靠下一个版本、靠八天之后撤回；第三回合的错误是在发布之前被拦住的，代价是七个月的迭代，而不是一次正式版本的事故。七个月听起来很长，但它买的是“错误不进入版本”这个结果。估算错了，设计改了，时间花了——但用户手里的版本没有坏过。

9. “What the heck”月：不用 GitHub 账号也能说话（约 13:24–14:33）

Nijhof 很坦率：GitHub 是个吓人的地方。需要账号，满眼都是代码。他爸爸这辈子都不可能去他们的项目里提一个 issue，他对此相当肯定。所以每两年，团队会换一种做法，为期一个月：论坛向所有人开放，只问一个问题——“What the heck, Home Assistant？”（Home Assistant 到底怎么回事？）任何让人恼火的事，无论大小，都可以扔进来。可以是一个词，也可以是一整本书。

第一次这么做是 2020 年，一个月里收到了 4,500 多条回复。更难得的是，那一个月里就已经有人在根据这些抱怨动手修东西了。幻灯片上把数字放大到了整屏：“The first time we did it — 4,500+ responses in one month”（第一次做的时候——一个月 4,500 多条回复），旁边写着规则：一个问题，一个月，在论坛上，对任何人开放：不用 GitHub 账号，不用技术能力，任何项目都能这么做。下一轮就在这个星期日，11 月 1 日开始。

这个环节的意义，在于补上公开路线图的一块短板。路线图再公开，门槛也在那里：GitHub 账号、issue 的写法、技术词汇。最需要被听到的声音——那些被产品惹恼、但永远不会提 issue 的普通用户——恰恰进不了这扇门。“What the heck”月把门槛降到了零：不用账号，不用技术，只需要一句话：这东西到底怎么回事。它不是路线图的替代品，而是路线图的入口：先把抱怨收进来，再把其中能变成机会的送进流水线。

10. 结尾：让他们上车（约 14:33–15:21）

结尾回到两年前。Nijhof 说，两年前他也站在 GitHub Universe 的主舞台上，请大家给仓库点星——如果点星了，舞台上的一盏灯就会亮起来。今年他的任务更重一点：请大家去看路线图，实实在在地告诉团队，他们哪里错了。路线图的网址他在台上念了出来，自动字幕没能辨认清楚；贡献指南的地址则很清楚：contributors.home-assistant.io，上面有帮助新人上手的各类指南。

最后他回到开场的比方，换了一个版本收束全场：代码是最容易的部分，对吧？别只给人看行车记录仪的录像，让他们上车。十五分钟的演讲到此结束，台下掌声响起。

“Code is the easy part, right? Don’t just give people the dash cam footage, but let them in the car.”

代码是最容易的部分，对吧？别只给人看行车记录仪的录像，让他们上车。

从“记录仪”到“上车”，两个比方之间差的正是整场演讲的论点。代码公开解决的是“走过的路能不能被看见”，路线图公开解决的是“没走的路能不能一起定”。前者是事后透明，后者是事前共治。Nijhof 的完整主张可以收成一句话：开源最难的部分不是写代码，而是把决定方向的人请进车里——而请他们上车的办法，就是把路线图、把讨论、把领活的入口，全部摆在明处。

核心观点

1. 代码是最容易的部分：把代码放到 GitHub 上毫不费力，难的是决定往哪儿开——方向、体验与路线图都在写代码之前。

2. 会议室里做的决定注定会错过用户家里的真实用法：加密备份锁住了找回单个自动化的路，新登录页把住户的脸和名字亮给了互联网。

3. 路线图公开不是为了不出错，而是为了让错误在更便宜的时候被发现：2026 年 4 月 8 日之后，任何人都能读、评论、领活。

4. 公开流水线把方向拆成了可以上手的具体活：需求进 Discussions，挑中的变成“机会”，获批的成为“史诗”，大功能先藏在 Home Assistant Labs 后面试用。

5. 最便宜的反馈是不用 GitHub 账号的反馈：“What the heck”月把门槛降到零，让永远不会提 issue 的普通用户也能说话。

讨论问题

1. 代码公开与路线图公开，哪一个对“决定往哪儿开”更有用？一个只公开代码、不公开路线图的项目，缺的是什么？

2. 加密备份与新登录页的两次翻车，有没有可能在会议室里避免？如果当时团队里有人用过反向代理、有人删过自动化，结局会不同吗？

3. 路线图上 5,000 多条待处理需求、成千上万条强烈意见：公开讨论的噪音与价值之间，界线应该划在哪里？

4. 12 个机会被公开拒绝并写明理由：公开拒绝会不会打击提议者的积极性？拒绝的理由应该写到多细？

5. 窗帘控件“一到两周”的估算变成了七个月：公开迭代拉长了工期，却拦住了进入版本的错误——这个交易划算吗？在什么情况下不划算？

6. “What the heck”月不用 GitHub 账号、不用技术能力：你的项目（或公司、团队）能不能也问一次这个问题？问之前要准备什么？

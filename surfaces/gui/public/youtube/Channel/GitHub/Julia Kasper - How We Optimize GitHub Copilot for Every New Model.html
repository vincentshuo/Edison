框架即产品

How We Optimize GitHub Copilot for Every New Model — Julia Kasper, GitHub Universe 2026

Speaker: Julia Kasper，GitHub Copilot 产品经理（Microsoft）

Event: GitHub Universe 2026 演讲

Length: 12 分 17 秒

Source: youtu.be/JSC8eVojIWY

Technical Monograph · 精读报告 发布 2026 年 11 月 18 日 生成 2026 年 11 月 19 日

十二分钟的演讲，讲的是一件反直觉的事：决定 Copilot 质量的不是模型本身，而是模型外面那层东西。GitHub Copilot 产品经理 Julia Kasper 在 GitHub Universe 2026 的舞台上说，仅这个季度，Copilot 就上线了 25 个新模型——而每一次上线，真正的工作都发生在模型之外：一个叫作编码框架的系统，负责给模型写系统提示词、暴露工具接口、驱动智能体循环。同一模型装进不同的框架，出来的产品质量可以天差地别；未经调校就把新模型丢进去，质量反而会下降，哪怕模型本身更强。Kasper 讲了 Copilot 如何与六家模型供应商每周对表、如何在上线前把框架逐项调好、如何用离线基准与内部试用守住质量、又如何在上线后用线上实验继续调——她的收束只有一句话：框架即产品。

Key Takeaways

  1. 智能体等于模型加框架。模型是推理引擎，框架是围绕模型的系统，同一模型换一个框架，产品质量可以天差地别。
  2. 新模型不能直接丢进未经调校的框架。否则质量反而下降，哪怕模型本身客观上更强。
  3. Copilot 的核心身份是模型选择。OpenAI、Anthropic、Google、Microsoft、xAI 与 Moonshot 六家模型都要在上线前逐个调进框架，用户不被锁在任何一家。
  4. 接入是一条固定流水线。供应商提前知会、模型接入 Copilot API、调框架、离线评测与内部试用、把发现反馈给供应商，最后才是上线日。
  5. 评估在上线后也不停。离线基准持续跑，线上实验以假设驱动，五个关键指标——用户参与、任务成功率、延迟、Token 消耗与单用户成本——决定每一次改动去留。

1. 开场：一个季度，25 个新模型（约 0:00–1:04）

Julia Kasper 走上 GitHub Universe 2026 的舞台，先问了台下一件事：有多少人听过“编码框架”（coding harness）这个词。举手的人不少；再问一句——有谁能自信地讲清楚它到底是什么，举起的手就明显少了。她点名坐在后排的两位 VS Code 工程师：正是他们把 GitHub Copilot 的框架集成进了 VS Code。整场演讲就是要回答那个没人举手的问题：当新模型一个接一个到来时，Copilot 团队到底在调什么。

她给出的第一组数字定下了全场的基调：仅这个季度，GitHub Copilot 就上线了 25 个新模型。模型来得如此之快，以至于“上新模型”在 Copilot 团队里已经不是一次性的发布事件，而是一项常态化的工程工作。演讲的标题点明了主题——每一次新模型上线，团队都要重新优化一遍 Copilot——而她接下来的十二分钟，就是把这句标题拆成一套可以执行的工作方法。

需要先说明这场演讲的形式：它不是访谈，而是一场带幻灯片的舞台演讲。Kasper 全程站在讲台边，配合十余页幻灯片讲解；幻灯片上的图表与流程图是本报告引用的主要一手材料，演讲者口头补充的数字则按自述处理，见末页注。

2. 智能体 = 模型 + 框架（约 1:04–2:38）

Kasper 先给出全场最重要的一条定义：一个智能体，本质上是模型与编码框架的组合。模型是推理引擎——权重与训练发生的地方，知识与能力由此而来，推理与规划也由它完成。框架则是模型周围的整个系统，是用户在 VS Code 里实际看到、实际交互的那一层。

■ 编码框架（Coding Harness）：围绕模型的整套系统，负责向模型提供系统提示词与指令、暴露工具接口与数据模式、驱动智能体循环与会话运行，并管理上下文、权限与安全关卡。

幻灯片把框架的构成拆成六项：系统提示词与指令、工具接口及其模式（schema）、智能体循环与会话运行时、上下文管理与检索、权限、钩子（hooks）与安全关卡，以及子智能体、技能（skills）与工作流。模型一侧的构成则只有四项：权重与训练、推理与规划能力、原生的工具调用行为、上下文窗口。两边一对比，Kasper 的判断就有了落点：框架不是模型的附属品，而是决定用户最终拿到什么的那一半。

“Same model, different harness — different product quality.”

同一模型，换一个框架，产品质量就不同。

她把这句话又说了一遍，换了一个更贴近用户的版本：同一模型装进不同的框架，产出质量会受到“重大的影响”，而 Copilot 团队每天与客户打交道时都能看到这一点。这也是整场演讲的立论基础——如果框架能决定质量，那么每一次新模型上线，真正要调校的东西就不是模型，而是框架。

■ 智能体循环（Agent Loop）：一次会话中模型与工具反复交互的运行过程——模型决定调用哪个工具、读取返回结果、再决定下一步，直到任务完成。

■ 系统提示词（System Prompt）：写给模型的底层指令，规定它如何行事；框架通过它把产品行为“教”给模型。

3. 为什么这件事重要：未经调校的框架会拖垮模型（约 2:38–4:14）

接下来的幻灯片把风险说得毫不含糊：把一个新模型直接丢进未经调校的框架，通常会让质量下降——哪怕这个模型客观上更强。Kasper 在这里引用了 Anthropic 的一句话，幻灯片注明出处为 2026 年 4 月 23 日 Anthropic 发布的《关于近期 Claude Code 质量报告的更新》。

“Each model behaves slightly differently, and we spend time before each release optimizing the harness and product for it.”

每个模型的行为都略有不同，我们会在每次发布前花时间优化框架与产品。—— Anthropic，2026 年 4 月 23 日

这句话成立的原因，Kasper 在口头上补了一句：新模型每次出现，行为方式都“略有不同”，尤其是在不同供应商之间。有的模型调用某个工具时更积极，有的则更“懒”——这是她在讲供应商合作时用的原话，指的是模型性格上的差异。框架的任务，就是在模型上线之前把这些差异一一抹平：让它调用正确的工具、遵循正确的系统提示词、在 Copilot 的会话流程里不出错。

幻灯片把“为什么这件事重要”落到三条与 Copilot 身份直接相关的理由上。第一，模型选择而不是锁定：用户可以按任务、预算与自身政策挑选最合适的前沿模型，而不是被绑在一家供应商身上。第二，每一个模型都要调进来：选择只有在每个选项都被认真集成之后才是真实的，团队为发出的每一个模型都做了这份工作。第三，多供应商让人保持诚实：同时跑多个模型，团队能拿到跨供应商的对比信号，不仅在同一模型家族内比较，也能在不同供应商之间比较，从而知道该为哪个模型调什么。

这三条理由其实是一条逻辑链：正因为 Copilot 的核心身份是模型选择，它才不能只服务好一家模型；正因为要服务好每一家，它才必须在每次上线前把框架调好；也正因为它同时服务多家，它才能反过来用横向对比知道自己调得对不对。模型选择在这里既是产品定位，也是工程方法。

4. 模型选择不是锁定：六家供应商与 Fusion（约 4:14–5:02）

Kasper 说，Copilot 的模型集成策略“很简单”：不把用户锁在任何一家供应商身上。为此团队与所有大型模型供应商都建立了合作关系，并且每周与每一家对表，随时掌握新模型何时到来。合同允许供应商提前透露新模型的发布时间，所以团队往往在模型正式发布之前就已经知道要做什么准备。

“We don’t just want you to be locked into one vendor.”

我们不想把你锁在任何一家供应商身上。

幻灯片上列出的供应商一共有六家：OpenAI（GPT 系列）、Anthropic（Claude 系列）、Google（Gemini 系列）、Microsoft（MAI 系列）、xAI（Grok 系列）与 Moonshot AI（Kimi 系列，开放权重，由 Fireworks 托管）。六家之上还有一行单独的标题：GitHub Copilot Fusion——Copilot 的多模型运行时，Kasper 提到 Fusion 发布后，团队还要确保它在多个供应商的模型之间都能正常工作。

每周对表、提前知会、逐个调校——这三件事合起来，就是 Copilot 把“模型选择”从一句口号变成现实的办法。Kasper 没有展开谈任何一家的具体模型，而是把重点放在机制上：选择本身不是自动发生的，它是靠一套合作与工程流程维持的。

■ Copilot Fusion：GitHub Copilot 的多模型运行时，让一次任务可以在多个供应商的模型之间协同完成，而不是只绑定某一家模型。

5. 接入流程：从提前知会到上线日（约 5:02–6:34）

模型集成的工作流程在幻灯片上画成一条六步的链。第一步，供应商宣布即将发布的新模型；第二步，把新模型的检查点接入 Copilot API，让它进入 Copilot 的系统与平台；第三步，也是核心一步，优化框架——调系统提示词、工具接口、上下文管理与智能体循环；第四步，跑离线基准评测并做内部试用；第五步，把发现分享给模型供应商；第六步，模型上线日。

这条链的特别之处在于第五步之后还有回路。Kasper 说，团队把评测发现分享给供应商之后，有时对方会回传一个更新过的模型检查点——根据 Copilot 的反馈改过之后的新版本；有时对方还会反过来给建议，因为供应商离模型训练更近，更清楚某个模型的“性格”，比如它调用某个工具时是不是偏懒。于是调校变成双向的：Copilot 调自己的框架，供应商调自己的模型检查点，双方朝着同一个目标收敛。

幻灯片的副标题点出了这条流程的性质：框架与模型是“共同发货”的。由于新模型每四到六周就到来一次，升级不是一次性的迁移，而是工程团队的一项经常性工作纪律。换句话说，Copilot 的质量不是在某一次发布里“修好”的，而是在每四到六周重复一次的流程里维持的。

■ 内部试用（Dogfooding）：在模型正式发布之前，先让内部员工在真实工作中使用它，靠实际体感发现基准测不出来的问题。

■ 离线评测（Offline Evals）：不依赖真实用户流量，事先用一套固定的基准任务集反复运行模型与框架，衡量任务解析率、成本等指标。

6. 评估永不停：离线基准、内部试用与公开榜单（约 6:34–8:57）

上线日不是终点。Kasper 的下一页幻灯片标题是“评估让人保持诚实”，副标题写得更直白：一次模型上线开启了这个循环，但没有结束它——上线前后，两条循环都在继续跑。上线前是离线评测，包括基准测试与内部试用；上线后是在线实验，包括 A/B 测试与每周汇报。

离线评测的核心是一套精心维护的基准组合。幻灯片写明，团队会持续更新基准组合：加入影响大、代表最新水平的新基准，剔除价值变低或已被污染的旧基准。现场展示的图表横轴是每任务平均成本、纵轴是任务解析率，当前视图是 DeepSWE 1.1——每轮 113 个任务，每个配置观测 2 至 5 次——图中同时出现了 Copilot CLI、Claude Code 与 Codex CLI 三种框架的身影，比较的是同一模型在不同框架里的表现。

评测的节奏分四档。回归评测在每次改动、每三小时与每日发布时各跑一次；每日评测是一套小而信号强的常规组合；每周与竞品评测覆盖更广的能力面与竞争对手；按需评测则用于建立基线、调查问题、新模型上线与回应外部说法。Kasper 口头补充说，团队还会把同一套基准跑在竞品的框架上，比较不同计算场景下的表现，看自己哪里还需要更好。

内部试用是另一条并行的线。团队在微软与 GitHub 内部有不同的试用渠道，靠实际使用“感受”某个模型用起来怎么样——她的原话是去“get the vibe”，看看东西用起来的感觉对不对。基准给数字，试用给体感，两者合起来才构成上线前的判断。

公开的部分则是一个网站：benchmarks.github.com。Kasper 说，网站是前一天刚刚发布或更新的，站内公开了两项基准——DeepSWE 1.1 与 Terminal-Bench。现场展示的 DeepSWE 1.1 排行榜上，Copilot Fusion 以 78.1% 的任务解析率居首（MAX 推理档），其后是 Claude Opus 5.5、GPT-6.1-sol 等模型。她承诺，随着新模型不断加入，网站会持续更新。

■ 任务解析率（Resolution Rate）：基准任务中被智能体成功解决的比例，是这场演讲里衡量质量最核心的数字。

■ Terminal-Bench：一项在终端环境里完成真实任务的公开基准，GitHub 在演讲前一天刚把它纳入公开基准站。

7. 线上实验：假设、离线验证、生产 A/B 与关键指标（约 8:57–11:03）

上线后的工作，Kasper 用一句话概括：每一次框架改动都是一条假设，先离线验证，再到生产环境中证明。幻灯片把这条链画成四格：假设——在框架仓库里开一个 issue；离线评测——针对提交的 PR 跑基准；内部先行发布——内部先以 10/10、再以 50/50 的 A/B 比例试用；公开——再以 10/10、再以 50/50 的比例推向客户。每一步都有明确的通过条件：离线评测先确认改动没有造成回归，内部试用先拿到内部数据，觉得有把握之后，才会尽快推向公开。

“Every harness change is a hypothesis, validated offline first and then proven in production.”

每一次框架改动都是一条假设，先离线验证，再到生产环境中证明。

她还给了一个真实的例子。幻灯片左侧是一份实验 issue：[Experiment] Remove worked tool examples from the current prompt（实验：从当前提示词中移除已完成示例），编号 #15735，右侧则是对应的生产记分卡截图。演讲没有展开这项实验的最终结论——它在这里的作用是展示流程本身：一个假设如何从 issue 出发，经过离线评测，进入生产记分卡，最后由数据决定是否全面推广。

决定改动去留的，是五项关键指标：用户参与、任务成功率、延迟、Token 消耗与单用户成本。其中用户参与的信号很直接：如果突然有大量用户从某个模型切换出去，就说明“有些地方不对劲”。延迟也要看齐：某个模型完成任务耗时明显更长，用户是能直接感受到的。而 Token 消耗与单用户成本之所以被单列出来，是因为越来越多企业客户——包括微软自己——开始盯着 Token 效率与每个用户的成本看。

■ 内部先行发布（Staff Shipping）：改动先只推给内部员工使用，拿到内部数据、确认无误之后，再推向公开用户。

■ Token 效率（Token Efficiency）：完成同样任务所消耗的 Token 数量；消耗越少，单用户成本越低，企业客户越在意这个数字。

8. 收束：框架即产品（约 11:03–12:17）

收束页只有三条，每条一句话。第一，框架即产品：模型是买来的许可，框架是工程化的成果——质量就住在这里。第二，每一次模型上线都是一次调校练习：提示词、工具、上下文与循环，都要在上线前与供应商一起重新调过。第三，评估永不停：离线基准持续跑，在线实验在生产环境中证明每一次改动。

“The model is licensed. The harness is engineered — and that is where quality lives.”

模型是买来的许可，框架是工程化的成果——质量就住在这里。

三句话其实把整场演讲收成了一个判断：当模型越来越像一种可以买到的商品，真正的产品工作就转移到了模型外面——提示词怎么写、工具怎么暴露、循环怎么跑、评测怎么做。Kasper 最后向台下致谢，并请有问题的人留下来找她与在场的 VS Code 工程师聊聊框架具体是怎么落地的，尤其是在 Copilot 框架方向上的工作。

这场演讲没有给出任何一行代码，也没有演示任何一个产品功能。它讲的是一套工作方法：当新模型每四到六周就到来一次，唯一能让质量跟得上的办法，是把“调框架”变成流程、把“评测”变成习惯、把“模型选择”变成每天都在维持的现实。模型会继续换，框架是留下来、越调越好的那部分。

讨论问题

1. 如果同一模型在不同框架里质量天差地别，评测模型时应不应该把框架也写进成绩单？

2. Copilot 把模型选择当作核心身份：对用户来说，多模型可选的价值大，还是单一模型深度优化的价值大？

3. 供应商每周对表、提前拿到新模型检查点——这种合作深度对小团队可复制吗？没有合作关系时该怎么办？

4. 离线基准、内部试用、线上实验三条线，哪一条最容易只报好消息？可以怎么防？

5. Token 消耗与单用户成本成了关键指标：当成本成为优化目标，会不会反过来牺牲任务成功率？

6. “框架即产品”——如果模型是买来的许可，框架是工程化的成果，那么一家公司的护城河到底在模型还是在框架？
